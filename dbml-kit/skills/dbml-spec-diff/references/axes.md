# dbml-spec-diff 분석축 상세

SKILL.md의 7개 섹션을 쓸 때 이 예시·규칙을 따른다. 분석 시작 전 1회 읽는다.

## Input validation 상세
DBML 쪽 입력이 진짜 DBML인지 먼저 확인:
- `CREATE TABLE`/`VARCHAR(n)`/`PRIMARY KEY`/`FOREIGN KEY ... REFERENCES`/`ENGINE=`/끝 `;` 같은 SQL DDL 시그널이 보이면 DBML이 아니다 → "DBML 쪽 입력이 SQL DDL로 보입니다. 정확한 비교를 위해 DBML로 변환하거나 원본 `.dbml`을 공유해 주세요"로 응답, **추정 진행 금지**.
- 빈 파일·문법 오류·부분 입력이면 어디가 불완전한지 한 줄로 지적하고 완전한 DBML 요청. 깨진 스키마를 정상처럼 비교하지 않는다.

## Input handshake
분석 전 각 측을 한 줄로 명시:
> DBML: `schemas/order.dbml` (87 lines)
> 기획서: `docs/PRD-주문.md` (3 sections)

어느 쪽이 모호하면 diff 전에 사용자에게 확인. 임의로 고르지 않는다.

## §1 커버리지 매트릭스
기획서 **business object**별 → DBML 테이블 매핑표.

| 기획서 개념 | DBML 테이블 | 상태 |
|---|---|---|
| 회원 | `users` | OK |
| 주문 | `orders` | OK |
| 환불 | (없음) | **누락** |
| 적립금 | `point_ledger` | **부분** (충전만 있고 사용 흐름 없음) |

상태: `OK` / `부분` / `누락` / `초과`(DBML에만 있고 기획서 미언급).

## §2 누락 (기획서엔 있으나 DBML에 없음)
각 항목:
- 기획서 출처 (섹션/문장 1줄 인용)
- 어디에 추가할지 (테이블 신설 / 기존 컬럼 추가 / 새 enum 값)
- 의존 관계 (이 누락이 다른 누락의 원인인가)
순서: 비즈니스 영향 큰 것부터.

## §3 초과 (DBML엔 있으나 기획서 미언급) — 시니어 PM이 가장 먼저 봄
- 정당한 시스템 컬럼(created_at/updated_at/deleted_at/version) → 무시
- 미래 기능 / 기술 부채 / 옛 기획 잔재 / 정말 빠진 기획?
각 항목에 "왜 있는지 묻는 질문" 1개 첨부.

## §4 의미 불일치
같은 이름 다른 의미 OR 다른 이름 같은 의미:
- 기획서 "주문 취소" / DBML `orders.status = 'refunded'` → 취소와 환불은 다른 개념인가?
- 기획서 "적립금 잔액" / DBML `users.point_balance` vs `point_ledger` 합계 → SoT 어디?

## §5 관계(cardinality) 충돌
기획서가 암시하는 cardinality와 DBML `Ref` 충돌만. 약어는 풀이 병기(`glossary.md`).
- 기획서 "한 주문에 하나의 결제 수단" / DBML `orders` ↔ `payments` 1:N(하나가 여럿) → 분할결제 의도?

> **추정 가드**: 기획서가 cardinality/관계/제약을 명시 않고 문맥으로만 암시하면 충돌이라 단정 말고 "기획서가 명시 않았으나 ~로 읽힘(추정) → 개발자 확인 질문: …" 형태로 표시. 스킬 추론을 기획서 규정 위반처럼 제시하지 않는다.

## §6 위험도 분류 (Top 3)
모든 항목을 P0/P1/P2로 분류, 상위 3개만:
- **P0**: 출시 차단. 핵심 비즈니스 흐름 표현 불가.
- **P1**: 출시는 되나 후속 마이그레이션 큰 영향.
- **P2**: 명명/주석/문서 차원.

> **추정 가드**: 추정 기반(명시 안 된 스킬 추론) 항목은 P0로 올리지 않는다. 명시된 충돌만 P0 후보.

## §7 개발자 합의용 질문 묶음
§3~§5 질문을 **복사 가능한 체크리스트**로(PM이 손으로 안 추리게). P0→P1→P2. 각 줄:
`[근거: 기획서 인용 또는 table.column]` `[질문]` `[내 추정 답]` `[왜 중요한지 1줄]`

예:
> - **[P0]** `[기획서 "환불 가능"]` `refunds`/`refund_amount`가 안 보이는데 환불 데이터는 어디 저장되나요? (추정: 미구현) — 핵심 흐름 표현 불가.
> - **[P1]** `[orders ↔ payments = 1:N]` 분할결제 의도인가요? (추정: Yes) — 후속 마이그레이션 영향.

질문이 많거나 explain 결과까지 합쳐야 하면 [[dbml-questions]]로 위임하고 이 섹션은 링크로 대체.

## Style rules 상세
- 비난 톤 금지. "~가 빠졌다" 대신 "기획서엔 있는데 DBML에서 못 찾음. 의도된 분리인지 확인 필요".
- 원문에 없는 도메인 사실은 추정 표기.
- 결론 먼저, 근거 뒤 (PM 가독성).
- "FK"/"normalization"/"index" 등 개발자 용어는 항상 풀어쓴다(`glossary.md`). 약어 단독 금지, 첫 등장 시 풀이 병기.
- 길이: 1화면 ±50%. 매트릭스 + 누락/초과 핵심만.

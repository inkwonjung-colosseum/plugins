# dbml-explain 출력 상세 규격

SKILL.md의 6개 섹션을 쓸 때 이 파일의 예시·규칙을 그대로 따른다. 분석 시작 전 1회 읽는다.

## Input validation 상세

비개발자는 DBML과 SQL DDL을 구분하지 못하므로 이 검증이 이 스킬의 존재 이유다.

**SQL DDL 감지 시그널** — 하나라도 보이면 DBML이 아니라 SQL DDL이다:
`CREATE TABLE`, `VARCHAR(n)`/`INT(n)` 괄호 길이 표기, `PRIMARY KEY (...)`, `FOREIGN KEY ... REFERENCES`, `ENGINE=`, 문장 끝 `;` 세미콜론 구분.

감지 시 **절대 추정으로 진행하지 말고** 다음으로 응답:
> 이건 DBML이 아니라 SQL DDL(데이터베이스 생성 구문)로 보입니다. 이 스킬은 DBML 전용이라 그대로 설명하면 부정확할 수 있어요. DBML로 변환해 드릴까요, 아니면 원본 `.dbml` 파일이 따로 있나요?

**Malformed/partial 감지** — 다음이면 채워 넣지 말고 멈춘다:
`Table` 블록 `{` 미닫힘, 본문 없는 빈 `Table`, 테이블 0개, 파일 읽기 실패, 중간이 잘린 부분 붙여넣기.
처리: 추정으로 빈칸을 메우지 말고 **어느 부분이 불완전한지 한 줄로 지적**하고 완전한 DBML을 요청한다. 부분 입력을 완전한 스키마처럼 설명하지 않는다.

**Dangling/순환 ref** — `Ref`의 대상 테이블이 스키마에 없으면(dangling) 정상 관계로 설명하지 말고 "참조 대상 `X`가 정의에 안 보임 — 의도인지 확인" 질문으로 돌린다. 순환 관계(A→B→C→A)는 §6에 노트.

## §1 한 줄 요약
`Project` 블록에 `Note`가 있으면 그 내용을 **1차 근거**로 삼는다(작성자가 직접 적은 도메인 설명이라 추정보다 정확). `database_type`(PostgreSQL 등)은 비개발자에게 무관하니 생략.

## §2 핵심 엔티티
**Table alias**: `Table users as U { ... }` 면 실제 테이블명 `users`로 해석. `Ref`의 alias(`U`)는 `users`로 환원. alias를 별개 테이블로 오인 금지. schema-qualified(`Table ecommerce.users`)도 테이블명 `users`로 읽되 스키마는 메모만.

각 `Table`:
- **테이블 이름**(technical) — **비즈니스 의미**(친근한 이름)
- 한 줄로 "무엇을 저장하는가". 기술 용어 금지.
- 주요 컬럼 3–5개만 자연어 풀이. `created_at` 같은 시스템 컬럼 생략.
- **연결 컬럼은 항상 포함**: `_id`로 끝나거나 다른 표를 가리키는 컬럼은 3–5개 제한과 무관하게 항상 포함, "~를 가리키는 연결"로 풀이 → §3 관계와 연결됨.
- **Note 우선**: 테이블/컬럼/standalone `Note`(또는 `[note: '...']`)가 있으면 명명 추정보다 **Note 원문 우선 인용**. Note가 의미를 명시한 항목은 §6 추정 대상에서 제외.
- **nullable/필수**: `[not null]`은 "필수 입력", `[null]`/무표기는 "선택"으로 1줄 풀이 — "이 값이 꼭 있어야 하나?"는 비개발자 1차 질문이다.

예:
> **orders** — 주문
> 고객이 결제한 주문 내역을 보관한다. 누가(`user_id`), 언제(`placed_at`), 얼마(`total_amount`), 어떤 상태(`status`)인지 기록.

## §3 관계 (Refs)
**3가지 문법 — 셋 다 같은 의미로 읽는다:**
1. inline `col int [ref: > other.id]`
2. standalone `Ref: a.col > b.id`
3. block `Ref name { a.col < b.id }`
**composite ref** `Ref: orders.(a,b) > x.(c,d)` 는 두 컬럼을 묶어 **하나의 연결**, 1문장 풀이.
**self-ref** `Ref: employees.manager_id > employees.id` 는 "같은 표 안에서 한 직원이 다른 직원(상사)을 가리킴"으로 풀이.
**참조 액션** `[delete: cascade]` 등은 "사용자 삭제 시 주문도 같이 삭제됨"처럼 비즈니스 결과로 풀이.

각 ref는 비즈니스 문장으로 — never "FK":
`Ref: orders.user_id > users.id` → "한 명의 **사용자**는 여러 개의 **주문**을 가질 수 있다. (1:N = 하나가 여럿을 가짐)"

**카디널리티 표기 규칙** (PM은 `N:M` 약어를 본 적 없다):
- `1:N`/`N:M`/`1:1` 약어를 **단독 사용 금지**. 첫 등장 시 1회 괄호 풀이 — `(1:N = 하나가 여럿을 가짐)`, `(1:1 = 서로 하나씩)`.
- `N:M`(연결 테이블)은 **반드시 연결 테이블 비즈니스 문장**으로 풀이:
  → "한 주문엔 여러 상품이 담기고 한 상품은 여러 주문에 담길 수 있어, 그 사이를 `order_items`가 잇는다. (N:M = 양쪽 모두 여럿, 중간 연결표가 둘을 이어줌)"
- 화살표 방향(`>`/`<`/`-`/`<>`) 매핑은 `glossary.md`의 'Ref 표기 → 방향 풀이' 표 기준. 비개발자에겐 화살표가 아니라 "누가 하나이고 누가 여럿인지"만 말한다.

Group by cardinality, 가장 중심 엔티티부터 바깥으로.

## §4 Enums
각 `Enum`을 허용 상태 불릿 목록 + 비즈니스 의미로. 값별 `[note: '...']`이 있으면 우선 인용. `Note` 없으면 명명에서 추정하되 (추정) 표기.

## §5 비즈니스 시나리오
실제 table/column명으로 1–2개 짧은 서술 (PM이 실제로 읽는 섹션):
> 회원가입(`users` 신규 row) → 장바구니 담기(`cart_items` 추가) → 결제 시 `orders` 1건 + `order_items` 다건 생성, `status=paid`.

`default`가 있는 `status`/`state`는 **초기 상태로 명시**: `status varchar [default: 'pending']` → "주문은 처음엔 `pending`(대기) 상태로 생긴다."

## §5.5 용어 사전 (양방향)
비즈니스 용어 ↔ DBML 식별자 **양방향** 표. 테이블·주요 컬럼·enum 값 포함. "개발자가 X라 하면 기획서의 Y" 역방향 조회가 되게 양쪽 정렬.

| 비즈니스 용어 | DBML 식별자 | 방향 메모 |
|---|---|---|
| 환불 금액 | `orders.refund_amount` | PM "환불 금액" = 개발자 `refund_amount` |
| 결제 완료 상태 | `order_status.paid` | "결제됨" = enum 값 `paid` |
| 회원 | `users` | 양쪽 동일 |

약어 풀이는 `glossary.md` 기준 통일.

## §6 누락/모호 → 개발자 질문
막힌 지점을 **개발자에게 그대로 보낼 질문 형태로 1줄씩** (서술 아니라 질문으로 끝):
- 불명확 컬럼 → "`status_v2`가 기존 `status`와 어떻게 다른가요? 마이그레이션 중인가요?"
- `Note` 없는 enum → "`order_status` 각 값이 비즈니스에서 어떤 단계인가요?"
- 비대칭 관계: **단정 말고 질문으로만** (의도된 분리일 수 있음) → "`refunds`와 `orders` 연결이 안 보이는데 의도된 분리인가요?"
- 명명 불일치 → "`user_id`와 `member_id`가 같은 대상인가요?"

질문 5개 초과 시 [[dbml-questions]]로 라우팅. 기획서가 있으면 [[dbml-spec-diff]]로 핸드오프.

## Style rules 상세
- 약어 풀어쓰기: PK/FK/UK는 `glossary.md` 기준 통일 (PK→"고유 식별값", FK→"~를 가리키는 연결", UK→"중복 불가 값").
- **index**: `[unique]`/`[pk]` (composite) 인덱스는 **비즈니스 유일성 규칙 1줄**: `indexes { (user_id, product_id) [unique] }` → "한 사용자는 같은 상품을 중복으로 담을 수 없다." 성능용 인덱스는 언급 안 함.
- `snake_case`는 표기 그대로 두고 직후 한국어 의미 풀이.
- 추측은 "(추정)"/"DBML 주석 없어 명시 안 됨" 표기.
- 길이: 테이블 10개 기준 1–2화면. 컬럼 전부 나열 금지.
- **대용량**(테이블 ~20개 초과): (1) 중심 엔티티(ref 최다) 핵심 N개만 깊게, (2) 나머지는 표 한 줄 요약, (3) 첫머리에 "전체 X개 중 핵심 N개 설명, 나머지 M개 요약 — 더 필요하면 지정"을 명시. **어떤 테이블도 무언급 누락 금지**.
- 코드블록 미사용. 식별자만 백틱.

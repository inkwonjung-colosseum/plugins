# 정책서·기능정의서 → 화면 세트 도출

> **이 파일의 목적**: 기능정의서/정책서로 화면을 만들 때 **리스트 한 장만 뽑는 실패**(과소)와
> **정책을 통째로 화면화하는 실패**(과다)를 둘 다 막는다.
> 정책서는 보통 CRUD + 상태머신 + 권한을 정의한다. 화면은 그만큼 나오되, **사용자가 조작하는 것만** 나온다.

## 0. 사용자 중심 필터 — 조작 화면만 만든다 (먼저 적용)

화면을 도출하기 전에 **"이 화면을 실제 사용자가 조작하는가?"**를 먼저 묻는다.
정책서의 모든 표가 화면이 되는 건 아니다. **정책의 제약은 화면이 아니라 affordance다.**

| 정책 요소 | 잘못 — 독립 화면/탭으로 | 맞음 — 조작 화면 안 affordance로 |
|-----------|------------------------|-------------------------------|
| 권한 테이블(§역할/권한) | "권한 정책" 탭에 표 그대로 | 세션 권한으로 **버튼 노출/숨김**. 권한 없는 액션은 안 보이게 |
| 이동·전이 통제 매트릭스 | "이동 통제 매트릭스" 탭 | 차단 시도 시 **토스트/인라인 안내**, 허용 전이만 라디오 노출 |
| 자동 변경/자동 전환 규칙 | 규칙표 화면 | 해당 엔티티 **상세/모달 안 안내 배너** ("이 Zone 들어오면 BAD") |
| 불변/잠금 규칙 | 별도 안내 페이지 | 폼 필드 **disabled + 자물쇠 라벨** |
| 플랫폼/설정 도메인에서 정의(제외 대상) | 만들지 마라 | 만들지 마라 (조회조차 MVP 제외면 생략) |

**판별 기준 3가지** — 셋 중 하나라도 "아니오"면 독립 화면으로 만들지 말고 affordance로 흡수:
1. 이 화면에서 사용자가 **데이터를 만들거나 바꾸는가?** (순수 참조표는 화면 아님)
2. 이 surface의 **주 사용자가 직접 보는가?** (플랫폼/설정 도메인 화면은 그 도메인 몫)
3. 정책서가 이 화면을 **MVP 범위로 두는가?** (`(Non-MVP)`/"화면 구축 제외"면 생략)

> 정책 이해를 돕는 참조 시각화(매트릭스·권한표)가 정말 필요하면 산출물이 아니라 **별도 부록**으로 분리하고,
> 운영 화면에는 섞지 마라. 운영 화면은 "사용자가 지금 할 일"만 담는다.

## 1. 액션 전수 (화면 도출의 시작)

정책서에서 다음 4개 테이블을 **전수**해 화면·모달 목록을 만든다. 하나라도 건너뛰지 마라.

| 정책서 섹션 | 도출물 |
|------------|--------|
| **권한 테이블** (Create/Read/Update/Delete) | 각 액션 → 화면 또는 모달 |
| **상태 정의 + 상태 전이 규칙** | 각 전이 → 상태 변경 UI(모달) + 사유 입력 |
| **생성/속성 규칙** | 생성 폼 + 필드별 잠금/조건부 노출 |
| **예외·승인 기준** | 예외 흐름(차단 안내, 권한별 허용) UI |

## 2. 표준 admin CRUD 화면 세트

마스터/엔티티 관리 정책서는 거의 항상 이 세트가 나온다. 빠진 화면이 있으면 정당화하라.

1. **리스트(조회)** — 필터·검색·정렬, 행 클릭 → 상세. stat 요약.
2. **생성 폼** — 필수 필드, 조건부 필드(타입별), 자동 발번 안내, 중복 검증.
3. **수정 폼** — 생성과 동일 골격, **불변 필드 잠금**(정책서의 "수정 불가" 항목).
4. **상세** — 읽기 전용 + 상속 정책 표시 + 인스턴스 속성.
5. **상태 변경 모달** — 현재 상태별 허용 전이만, 차단 전이 안내, **사유 코드 필수**.
6. **예외/승인 흐름** — 권한별 허용·차단, 사유 관리.

> 정책서에 "삭제 불가, Inactive 처리"가 있으면 Delete 버튼 대신 **상태 변경**으로 흡수한다.

## 3. 각 surface에 5상태 매핑 (state-coverage 연동)

리스트·폼·상세 각각에 `craft/state-coverage.md`의 **5상태**(loading/empty/error/populated/edge)를
적용한다. populated만 그리는 게 가장 흔한 AI 실패다.

- 리스트 → empty(검색 0건), loading(skeleton), error(재시도), edge(10k행/긴 문자열)
- 폼 → untouched/dirty/submitted-pending + 검증 에러(`craft/form-validation.md`)
- 상세 → 선택 옵션 누락 시 "미적용" 표시

## 4. 완결성 체크리스트 (산출 전 P0 — 통과 못 하면 미완성)

- [ ] **사용자 중심 필터(§0)** 통과 — 순수 참조표(권한/이동 매트릭스)를 독립 탭/화면으로 만들지 않았는가? 제약은 affordance(버튼 게이팅·차단 안내·잠금)로 흡수했는가?
- [ ] 권한 테이블의 **모든 액션**(C/R/U/D)에 화면 또는 모달이 있는가?
- [ ] 상태 전이표의 **모든 전이**(허용/차단/자동)에 UI 또는 안내가 있는가?
- [ ] 생성 폼: 필수 필드·조건부 필드·자동 발번·중복 검증이 모두 있는가?
- [ ] 수정 폼: 정책서의 **불변 필드가 잠겨** 있는가?
- [ ] 각 리스트/폼/상세에 **5상태**가 렌더되는가? (populated만 아님)
- [ ] 상태 변경에 **사유 코드 입력**이 강제되는가?
- [ ] 차단 전이(예: Active→Inactive 직접)에 **차단 안내**가 있는가?
- [ ] 정책서의 `[미확정]`/`(Non-MVP)` 항목은 UI에 "미정의/추후" 라벨로 **명시**했는가? (지어내지 마라)
- [ ] 권한 레이어별(Authority/Lead/Operator/External) 버튼 노출이 정책서와 맞는가?

## 5. 산출 형태

- 단일 프로토타입이면: 리스트 + 오버레이(생성/수정 슬라이드오버, 상태변경 모달, 상세 드로어)로 통합.
  → `examples/wms-zone-console.html`가 이 패턴의 레퍼런스 품질 기준.
- 여러 화면이면: 화면별 HTML 파일 + 공통 LNB/토큰.

> 의심되면 **리스트만 만들지 마라.** 위 체크리스트로 누락 화면을 먼저 나열한 뒤 작업한다.

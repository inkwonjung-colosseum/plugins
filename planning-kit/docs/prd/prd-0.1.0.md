# planning-kit PRD

## 1. 개요

`planning-kit`은 사용자가 제공한 기획 초안을 **정책서 + 기능설계서 두 템플릿으로 변환**하고, 변환 직후 **같은 흐름에서 자동 리뷰**까지 한 번에 진행하는 단일 스킬 플러그인이다.

산출물은 **로컬에 파일로 저장하지 않고 화면 output으로만 출력**한다. 사용자가 응답을 보고 직접 복사·반영한다. 파일 IO·timestamp·collision·폴더 구조 같은 저장 절차가 모두 사라져 속도가 빠르다.

기존 `product-team-kit`이 `set-config`, `plan-format`, `plan-review` 세 스킬로 분리되어 있던 흐름을 한 스킬로 합친다. 사용자는 한 번 호출하면 두 변환 본문과 리뷰 결과까지 같은 응답에서 받는다.

Claude Code와 Codex 양쪽에서 동작한다.

## 2. 목표

- 기획 초안(텍스트·파일·디렉터리)을 받아 **정책서**와 **기능설계서** 두 본문으로 동시에 변환한다.
- 변환 직후 같은 스킬 안에서 자동으로 두 본문을 리뷰한다.
- 변환 결과 + 리뷰 결과를 **단일 응답 화면 output**으로만 출력한다 (로컬 저장 없음).
- 설치 직후 별도 config 파일 없이 default 동작이 가능하다.

## 3. 비목표

- **로컬 파일 저장은 하지 않는다.** mkdir·Write 호출 없음. 산출물은 모두 응답 화면 output.
- timestamp 폴더, 안전기능명 정규화, collision suffix, staging→verify→rename 절차는 모두 없다.
- 별도 set-config 스킬, `.planning-kit/config.json`, `CLAUDE.md`/`AGENTS.md` 안내 블록 upsert는 하지 않는다.
- 변환과 리뷰를 별도 호출로 분리하지 않는다 (한 스킬 호출에서 둘 다 처리).
- 외부 시스템 자동 게시·snapshot 동기화는 하지 않는다.
- worker subagent 분리, 2층 출력 구조, GFM cell escape 알고리즘은 두지 않는다.
- marker 4종, 빈 위치 보존 원칙, 라벨 cross-bleed 검사, 중복·구조 retry는 두지 않는다.
- Gate First 변환 가능성 판정은 두지 않는다. 모든 입력은 변환을 시도하고 부족분은 리뷰가 남긴다.

## 4. 사용자와 시나리오

### 4.1 사용자

기획자, PM, 제품팀 운영자.

### 4.2 시나리오

1. **기획 노트 한 덩어리 → 두 본문 + 리뷰 (화면 output)**
   - 입력: `formalize` 호출 + 기획 노트 텍스트 또는 파일.
   - 출력: 정책서·기능설계서 본문 markdown + 리뷰 결과 list. 같은 응답에 모두 표시.
   - 사용자는 화면 출력을 보고 직접 복사·반영한다.

2. **기획자료 디렉터리 → 두 본문 + 리뷰 (화면 output)**
   - 입력: 디렉터리 경로.
   - 디렉터리 안 모든 UTF-8 텍스트 파일을 읽고 통합한 뒤 두 본문으로 분리해 화면에 출력.
   - 같은 응답에 리뷰 결과 함께 출력.

## 6. 단일 스킬 명세 — `formalize`

### 6.1 호출

- Claude Code: `/planning-kit:formalize <기획 초안 텍스트 또는 파일/디렉터리 경로>`
- Codex: `$formalize <기획 초안 텍스트 또는 파일/디렉터리 경로>`

기능명은 별도 인자로 받지 않는다. 입력 본문·파일명·디렉터리명에서 추출한다.

CLI 인자(optional):

- `--ssot-include <glob>` (리뷰 SSOT corpus 좁히기. default: 프로젝트 폴더 안 모든 `*.md` — 노이즈 폴더 `.git/`, `node_modules/` 자동 제외)
- `--no-review` (변환만 출력하고 리뷰는 건너뛴다)

### 6.2 동작 시퀀스

```
1. 입력 dispatch
   - 텍스트/파일/디렉터리 자동 분기
   - 기능명 추출 (출력 헤더용. 안전기능명 정규화는 안 함 — 파일 안 만들므로)
   - 여러 기능 후보가 있을 때: 1순위 1개만 처리.
     선택 우선순위 = 명시 주제 → 파일명/디렉터리명 → 반복 등장 제목 → 첫 핵심 명사구.
     그 외 후보는 변환에서 제외하고 §1.5 제외 추적에 기록.
   - Gate 없음. 입력 부족·근거 부족·범위 모호도 변환 시도하고
     리뷰 결과에 "근거 부족" 발견으로 남긴다.

1.5. 입력 제외 추적
   - 변환 본문에 반영하지 않은 입력 조각을 모두 기록.
   - 사유 카테고리:
     - `다른 기능 후보`: dispatch 1순위 외 기능 후보
     - `라벨 미매핑`: 정책/기능 어느 쪽으로도 분류 안 되는 본문(잡담·진행 메모·이모지 톤 등)
     - `중복`: 같은 내용이 다른 곳에 이미 반영됨
     - `근거 부족 무시`: [TBD]로도 못 채울 만큼 단편적이라 누락 결정
     - `포맷 노이즈`: 빈 줄·구분선·미완성 문장
   - 각 제외 항목 = {입력 위치(파일명·라인 또는 텍스트 인용 ≤80자), 사유 카테고리, 한 줄 설명}
   - 제외 0건이면 §7.1 출력 블록 생략.

2. 두 템플릿 변환 (항상 실행)
   - templates/기능설계서.md, templates/정책서.md 병렬 read
   - main이 같은 턴에서 두 본문을 직접 작성
   - 라벨 매핑: 화면·흐름·동작 → 기능설계서, 규칙·조건·예외 → 정책서
   - 라벨 매핑 안 되거나 중복인 입력 조각은 §1.5 제외 추적으로 보낸다.
   - 근거가 부족한 셀은 inline [TBD]로 채운다. 빈 row·섹션 삭제 허용.
   - 작성 결과는 메모리에만. 파일 저장 안 함.

3. 자동 리뷰 (--no-review가 아닐 때)
   - 메모리의 두 본문 + 입력 그대로 사용
   - main 단일 패스로 2축 점검 (worker 분리 없음)

   3a. 본문 자체 품질 (Self-Review)
       - 정책서·기능설계서 본문 자체 점검
       - 섹션 충실도: [TBD] 비율, 빈 row, 빈 섹션 식별
       - 라벨 cross-bleed: 정책서에 화면 동작·입력 방식이? 기능설계서에 허용/금지/판단 기준이?
       - 두 문서 간 용어 일관성: 같은 대상의 역할명·상태명·권한명·도메인 stem 통일
       - 정책-기능 매핑: 정책서의 규칙이 기능설계서의 동작에 반영되었는지
       - 누락 핵심 정보: 입력에 있었지만 본문에 빠진 항목

   3b. SSOT 충돌
       - 키워드 추출 (기능명·도메인·역할·상태·정책 핵심어)
       - SSOT corpus = 프로젝트 폴더 안 모든 *.md (노이즈 폴더 자동 제외)
       - 키워드 grep으로 매칭 file 추출
       - 매칭 0건 → 검증 대상 없음 (자체 품질만 점검)
       - 매칭 ≥1건 → 본문 확정 문장과 SSOT 매칭 file 비교

4. 통합 출력 (화면 output only)
   - 변환 본문 2개(정책서·기능설계서) + 입력 제외 항목 + 리뷰 결과를 한 응답 markdown으로 출력
   - 제외 항목 0건이면 해당 블록 생략
   - mkdir·Write 툴 호출 없음
```

**예외**: 입력이 literal 빈 문자열·whitespace 또는 읽을 수 있는 텍스트 0byte인 경우만 sanity check로 거른다 (한 줄 안내 후 종료). 그 외 모든 입력은 변환을 시도한다.

### 6.3 Marker

`[TBD]` 1종만 사용한다. 결정되지 않은 항목·근거 부족 셀에 inline 표기. `미결 사항` 색인 별도 운영 안 함. 빈 셀·빈 row 삭제 허용.

### 6.4 검사

라벨 cross-bleed, 중복, 빈 골격, 구조 일치 retry는 두지 않는다. main 직접 작성 그대로 저장한다.

### 6.5 리뷰 축

**2축**:

1. **본문 자체 품질 (Self-Review)** — 정책서·기능설계서 본문 자체 점검
   - 섹션 충실도 ([TBD] 비율·빈 row·빈 섹션)
   - 라벨 cross-bleed (정책서 ↔ 기능설계서 내용 어긋남)
   - 두 문서 간 용어 일관성 (역할명·상태명·권한명·도메인 stem 통일)
   - 정책-기능 매핑 (정책서 규칙이 기능설계서 동작에 반영)
   - 누락 핵심 정보 (입력에는 있었지만 본문에 빠진 항목)

2. **SSOT 충돌** — 두 본문 확정 문장이 같은 프로젝트 폴더 안 모든 `*.md` Markdown 문서와 충돌하는지 점검. 문서 종류·역할(정책/PRD/회의록/README 등) 구분하지 않고 일괄 corpus로 본다.

worker subagent 분리 없음. main이 단일 패스로 두 축 모두 점검한다.

SSOT corpus 인덱스 스캔, archive/draft 분류, version 우선 처리 같은 정렬 단계는 두지 않는다. 매칭 file을 그대로 read한다.

## 7. 출력 포맷

모든 출력은 화면 output (응답 markdown). 파일 저장 없음.

**정책서·기능설계서 본문은 ` ```markdown ... ``` ` 코드 펜스로 감싸 출력**한다. 사용자가 화면에서 코드 블록을 통째로 복사해 자기 문서 시스템(Notion·Confluence·Markdown 파일 등)에 그대로 붙여넣을 수 있도록 한다. 펜스 언어는 `markdown`으로 명시해 IDE syntax highlight를 활용한다.

### 7.1 정상 (변환 + 리뷰)

````markdown
# [기능명]

- 입력 처리: [직접 입력 / 파일 N개 / 디렉터리 텍스트 N개]
- 미결 표기: [TBD] N개
- 입력 제외: N건 (0건이면 "없음")

---

## 정책서

```markdown
[정책서 본문 — 10 섹션 markdown 그대로]
```

---

## 기능설계서

```markdown
[기능설계서 본문 — 8 섹션 markdown 그대로]
```

---

## 입력 제외 항목

발견 사항 (≥1건일 때만 출력. 0건이면 이 섹션 통째로 생략):

1. [한 줄 제목]
   - 사유: [다른 기능 후보 / 라벨 미매핑 / 중복 / 근거 부족 무시 / 포맷 노이즈]
   - 위치: [파일명:라인 또는 "직접 입력"]
   - 인용: "[입력 원문 ≤80자]"
   - 설명: [왜 본문에 안 넣었는지 한 줄]

---

## 리뷰 결과: [통과 | 발견 N건]

- 자체 품질 발견: N건
- SSOT 충돌 발견: N건 (SSOT 매칭 파일 N개)

### 자체 품질 (Self-Review)

발견 사항 (≥1건일 때만):

1. [제목]
   - 카테고리: [충실도 / cross-bleed / 용어 일관성 / 정책-기능 매핑 / 누락]
   - 위치: [정책서/기능설계서 §섹션]
   - 근거: "[변환 본문 인용]"
   - 영향: [한 줄]
   - 제안: [최소 수정 또는 확인 조건]

### SSOT 충돌

발견 사항 (≥1건일 때만):

1. [제목]
   - 위치: [정책서/기능설계서 §섹션] vs [SSOT 파일 §섹션]
   - 근거: "[변환 본문 인용]" vs "[SSOT 인용]"
   - 영향: [한 줄]
   - 제안: [최소 수정 또는 확인 조건]
````

자체 품질·SSOT 충돌 모두 0건이면 `## 리뷰 결과: 통과`로만 출력하고 두 sub-section 생략.

**fence 중첩 주의**: 위 §7.1 템플릿은 docs 가독성용 4-backtick fence(```` ```` ````)로 감싸져 있다. 실제 응답에서는 4-backtick fence wrapper를 출력하지 않고, 안쪽 본문(헤더, sub-section, 정책서·기능설계서 3-backtick 코드 블록 포함)만 그대로 출력한다.

### 7.2 빈 입력 sanity check

```
입력 비어 있음. 기획 초안 텍스트 또는 경로를 인자로 주세요.
```

literal 빈 문자열·whitespace·0byte 파일·완전 비어 있는 디렉터리에서만 출력한다. 그 외 모든 케이스는 §7.1로 처리한다 (근거 부족도 변환 진행 + 리뷰에서 남김).

### 7.3 `--no-review` 사용 시

리뷰 블록(`## 리뷰 결과`) 생략. 정책서·기능설계서 본문만 출력.

저장 실패 분기는 두지 않는다. 파일 IO가 없으므로 실패 단계 없음.

## 8. 통합 vs 분리 (vs product-team-kit)

| 항목 | product-team-kit | planning-kit |
|---|---|---|
| Skill 수 | 3 | 1 |
| 변환·리뷰 호출 | 2번 (`plan-format` → `plan-review`) | 1번 (`formalize`) |
| Agent worker | 1 (terminology) | 0 |
| Reference 수 | 5 | 1 |
| Template 수 | 2 (정책서 + 기능설계서) | 2 (정책서 + 기능설계서) |
| 산출물 | 정책서 + 기능설계서 2 file (`<outputRoot>/.../*.md`) | 정책서 + 기능설계서 본문 화면 output (저장 안 함) |
| 파일 IO | mkdir + Write 호출 | 없음 |
| Config 파일 | `.product-team-kit/config.json` 필수 | 없음 (default + CLI 인자) |
| `CLAUDE.md`/`AGENTS.md` upsert | 항상 | 안 함 |
| Marker | 4종 + `해당 없음` fill | 1종 (`[TBD]`) |
| Gate First | 4 조건 + 2 문서 최소 검사 | 없음 (literal 빈 입력만 sanity check) |
| 빈 위치 보존 | row·셀 삭제 금지 | 삭제 허용 |
| 본문 검사 | 빈 골격/구조 일치 retry/중복/cross-bleed | 없음 |
| 저장 절차 | staging→write→verify→rename + collision `--01..99` | 없음 |
| 안전기능명 정규화 | 폴더명 안전화 (NFC, 특수문자 제거 등) | 없음 (출력 헤더용 raw 기능명만) |
| 출력 템플릿 | 4종 (설정없음/저장보류/저장완료/저장실패) | 2종 (변환+리뷰/보류) |
| 리뷰 축 | 2축 (SSOT 충돌 + 용어 일관성) | 2축 (자체 품질 + SSOT 충돌) |
| 리뷰 worker | B축 worker 분리 | main 단일 패스 |
| SSOT corpus 처리 | 인덱스 스캔 + version + archive 분류 | grep 매칭 후 직접 read |
| 검토 결과 | 3종 (통과/조건부/수정 필요) | 2종 (통과/발견 N건) |
| 출력 구조 | 2층 (상단 합의 + 하단 agent 원본) | 1층 |
| GFM cell escape | 단일 진실 소스 알고리즘 | 없음 (numbered list) |
| 진행 표시 | step header 시퀀스 통제 | 자유 |
| 추정 size | ~1850 line | ~500 line |

## 9. Templates

**기존 `product-team-kit`의 두 템플릿 파일을 그대로 사용한다.** 섹션 헤더, 표 구조, admonition metadata 모두 동일.

원본 경로:

- `product-team-kit/skills/plan-format/templates/기능설계서.md` — 8 섹션 (개요·범위·사용자 흐름·화면과 입력·기능 동작·권한·예외·미결).
- `product-team-kit/skills/plan-format/templates/정책서.md` — 10 섹션 (목적·적용 범위·용어·정책 원칙·세부 규칙·상태·역할·예외 승인·외부 연동·미결).

복사 위치:

- `planning-kit/skills/formalize/templates/기능설계서.md`
- `planning-kit/skills/formalize/templates/정책서.md`

템플릿 파일 자체는 손대지 않는다. **본문 채우는 규칙만 단순화**:

- 빈 셀은 비워둠 허용 (또는 inline `[TBD]`).
- 표 row·셀·섹션 헤더 삭제 허용 (product-team-kit의 "빈 위치 보존 원칙" 적용 안 함).
- `미결 사항` 섹션 색인은 채우지 않아도 된다. 본문에 inline `[TBD]`만으로 충분.
- marker는 `[TBD]` 1종만. `[미정]`/`[가정]`/`[확인 필요]`/`[충돌 후보]`/`해당 없음` 모두 사용 안 함.

## 10. 마일스톤

1. **M1 — 골격**: 폴더 구조, 두 manifest, README, 두 템플릿.
2. **M2 — `formalize` 변환부 구현**: 입력 dispatch + 빈 입력 sanity check + 두 템플릿 변환.
3. **M3 — `formalize` 리뷰부 구현**: 자체 품질 점검(충실도·cross-bleed·용어·정책-기능 매핑·누락) + SSOT grep·충돌 점검 + 카테고리별 발견 list.
4. **M4 — 통합 출력**: 두 변환 본문 + 입력 제외 항목 + 리뷰 결과 단일 응답.
5. **M5 — `--no-review` 옵션 동작 확인**.
6. **M6 — Claude Code + Codex 양쪽 동작 확인**.
7. **M7 — release v0.1.0**.

## 11. 성공 기준

- `formalize` 한 번 호출로 정책서·기능설계서 본문 + 리뷰가 화면에 함께 출력된다.
- 파일 저장 없이 응답만으로 결과를 받는다 (속도 우위).
- 신규 사용자가 README만 보고 5분 안에 첫 두 본문을 받고 리뷰 결과를 본다.
- `--no-review`로 변환 본문만 받을 수 있다.
- 자체 품질·SSOT 충돌 둘 다 0건이면 `통과`, 어느 한쪽이라도 발견이 있으면 카테고리별 발견 list를 출력한다.
- 변환 본문에 반영하지 않은 입력 조각이 있으면 사유 카테고리·인용·설명과 함께 `## 입력 제외 항목` 블록으로 출력한다 (제외 0건이면 블록 생략).

## 12. 호환성과 마이그레이션

- 기존 `product-team-kit`을 대체하지 않는다. 두 플러그인은 별도 동작한다.
- `planning-kit`은 파일을 만들지 않으므로 `<outputRoot>` 충돌 같은 이슈가 없다. 같은 프로젝트에서 두 플러그인을 자유롭게 병행 사용할 수 있다.
- 사용자가 출력 본문을 직접 파일에 저장하고 싶다면 응답에서 markdown 블록을 복사해 원하는 위치에 저장한다 (저장 위치·파일명·timestamp 모두 사람이 결정).

## 13. 용어

- **기획 초안**: 사용자가 `formalize` 스킬에 입력으로 주는 텍스트·파일·디렉터리.
- **정책서**: 규칙·조건·예외 정의 문서.
- **기능설계서**: HOW·화면·플로우 명세 문서.
- **SSOT**: Single Source of Truth. **현재 프로젝트 폴더 안 모든 `*.md` 파일**. 종류·역할 구분 없음 (정책/PRD/회의록/README 모두 동등). 노이즈 폴더(`.git/`, `node_modules/`)만 자동 제외.
- **`[TBD]`**: 결정되지 않은 항목 inline marker. 1종만 사용.

`product-team-kit`에 있던 `<outputRoot>`, `안전기능명`, collision suffix, staging folder 같은 저장 관련 용어는 본 PRD에서 사용하지 않는다 (저장 자체가 없음).

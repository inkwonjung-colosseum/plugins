# planning-kit PRD 0.2.1

> 0.2.0 기반 incremental PRD. 본 문서는 `planning-format` 출력에서 "변환 본문(정책서·기능설계서)에 담기지 않은 입력 조각"을 사용자가 한 화면에서 빠짐없이 식별할 수 있도록, **입력 제외 항목 블록**을 확장하고 자체 품질 검증 F5(누락) 기준에 cross-reference 점검을 추가한다. 본 PRD에서 다루지 않는 명세(스킬 분할·connector 라우팅·재귀 fetch·이미지 multimodal·자체 검증 F1~F4·F6 등)는 [`prd-0.2.0.md`](./prd-0.2.0.md), [`prd-0.1.2.md`](./prd-0.1.2.md), [`prd-0.1.1.md`](./prd-0.1.1.md), [`prd-0.1.0.md`](./prd-0.1.0.md)를 그대로 따른다.

## 1. 변경 요약

다섯 가지 변경:

1. **입력 제외 항목 카테고리 확장 (5종 → 10종)** — 0.2.0의 5종(`다른 기능 후보 / 라벨 미매핑 / 중복 / 근거 부족 무시 / 포맷 노이즈`)에 5종을 추가: `디테일 축약 / 범위 외 / 구조 변환 / fetch 실패 / 원문 정의 부재`. 본문 미합류·구조 변환·외부 fetch 실패·원문 모호까지 한 블록에서 추적.
2. **입력 제외 블록 상시 출력** — 0건일 때도 블록을 출력하고 `없음`으로 명시. 사용자가 "검토되었음"을 적극적으로 확인 가능. 0.2.0의 ≥1건일 때만 출력 정책을 깬다.
3. **항목 형식에 `처리` 줄 추가** — 각 입력 제외 항목에 변환 본문·출처 list·미결 §과의 cross-reference를 1줄로 명시 (`본문 미합류` / `구조 변환 (위치: 정책서 §3·§4)` / `fetch 실패 (출처 list #N 참조)` / `[TBD] 추적 (미결 §N)` 등).
4. **헤더 `입력 제외` 줄에 카테고리 분포 표기** — 단일 N건 대신 카테고리별 분포를 괄호 안에 분해해 헤더 한 줄로 사용자가 누락 양상을 파악할 수 있게 한다.
5. **자체 검증 F5(누락) 기준 강화** — 출처 list 실패·정책서/기능설계서 §2 제외 범위·미결 § [TBD] 항목이 입력 제외 블록에 대응 항목으로 추적되는지 cross-reference 점검 추가. 본문 누락은 발견을 만들고, 추적 누락도 발견을 만든다.

이 다섯 변경은 모두 `planning-format`의 자체 출력 포맷·자체 검증 reference 파일에만 영향. `planning-review` 스킬 동작·축·인자는 0.2.0 그대로.

## 2. 동기

0.2.0 운영 직후 실제 호출에서 다음 패턴이 반복 관찰됐다:

- **인접 도메인 디테일 누락**: `Zone 관리 v0.9` Confluence 페이지 변환 시 §6.2 Zone Function별 운영 디테일(RECEIVING의 과입고/부족입고 관리자 처리, Dock의 외관 검사 FAIL시 회송, BUFFER의 정온 아닌 경우 거치지 않도록 설정 등)이 정책서 §5 귀속 종류 list로만 축약. 라벨이 입고/출고/관리자 입출고·피킹 전략 도메인에 가까워 의도적으로 옮기지 않았으나, 입력 제외 §에는 항목이 없어 사용자가 "이게 빠진 게 의도인지 누락인지" 구분 불가.
- **fetch 실패 흔적 분리**: Figma board가 인증 실패로 본문 미합류. `## 출처` list에는 X로 기록되지만 `## 입력 제외 항목`에는 등장하지 않음. 사용자가 "왜 사용자 흐름 다이어그램이 없냐"를 한 블록에서 확인 못 함.
- **본 문서 제외 범위 항목**: §9.1 Platform 도메인 Zone Type 설정 시나리오는 본 문서 §2 제외 범위에 명시된 영역이라 의도적 제외. 정책서/기능설계서 §10·§8 미결로 일부 추적되나, "왜 본문에 없는지"의 근거(=명시적 제외 선언)가 입력 제외 §에는 부재.
- **표 구조 분해 추적**: 14개 Zone 관리 항목 표가 정책서 §3 용어 정의·기능설계서 §4 입력 항목으로 분산. 의미는 보존됐으나 원문 표 형태가 어디로 갔는지 사용자가 즉시 못 본다.
- **원문 자체의 모호함**: "순서" 컬럼·수정 일시 정렬 기준 미정의 같은 항목은 미결 §에서 `[TBD]`로 추적되지만, "원문 자체에 정의가 없어 변환에 못 옮겼다"는 사실은 미결 §과 입력 제외 §의 의미가 달라 사용자가 헷갈린다.

결국 사용자는 "변환 본문에 안 담긴 모든 입력 조각"을 **한 블록에서** 보고 싶다. 카테고리별 분포가 헤더에 있으면 한 호출의 누락 양상을 한눈에 파악할 수 있다. 자체 검증 F5는 본문에 누락된 항목만 잡지만, 추적까지 누락되면 검증이 "통과"로 떨어지는 사각이 있다.

## 3. 비목표

- 변환 본문에 모든 입력 조각을 우겨넣지 않는다. 라벨 매핑·인접 도메인 분리 정책은 0.2.0 그대로.
- 자동 재변환·라벨 재분기·인접 도메인 자동 라우팅을 도입하지 않는다.
- 입력 조각의 sentence-level diff·구문 해석을 도입하지 않는다. 발견 단위는 입력 텍스트의 의미 묶음(섹션·표·문단·셀).
- F1~F6 자체 검증 6 카테고리 라벨은 그대로 유지. F5만 점검 기준 추가.
- `planning-review` 스킬 출력·축·인자는 변경하지 않는다.
- 입력 제외 항목을 자동 분류하는 머신러닝·LLM 외부 호출은 두지 않는다. main이 단일 패스로 카테고리 라벨링.
- 0.2.0 `--save` 동작·collision 정책·기능명 안전화 동작은 그대로.

## 4. 입력 제외 항목 블록 확장

### 4.1 카테고리 (10종)

| # | 카테고리 | 정의 | 예시 (Zone 관리 v0.9 호출 기준) |
|---|---|---|---|
| 1 | `다른 기능 후보` | 기능명 추출 시 1순위 외 후보. 또는 입력에 함께 들어왔지만 별도 기획 대상 | 권한 시트의 PDA·기준정보·재고관리 등 비-Zone 메뉴 트리 |
| 2 | `라벨 미매핑` | 정책서 10 섹션·기능설계서 8 섹션 어디에도 라벨 매핑할 자리가 없음 | 사업 KPI·인건비·AWS 비용 시트 |
| 3 | `중복` | 같은 사실이 입력에 반복 등장. 한 번만 본문에 합류 | 입력 본문에서 감사 로그 정책이 정책서 §10·기능설계서 §10에 동일 등장 |
| 4 | `근거 부족 무시` | 추측·draft 메모·임시 작성으로 본문 신뢰도를 떨어뜨림 | "이거 좀 더 봐야 함" / TODO 코멘트 |
| 5 | `포맷 노이즈` | 인용·꾸밈·자동 metadata·임의 mark-up. 본문 의미 비기여 | Confluence `<custom data-type="smartlink">` 자동 wrap, 빈 줄, blob 이미지 placeholder |
| 6 | `디테일 축약` (신규) | 라벨 매핑은 됐으나 본문 디테일 일부가 인접 도메인에 더 가까워 옮기지 않음 | Zone Function별 RECEIVING의 과입고/부족입고 관리자 처리 흐름 |
| 7 | `범위 외` (신규) | 정책서 §2 / 기능설계서 §2 제외 범위에 명시된 영역에 해당 | Platform 도메인 Zone Type 설정 화면 시나리오 (§9.1 시나리오 1·2) |
| 8 | `구조 변환` (신규) | 의미는 보존되나 원문 표·구조가 분해돼 다른 섹션으로 분산 | 14개 Zone 관리 항목 표 → 정책서 §3 용어 정의·기능설계서 §4 입력 항목 분산 |
| 9 | `fetch 실패` (신규) | 외부 자원(URL·이미지) 본문 미합류. `## 출처` list X 행과 cross-reference | Figma board 인증 실패 (Figma MCP get_figjam 미접근) |
| 10 | `원문 정의 부재` (신규) | 입력 자체가 모호·미정의. 본문은 [TBD] 처리, 미결 §과 cross-reference | "순서" 컬럼 의미·정렬 기준 / 메뉴 클릭 후 화면 mode 진입 디테일 |

10종 모두 동등한 1차 카테고리. 한 항목이 둘 이상에 걸치면 더 본질적인 1개만 선택 (보수: `범위 외` > `fetch 실패` > `구조 변환` > `디테일 축약` > `원문 정의 부재` > `다른 기능 후보` > `라벨 미매핑` > `중복` > `근거 부족 무시` > `포맷 노이즈` 순. 위로 갈수록 우선).

#### 4.1.1 카테고리 6~10 상세 판정 휴리스틱

**`디테일 축약`**:
- 입력 조각의 라벨이 변환 본문 어떤 셀에 매핑됐는지 main이 1순위로 식별 가능.
- 매핑된 셀에 디테일 일부만 들어갔고, 빠진 디테일은 인접 도메인의 별도 정책서·기능설계서에 더 어울림.
- 빠진 디테일을 본 문서에 합류시키면 자체 검증 F2 (라벨 cross-bleed)가 발견될 가능성이 있음.

**`범위 외`**:
- 입력 조각이 정책서 §2 제외 대상 / 기능설계서 §2 제공하지 않는 것 표에 등장한 키워드 매칭.
- 또는 입력 본문 자체가 명시적으로 "후속 과제", "별도 정의", "다른 도메인" 같은 마커로 본 문서 외부임을 선언.

**`구조 변환`**:
- 입력 조각이 표·list·다이어그램 등 구조적 단위인데, 변환 본문에서 동일 구조로 등장하지 않고 분해 합류.
- 의미는 보존됐다는 main의 판단(분해 위치 1개 이상 식별 가능)이 있어야 본 카테고리. 의미가 빠지면 `디테일 축약` 또는 `라벨 미매핑`.

**`fetch 실패`**:
- `## 출처` list에 `본문 사용 = X` 행이 1개 이상 존재.
- 해당 자원이 입력의 일부분으로 인용·참조됐던 경우만 본 카테고리. fetch 실패했지만 입력에서 단순 부수 링크였으면 본 카테고리에 안 넣고 출처 list에만 둠.

**`원문 정의 부재`**:
- 변환 본문 셀이 `[TBD]`로 처리되고, 그 사유가 입력 자체가 모호·미정의했기 때문.
- 또는 미결 § 항목으로 추적되며, 미결 §의 설명이 "원문 명시 없음" 같은 표현을 포함.
- 원문에는 명시되어 있는데 main이 라벨 매핑을 못 한 경우는 `라벨 미매핑`. 두 카테고리 구분이 헷갈리면 입력 측 결손이면 본 카테고리, 변환 측 매핑 결손이면 `라벨 미매핑`.

### 4.2 항상 출력 정책

`## 입력 제외 항목` 블록은 모든 정상 호출에서 등장한다 (0.2.0의 "≥1건일 때만" 정책 깬다). 0건일 때도 블록 헤더 + `없음` 1줄로 출력.

```markdown
## 입력 제외 항목

없음
```

이유: 사용자가 "검토되었음"을 적극적으로 확인 가능. 블록 부재 = 검토 안 함 / 0건 = 검토했고 모두 본문 합류, 두 상태 구분.

`--no-self-review` 옵션은 자체 검증 § 출력만 끄고 입력 제외 §은 끄지 않는다 — 입력 제외는 변환 결과의 핵심 정보. `--save`는 입력 제외 §을 디스크에 저장하지 않는다 (0.2.0 §5.5.1 그대로 — 본문만 저장).

### 4.3 항목 형식 (확장)

각 항목은 다음 5필드:

```markdown
1. [한 줄 제목]
   - 카테고리: [§4.1 10종 중 하나]
   - 위치: [입력 측 위치 — 파일명:라인 / "직접 입력" / "[출처 N] §섹션 또는 라인 N"]
   - 인용: "[입력 원문 ≤80자]"
   - 처리: [§4.3.1 처리 줄 형식]
   - 설명: [한 줄]
```

0.2.0의 4필드(사유·위치·인용·설명)에 `처리` 1줄 추가. `사유`는 `카테고리`로 명칭만 변경 (의미 동일).

#### 4.3.1 `처리` 줄 형식

`처리` 줄은 변환 본문·출처 list·미결 §의 어디에 흔적이 남았는지(또는 안 남았는지) 1줄로 명시:

| 카테고리 | `처리` 줄 형식 |
|---|---|
| `다른 기능 후보` | `본문 미합류 (별도 기획 대상)` |
| `라벨 미매핑` | `본문 미합류` |
| `중복` | `중복 제거 (1차 합류 위치: 정책서 §N / 기능설계서 §M)` |
| `근거 부족 무시` | `본문 미합류` |
| `포맷 노이즈` | `본문 미합류` |
| `디테일 축약` | `라벨 매핑은 정책서 §N / 기능설계서 §M, 디테일 미합류` |
| `범위 외` | `명시 제외 (정책서 §2 / 기능설계서 §2 참조)` |
| `구조 변환` | `구조 분해 (위치: 정책서 §N1·§N2 / 기능설계서 §M1·§M2)` |
| `fetch 실패` | `본문 미합류 (출처 list #K 참조)` |
| `원문 정의 부재` | `[TBD] 추적 (미결: 정책서 §10 #N / 기능설계서 §8 #M)` |

`처리` 줄은 main이 변환·합류·추적 단계에서 가지고 있는 정보로 자동 채운다. 매핑·합류 위치를 식별 못 하면 `본문 미합류`로 폴백.

### 4.4 헤더 `입력 제외` 줄 카테고리 분포 표기

0.2.0:

```
- 입력 제외: N건
```

0.2.1:

```
- 입력 제외: N건 (다른 후보 K, 라벨 미매핑 L, 중복 M, 근거 부족 P, 포맷 노이즈 Q, 디테일 축약 R, 범위 외 S, 구조 변환 T, fetch 실패 U, 원문 정의 부재 V)
```

규칙:
- 카테고리 카운트가 0인 항목은 괄호에서 누락 (가독성).
- 0건일 때 `- 입력 제외: 없음`으로만.
- 카테고리 라벨은 §4.1 표의 한국어 약형 그대로 (`다른 기능 후보` → `다른 후보`, `근거 부족 무시` → `근거 부족`).
- 합계가 N과 일치해야 한다 (검증 자체는 main 책임, 출력에 합계 다시 표시 안 함).

### 4.5 변환 본문·미결 §과의 일관성 규칙

- 정책서 §10 / 기능설계서 §8 미결 항목 중 "원문 정의 부재" 사유 항목은 입력 제외 §에 같은 항목이 `원문 정의 부재` 카테고리로 1대1 등장해야 한다 (자체 검증 F5에서 강제, §5).
- 정책서 §2 / 기능설계서 §2 제외 범위에 명시된 키워드와 입력 본문에 등장하는 키워드가 매칭되면, 입력 제외 §에 `범위 외` 항목으로 적어도 1건 이상 나와야 한다.
- `## 출처` list에서 `본문 사용 = X` 행 중 입력에서 단순 부수 링크가 아닌 항목은 입력 제외 §에 `fetch 실패` 카테고리로 등장해야 한다.

이 세 규칙은 §5 자체 검증 F5에서 자동 점검된다.

## 5. 자체 검증 F5(누락) 기준 강화

### 5.1 0.2.0 F5 기존 점검

> 입력의 명시 사실(역할·상태·기능명·수치 임계)이 두 본문·입력 제외 추적에 모두 부재 → 발견.

본 점검은 그대로 유지.

### 5.2 0.2.1 F5 추가 점검 (3종 cross-reference)

다음 3종 점검을 단일 패스에 추가:

1. **fetch 실패 cross-reference**: `## 출처` list에 `본문 사용 = X` 행이 ≥1건이고 입력에서 단순 부수 링크가 아닌 자원(=인용·참조 문장에 언급)인 경우, 입력 제외 §에 같은 자원에 대한 `fetch 실패` 카테고리 항목이 없으면 발견.
2. **명시 제외 cross-reference**: 정책서 §2 / 기능설계서 §2 제외 범위에 명시된 키워드가 입력 본문에 매칭되는데 입력 제외 §에 `범위 외` 카테고리 항목이 없으면 발견. 매칭 키워드는 main이 정책서·기능설계서 §2 표 cell에서 추출 + 입력 본문에서 grep.
3. **[TBD] cross-reference**: 정책서 §10 / 기능설계서 §8 미결 항목 중 "원문 명시 없음", "원문 정의 부재", "입력 미정", "원본 본문에 없음" 같은 표현이 들어 있는데 입력 제외 §에 `원문 정의 부재` 카테고리 항목이 없으면 발견.

각 cross-reference 발견은 F5 카테고리 안에 sub-label `cross-ref-fetch` / `cross-ref-scope` / `cross-ref-tbd`로 표시.

### 5.3 발견 사항 형식

0.2.0 §5.3.2 그대로. `위치` 줄에 cross-reference인 경우 양쪽 위치를 모두 명시:

```markdown
1. fetch 실패 항목이 입력 제외 §에 추적 안 됨
   - 카테고리: 누락 (sub: cross-ref-fetch)
   - 위치: 출처 list #3 (Figma board) ↔ 입력 제외 § (해당 카테고리 항목 부재)
   - 근거: "출처 list 행에 인증 실패. 입력 §2 사용자 흐름에서 다이어그램으로 인용됨"
   - 영향: 사용자가 다이어그램 누락을 입력 제외 §에서 확인 못 함
   - 제안: 입력 제외 §에 `fetch 실패` 카테고리 항목 추가 (출처 list #3 cross-reference)
```

## 10. 검증 시나리오

PRD 검수 시점 main이 트레이스 (실 호출은 사용자 환경 검증):

1. **모든 입력 본문 합류**: 깨끗한 입력. 헤더 `- 입력 제외: 없음`. `## 입력 제외 항목` 블록 = `없음` 1줄.
2. **사업 KPI + 기능 페이지 동시 입력**: 헤더 `- 입력 제외: N건 (다른 후보 K, 라벨 미매핑 L)`. 항목 list에 두 카테고리 섞여 등장. 모든 항목에 `처리: 본문 미합류` 줄.
3. **Confluence 페이지 + Figma board fetch 실패**: `## 출처` list에 Figma board 행 X. `## 입력 제외 항목`에 `fetch 실패` 카테고리 항목 1건 + `처리: 본문 미합류 (출처 list #N 참조)`. 자체 검증 F5 cross-ref-fetch 통과.
4. **자체 검증 F5 cross-ref-fetch 발견**: Figma board fetch 실패 + 입력 제외 §에 해당 항목 부재. 자체 검증 §발견 사항에 F5 sub-label `cross-ref-fetch` 1건. 제안 = 입력 제외 § 항목 추가.
5. **본 문서 제외 범위 항목**: Platform 도메인 시나리오가 입력에 명시. 정책서 §2 제외 범위에 등장. 입력 제외 §에 `범위 외` 카테고리 항목 + `처리: 명시 제외 (정책서 §2 / 기능설계서 §2 참조)`.
6. **자체 검증 F5 cross-ref-scope 발견**: 정책서 §2에 "Floor Plan 편집은 후속 과제"가 명시되어 있고 입력 본문에 "Floor Plan"이 등장하는데 입력 제외 §에 `범위 외` 항목 부재. F5 sub-label `cross-ref-scope` 1건.
7. **14개 항목 표 분해**: 정책서 §3 용어 정의·기능설계서 §4 입력 항목으로 분산. 입력 제외 §에 `구조 변환` 카테고리 항목 + `처리: 구조 분해 (위치: 정책서 §3 / 기능설계서 §4)`.
8. **Zone Function별 디테일 축약**: RECEIVING 과입고/부족입고 흐름이 정책서 §5 귀속 종류 list로만 축약. 입력 제외 §에 `디테일 축약` 카테고리 항목 + `처리: 라벨 매핑은 정책서 §5, 디테일 미합류`.
9. **원문 "순서" 컬럼 미정의**: 미결 §에 [TBD] + "원문 명시 없음"으로 추적. 입력 제외 §에 `원문 정의 부재` 카테고리 항목 + `처리: [TBD] 추적 (미결: 기능설계서 §8 #N)`.
10. **자체 검증 F5 cross-ref-tbd 발견**: 미결 §에 "원본 본문에 없음" 표현이 있는데 입력 제외 §에 `원문 정의 부재` 항목 부재. F5 sub-label `cross-ref-tbd` 1건.
11. **`--no-self-review`**: 입력 제외 § 정상 출력 (블록 끄지 않음). 자체 검증 § 블록만 통째 생략.
12. **`--save` + 입력 제외 ≥1건**: 입력 제외 §·자체 검증 §은 화면만. `./.planning-kit/<기능명>/정책서.md`·`기능설계서.md`만 디스크. (0.2.0 정책 그대로.)
13. **카테고리 우선순위 충돌**: 입력 조각이 `범위 외` + `디테일 축약` 둘 다 해당. 우선순위 규칙(§4.1)에 따라 `범위 외` 1개로 라벨링.
14. **fetch 실패가 단순 부수 링크**: 입력에 인용·참조 없는 외부 링크가 fetch 실패. 출처 list만 X로 기록, 입력 제외 §에는 등장하지 않음. F5 cross-ref-fetch 발견 안 함 (단순 부수 링크 판단).
15. **헤더 분포 0건 카테고리 누락**: 카테고리 4종에 항목이 있고 6종은 0건. 헤더 괄호에 4종 분포만 표기, 6종은 누락 (가독성).

## 11. 성공 기준

- 모든 정상 `planning-format` 호출에서 `## 입력 제외 항목` 블록이 등장한다 (0건일 때 `없음`).

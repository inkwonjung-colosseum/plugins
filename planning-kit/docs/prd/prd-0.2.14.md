# planning-kit PRD 0.2.14

> 0.2.13 기반 incremental PRD. 0.2.12는 `planning-format`에 `생성 결과 요약`과 조건부 `결정 보드`를, `planning-review`에 항상 출력되는 `결정 보드`를 도입해 첫 화면 인지성을 개선했다. 그러나 실제 기획자가 혼자 문서를 정리하고 판단·보강까지 진행하는 흐름에서는 결정/작업 projection이 문서 본문과 검토 결과보다 앞서 보여, 두 스킬 모두 회의용 우선순위판처럼 보이는 문제가 남았다.
>
> 핵심 변경: `planning-format`과 `planning-review`의 public 화면 출력은 **결과/검토 결과 우선 + 하단 체크리스트** 구조로 바꾼다. `planning-format`은 기본적으로 로컬 `planning/[안전기능명]--YYYY-MM-DD-HHMMSS/`에 정책서·기능설계서를 저장하고, 화면에는 저장 파일 링크와 `체크해야 할 항목`만 보여준다. 정책서·기능설계서 전문을 화면에 펼치는 것은 파일 저장하지 않는 `--no-save` 실행에서만 한다. `planning-review`는 헤더 요약 뒤 바로 `결론`, `검토 결과`를 보여준다. 미확정·누락·보강점은 마지막 `체크해야 할 항목`에 모은다. `planning-publish-confluence`는 기본 저장 결과를 발행할 수 있도록 명시적 저장 폴더 입력을 지원하되, canonical 정책서·기능설계서 두 파일만 읽고 최종 쓰기 확인은 유지한다. `## 결정 보드` heading은 신규 public 출력에서 쓰지 않고, legacy 0.2.10~0.2.13 화면 출력 읽기 호환으로만 유지한다.

| 항목 | 값 |

| PRD 상태 | 목표 계약. 실제 릴리즈 완료 전까지 runtime 현재 계약으로 간주하지 않는다. |
| 베이스 | 0.2.13 |

## 2. 변경 계약 요약

1. **결과/검토 결과 우선** — `planning-format` 기본 저장 출력은 `헤더 요약 -> 저장 파일 -> 체크해야 할 항목` 순서를, `planning-format --no-save` 출력은 `헤더 요약 -> 정책서 -> 기능설계서 -> 체크해야 할 항목` 순서를, `planning-review` 최종 출력은 `헤더 요약 -> 결론 -> 검토 결과 -> 체크해야 할 항목` 순서를 기본으로 한다.
2. **로컬 저장 기본값 전환** — `planning-format`은 옵션이 없으면 기본적으로 `planning/[안전기능명]--YYYY-MM-DD-HHMMSS/`에 정책서 1개와 기능설계서 1개를 저장한다. 파일 저장하지 않는 화면 only 실행은 `--no-save`로 명시한다.
3. **Confluence 발행 입력 확장** — `planning-publish-confluence`는 무인자 context-body 발행을 유지하고, 명시적 저장 폴더 입력이 있으면 해당 폴더의 canonical 정책서·기능설계서 두 파일만 읽어 발행 후보로 사용한다.
4. **상단 결정 보드 제거** — 두 스킬의 신규 public 출력에서는 `## 결정 보드`를 출력하지 않는다. 결정/작업/차단 항목은 하단 `## 체크해야 할 항목`에 통합한다.
5. **상단 요약 축소** — `planning-format`의 `## 생성 결과 요약`과 `planning-review`의 `## 결정 보드`는 신규 출력에서 별도 H2로 쓰지 않는다. 입력·산출물·검증·저장 상태는 `# [기능명]` 또는 `# [기능명] 검토 결과` 바로 아래 헤더 bullet에 압축한다.
6. **체크리스트 후행** — 사용자가 정책서와 기능설계서 정리본 또는 review 결론과 결과를 읽은 뒤, 마지막에 결정 필요·문서 보강 필요·출처/누락 참고를 확인하게 한다.
7. **기존 정보 보존** — 기존 `결정 보드`, `검증 피드백`, `출처 요약`, `입력 제외 요약`의 핵심 정보는 사라지지 않는다. `체크해야 할 항목`, `출처/누락 요약`, 조건부 `상세 추적`으로 재배치한다.
8. **trace는 선택 확인 영역** — full source table, connector status, 입력 제외 전체 목록, 원시 F* 피드백은 하단 `상세 추적`에만 둔다. 일반 검토자가 매번 필수로 읽는 영역이 아니어야 한다.
9. **legacy 결정 보드는 읽기 호환 전용** — 0.2.10~0.2.13 출력의 `## 결정 보드`는 parser가 계속 읽되, 0.2.14 신규 public 출력의 작성 목표가 아니다.

## 3. 문제와 범위

### 문제

- `planning-format`의 본질은 원문을 정책서·기능설계서로 정리하는 것이다. 그런데 상단 `결정 보드`가 먼저 나오면 사용자가 산출물보다 회의 아젠다를 먼저 보게 된다.
- 기획자가 혼자 후속 보강까지 진행하는 사용 흐름에서는 산출물이 기본적으로 로컬 파일로 남아야 한다. 기존 opt-in `--save` 방식은 중요한 정책서·기능설계서 결과를 화면 응답에만 남길 수 있다.
- 저장이 기본이면 같은 응답에 정책서·기능설계서 전문을 다시 출력하는 것은 중복이다. 저장 성공 화면은 파일 위치와 후속 체크 항목만 보여주는 편이 더 읽기 쉽다.
- 0.2.13 `planning-publish-confluence`는 현재 context memory에 정책서·기능설계서 전문이 있을 때만 동작한다. 0.2.14 기본 저장 출력은 전문을 화면에 출력하지 않으므로, 저장 폴더 입력 계약이 없으면 기본 작성 흐름에서 Confluence 발행으로 이어지지 않는다.
- `생성 결과 요약`, `결정 보드`, `검증 피드백`, `출처 요약`, `입력 제외 요약`이 모두 분리되면 같은 미확정/누락 항목을 여러 번 읽게 된다.
- 결정 필요 항목이 상단에 너무 자세히 펼쳐지면 정책서·기능설계서 본문이 뒤로 밀린다.
- 반대로 출처·누락 상세를 완전히 제거하면 환각 위험과 검증 가능성이 떨어진다.
- `planning-review`도 기획자가 혼자 판단·보강하는 흐름에서는 `결정 보드`보다 결론, 발견, 반영 위치, 근거 한계가 먼저 보여야 한다.

### 비목표

- legacy `planning-format` 화면 출력의 `## 생성 결과 요약`, `## 결정 보드`를 parser에서 읽지 못하게 만들지 않는다.
- D*/A*/T*/F* ID 모델을 폐기하지 않는다. 신규 public 출력에서는 노출을 줄이되, `상세 추적`과 parser용 structured mapping에서는 보존할 수 있다.
- `planning-format` 저장 파일의 내용 계약을 바꾸지 않는다. 저장 파일은 계속 정책서 1개 + 기능설계서 1개 canonical Markdown이다. 단, 저장 실행 방식은 opt-in `--save`에서 default-on + opt-out `--no-save`로 바꾼다.
- R1/R2/R3 review 축이나 SSOT/AC/의존 영향 분석 규칙을 변경하지 않는다.
- `planning-publish-confluence`가 저장 결과를 자동으로 찾아 즉시 발행하게 만들지 않는다. context 본문 또는 명시적 저장 폴더 입력이 있어야 하며, 최종 쓰기 확인은 계속 필수다.
- `planning-publish-confluence`에서 URL fetch, Confluence 원문 재조회, 임의 `.md` 파일 묶음 추론을 새로 도입하지 않는다.

## 4. 신규 `planning-format` 출력 순서

### 4.1 기본 저장 출력

```markdown
# [기능명]

- 입력: [사람이 읽는 요약]
- 산출물: 정책서, 기능설계서
- 검증: 확인 필요 N건, 문서 보강 M건 / 확인 필요 없음
- 저장: planning/[안전기능명]--YYYY-MM-DD-HHMMSS/

---

## 저장 파일

- 정책서: planning/[안전기능명]--YYYY-MM-DD-HHMMSS/[안전기능명]_정책서.md
- 기능설계서: planning/[안전기능명]--YYYY-MM-DD-HHMMSS/[안전기능명]_기능설계서.md

---

## 체크해야 할 항목

[결정 필요 / 문서 보강 필요 / 출처·누락 참고]

---

## 출처/누락 요약

[짧은 출처 상태와 제외 요약]

---

## 상세 추적

[조건 충족 시에만 full trace]
```

### 4.2 `--no-save` 화면 only 출력

```markdown
# [기능명]

- 입력: [사람이 읽는 요약]
- 산출물: 정책서, 기능설계서
- 검증: 확인 필요 N건, 문서 보강 M건 / 확인 필요 없음
- 저장: 없음 (--no-save)

---

## 정책서

[정책서 정리본 전체]

---

## 기능설계서

[기능설계서 정리본 전체]

---

## 체크해야 할 항목

[결정 필요 / 문서 보강 필요 / 출처·누락 참고]
```

규칙:

- 기본 저장 출력에서는 `## 저장 파일`이 첫 H2가 된다.
- 기본 저장 출력에는 `## 정책서`, `## 기능설계서` 본문 섹션을 출력하지 않는다. 전문은 저장 파일을 기준으로 확인한다.
- `--no-save` 출력에서만 `## 정책서`가 첫 H2가 되고 `## 기능설계서` 본문을 이어서 출력한다.
- `## 생성 결과 요약`은 신규 출력에서 쓰지 않는다.
- `## 결정 보드`는 신규 `planning-format` 출력에서 쓰지 않는다.
- 옵션이 없으면 저장을 실행한다. `--no-save`가 있을 때만 저장하지 않고 화면 출력만 제공한다.
- 기존 `--save` 옵션은 0.2.x 호환용 no-op alias로 허용한다. `--save`가 있어도 기본 저장 동작과 동일하다.
- `확인 필요 없음`이면 `## 체크해야 할 항목`은 유지하되 각 subsection을 `없음`으로 표시한다. 단, 출력을 더 짧게 해야 하는 low-risk 입력에서는 `체크해야 할 항목: 없음` 한 줄로 축약할 수 있다.
- `## 출처/누락 요약`은 fetch 실패, 원문 정의 부재, 입력 제외 high-signal 항목이 있을 때 출력한다. 없으면 생략 가능하다.
- `## 상세 추적`은 full 출처표, full 입력 제외 목록, parser warning, connector 실패, 연결 맵이 필요한 경우에만 출력한다.

## 5. 헤더 요약

헤더 bullet은 4줄을 기본으로 한다.

| 라벨 | 규칙 |
|---|---|
| `입력` | 파일/URL/디렉터리/이미지 수와 추가 출처 수를 사람용으로 요약한다. |
| `산출물` | 항상 `정책서, 기능설계서`를 쓴다. |
| `검증` | `확인 필요 N건`, `문서 보강 M건`, `출처 누락 K건`, `확인 필요 없음` 중 필요한 것만 압축한다. |
| `저장` | 기본은 저장 경로를 쓴다. `--no-save` 사용 시에만 `없음 (--no-save)`를 쓴다. |

금지:

- 헤더에 connector 이름과 status code를 나열하지 않는다.
- 헤더에 D*/A*/F* 원시 ID를 직접 나열하지 않는다.
- 헤더를 `생성 결과 요약`과 중복하지 않는다.

## 6. `체크해야 할 항목` 계약

### 6.1 목적

`체크해야 할 항목`은 저장 파일 또는 `--no-save` 화면 본문에서 정책서·기능설계서를 확인한 뒤 처리할 후속 checklist다.

이 섹션은 다음 질문에 답해야 한다.

1. 어떤 결정이 아직 필요한가?
2. 어떤 문서 보강이 필요한가?
3. 어떤 출처 실패·누락·원문 정의 부재가 결과 신뢰도에 영향을 주는가?
4. 각 항목은 정책서/기능설계서 어디에 반영되는가?

### 6.2 섹션 구조

```markdown
## 체크해야 할 항목

### 결정 필요

1. [항목명]
   - 확인할 것: ...
   - 이유: ...
   - 반영 위치: ...

### 문서 보강 필요

1. [항목명]
   - 이유: ...
   - 반영 위치: ...

### 출처/누락 참고

- [출처 실패 또는 원문 정의 부재 요약]
```

규칙:

- `결정 필요`, `문서 보강 필요`, `출처/누락 참고` 3개 subsection을 기본으로 한다.
- 항목이 없는 subsection은 `없음`으로 쓴다.
- `결정 필요자`는 출력하지 않는다. 이 도구의 기본 독자는 기획이며, 특정 외부 승인 주체가 원문에 명시된 경우에만 `승인/확인 주체`를 예외적으로 추가한다.
- `확인할 것`은 사용자가 답해야 하는 판단을 한 문장으로 쓴다.
- `이유`는 원문 `TBD`, `확정 시 재정의`, fetch 실패, 충돌 후보, 용어 혼재 등 핵심 근거를 한 줄로 쓴다.
- `반영 위치`는 clean display를 사용한다. 예: `정책서 세부 규칙`, `기능설계서 예외와 메시지`.
- full 검증문, Given/When/Then, full source URL, connector status code 전문은 쓰지 않는다.

### 6.3 항목 분류

| 기존 신호 | 신규 위치 |
|---|---|
| D* 결정 항목 | `체크해야 할 항목 > 결정 필요` |
| A* 문서 작업 | `체크해야 할 항목 > 문서 보강 필요` |
| T* 출시 전 해결 | 관련 `결정 필요` 또는 `문서 보강 필요` 항목의 `이유`에 차단 사유로 포함 |
| F* 사용자 확인 필요 | 관련 checklist 항목으로 흡수, 원본은 `상세 추적`에 보존 가능 |
| fetch 실패 | 핵심 흐름에 영향 있으면 `문서 보강 필요`, 그 외 `출처/누락 참고` |
| 원문 정의 부재 | 정책/기능 판단을 막으면 `결정 필요`, 그 외 `출처/누락 참고` |
| 포맷 노이즈·self-anchor 중복 | 기본 checklist 제외, 필요 시 `상세 추적` |

## 7. Zone 관리 예시

```markdown
# Zone 관리

- 입력: URL 1개, 추가 출처 3개
- 산출물: 정책서, 기능설계서
- 검증: 확인 필요 3건, 문서 보강 2건, 출처 누락 1건
- 저장: planning/Zone-관리--YYYY-MM-DD-HHMMSS/

---
```

## 8. 신규 `planning-review` 출력 순서

기본 출력:

```markdown
# [기능명] 검토 결과

- 대상: 정책서, 기능설계서
- 기준: SSOT / AC / 의존 영향
- 판정: 수정 필요 N건, 문서 보강 M건, 확인 필요 K건 / 통과
- 추적: 상세 추적 있음 / 없음

---

## 결론

[검토 판정과 핵심 이유]

---

## 검토 결과

### 필수 수정

[SSOT 충돌, AC 불충분, 의존 영향 중 출시·구현 판단을 막는 항목]

### 문서 보강 필요

[본문 보강, 예외·QA·권한·상태 기준 보강 항목]

### 확인 필요

[기획자가 단독으로 확정해야 하는 선택지, 원문 정의 부재, 근거 부족]

---

## 체크해야 할 항목

[지금 반영할 것 / 기획자가 확인할 것 / 출처·근거 한계]

---

## 검토 근거 요약

[읽은 대상과 기준 문서, 신뢰도에 영향을 준 근거 한계]

---

## 상세 추적

[조건 충족 시에만 R1/R2/R3 raw finding, legacy ID mapping, source trace]
```

규칙:

- `planning-review` 신규 public 출력에서는 `## 결정 보드`를 쓰지 않는다.
- `## 결론`이 첫 H2가 된다.
- `## 검토 결과`는 사용자가 바로 고칠 수 있는 발견 목록이다. 축 이름(R1/R2/R3)은 사용자-facing 제목이 아니라 하단 상세 추적의 근거로만 둔다.
- `## 체크해야 할 항목`은 review 결과를 읽은 뒤 실제 후속 행동을 정리하는 checklist다. `지금 반영할 것`, `기획자가 확인할 것`, `출처/근거 한계` 3개 subsection을 기본으로 한다.
- legacy `## 최우선 수정 항목`, `## 작업 백로그`는 0.2.x consumer 호환용으로 읽을 수 있지만, 신규 출력에서는 반복하지 않는다.
- R1/R2/R3 raw finding, D*/A*/T* mapping, source id, parser warning은 필요 시 `## 상세 추적`에 둔다.

## 9. 출처/누락 요약과 상세 추적

### 9.1 출처/누락 요약

`출처/누락 요약`은 기존 `출처 요약`과 `입력 제외 요약`을 사용자-facing으로 합친 압축 섹션이다.

포함:

- 출처 종류별 성공/실패 수
- 본문 미사용 출처
- 결과 영향이 있는 입력 제외 항목
- 원문 정의 부재 항목
- fetch 실패가 기능설계서/정책서에 주는 영향

제외:

- full URL table
- self-anchor 중복 처리 상세
- 포맷 노이즈 전체 목록
- connector fallback 내부 경로

### 9.2 상세 추적

`상세 추적`은 감사·디버깅용이다. 다음 중 하나라도 있으면 출력한다.

- fetch 실패 1건 이상
- 원문 정의 부재가 checklist 항목으로 승격됨
- 입력 제외 high-signal 항목 1건 이상
- parser boundary warning
- D*/A*/F* legacy ID mapping 보존 필요

`상세 추적`에는 다음을 둘 수 있다.

- full 출처표
- full 입력 제외 5필드 목록
- legacy `D*/A*/T*/F*` 연결 맵
- fetch/connector 상태
- parser boundary warning

## 10. `planning-publish-confluence` 입력 계약

### 10.1 목적

0.2.14에서 `planning-format`은 기본적으로 로컬 파일을 저장하고 화면에는 저장 파일 링크와 체크리스트만 출력한다.

따라서 `planning-publish-confluence`는 다음 두 흐름을 모두 지원해야 한다.

1. `planning-format --no-save`처럼 현재 대화 context에 정책서·기능설계서 전문이 있는 경우
2. 기본 저장 실행처럼 로컬 저장 폴더에만 정책서·기능설계서 전문이 있는 경우

### 10.2 지원 입력

| 입력 형태 | 지원 여부 | 처리 |
|---|---:|---|
| 인자 없음 | O | 현재 context memory에서 정책서 1개와 기능설계서 1개 전문을 찾는다. 0.2.13 동작과 동일하다. |
| 저장 폴더 경로 | O | `planning/[안전기능명]--YYYY-MM-DD-HHMMSS/` 또는 설정된 output root 하위의 저장 폴더에서 canonical 두 파일만 읽는다. |
| `## 저장 파일` 화면 링크만 있는 context | 조건부 | 자동 추적하지 않는다. 사용자가 해당 저장 폴더 발행을 명시하거나, skill이 하나의 후보 경로를 확인 질문으로 확정받은 뒤에만 읽는다. |
| URL / Confluence page URL | X | publish skill이 새 원문 fetch나 변환을 수행하지 않는다. |
| 임의 단일 `.md` 파일 | X | 정책서·기능설계서 쌍을 추론하지 않는다. 저장 폴더 단위만 지원한다. |
| 여러 저장 폴더 | X | 발행 대상이 모호하므로 거부하고 하나의 폴더를 다시 요구한다. |

### 10.3 저장 폴더 검증

저장 폴더 입력은 다음 조건을 모두 만족해야 한다.

- 폴더가 존재하고 읽기 가능해야 한다.
- 폴더 바로 아래에 정책서 파일 1개와 기능설계서 파일 1개가 있어야 한다.
- 정책서 파일명은 `*_정책서.md`, 기능설계서 파일명은 `*_기능설계서.md` 형식을 따른다.
- 하위 폴더 재귀 탐색, sibling 폴더 glob, 최근 폴더 자동 선택은 하지 않는다.
- `체크해야 할 항목`, `출처/누락 요약`, `상세 추적` 파일이나 화면 섹션은 Confluence child page 본문으로 발행하지 않는다.
- 정책서·기능설계서 H1 또는 파일명 기반 기능명이 서로 충돌하면 발행 전 거부한다.

검증 실패 시에는 Confluence parent 조회나 쓰기 확인으로 넘어가지 않고, 어느 조건이 실패했는지만 짧게 보고한다.

### 10.4 발행 전 확인

저장 폴더 입력을 지원하더라도 0.2.13의 안전장치는 유지한다.

- 기본 Product Docs SSOT parent 제안 또는 parent URL 직접 입력 지원
- 기능 container와 child page title preflight
- 중복 title 또는 기존 page update 여부 확인
- 최종 쓰기 전 사용자 확인
- write 후 readback 검증
- blind overwrite, 자동 merge, 자동 rollback 금지

### 10.5 본문 제외 boundary

`planning-publish-confluence`는 다음 heading을 Confluence child page 본문으로 발행하지 않는다.

- `## 저장 파일`
- `## 체크해야 할 항목`
- `## 출처/누락 요약`
- `## 검토 결과`
- `## 검토 근거 요약`
- `## 상세 추적`
- legacy `## 생성 결과 요약`
- legacy `## 결정 보드`
- legacy `## 검증 피드백`
- legacy `## 출처 요약`
- legacy `## 입력 제외 요약`

## 11. Parser와 호환성

- 0.2.14 신규 `planning-format` 기본 저장 출력에서는 첫 H2가 `## 저장 파일`이다.
- 0.2.14 신규 `planning-format --no-save` 출력에서는 첫 H2가 `## 정책서`다.
- 0.2.14 신규 `planning-review` 출력에서는 첫 H2가 `## 결론`이다.
- parser는 `## 저장 파일`, `## 체크해야 할 항목`, `## 출처/누락 요약`, `## 검토 결과`, `## 검토 근거 요약`, `## 상세 추적`을 정책서·기능설계서 본문 종료 boundary 또는 review report boundary로 인식해야 한다.
- `## 저장 파일`은 report metadata다. 정책서·기능설계서 본문으로 병합하지 않는다.
- legacy 0.2.10~0.2.13 `planning-format` 출력의 `## 생성 결과 요약`과 `## 결정 보드`는 계속 metadata로 읽기 호환한다.
- legacy 0.2.10~0.2.13 `planning-review` 출력의 `## 결정 보드`, `## 최우선 수정 항목`, `## 작업 백로그`는 계속 report metadata로 읽기 호환한다.
- 0.2.14 신규 public 출력에서 `## 결정 보드` 부재를 실패로 보지 않는다.
- 0.2.14 신규 `planning-format` 호출은 저장 기본값을 따른다. legacy caller가 `--save`를 붙여도 같은 저장 동작으로 처리하고, 저장하지 않으려면 `--no-save`를 사용한다.
- `planning-publish-confluence`는 `## 저장 파일`, `## 체크해야 할 항목`, `## 출처/누락 요약`, `## 검토 결과`, `## 검토 근거 요약`, `## 상세 추적`을 발행 본문에서 제외해야 한다.
- downstream parser는 `결정 필요자`, `담당/결정 필요자`, `첫 화면 요약` 필드 부재를 실패로 보지 않아야 한다.
- 저장 파일에는 기존처럼 `체크해야 할 항목`, `출처/누락 요약`, `상세 추적`을 쓰지 않는다.

## 12. 검증 계획

1. **`planning-format` Zone 관리 출력 순서 fixture**
   - 입력: Refurbish TBD, DEFECT/RETURN 팝업 TBD, Figma fetch 실패, 역할명 혼재, DEFECT -> OUTBOUND 예외 누락.
   - 기대: 옵션 없는 기본 실행에서는 `## 저장 파일`이 첫 H2다.
   - 기대: 옵션 없는 기본 실행 화면에는 `## 정책서`, `## 기능설계서` 전문 섹션이 없다.
   - 기대: `## 저장 파일` 뒤에 `## 체크해야 할 항목`이 나온다.
   - 기대: `## 결정 보드`와 `## 생성 결과 요약`은 신규 출력에 없다.
   - 기대: 옵션이 없으면 저장 경로가 `planning/Zone-관리--YYYY-MM-DD-HHMMSS/` 형식으로 표시된다.

2. **체크리스트 내용 fixture**
   - 기대: `결정 필요`에 Refurbish 재고 속성, DEFECT/RETURN 팝업 UX, 역할명 표기 통일이 있다.
   - 기대: `문서 보강 필요`에 Figma 사용자 흐름 보강, DEFECT -> OUTBOUND 예외 명시가 있다.
   - 기대: `결정 필요자` 필드는 없다.

3. **출처/누락 요약 fixture**
   - 입력: 출처 4건, fetch 실패 1건, 입력 제외 16건.
   - 기대: `출처/누락 요약`에는 count와 결과 영향 항목만 있다.
   - 기대: full URL table과 full 입력 제외 목록은 `상세 추적`에만 있다.

4. **`planning-review` 결과 우선 fixture**
   - 입력: SSOT 충돌 1건, AC 보강 1건, 의존 영향 확인 1건.
   - 기대: `## 결론`이 첫 H2다.
   - 기대: `## 검토 결과` 뒤에 `## 체크해야 할 항목`이 나온다.
   - 기대: `## 결정 보드`, `## 최우선 수정 항목`, `## 작업 백로그`는 신규 출력에 없다.

5. **Parser boundary fixture**
   - 기대: `## 체크해야 할 항목` 이후 내용은 기능설계서 body에 합류하지 않는다.
   - 기대: legacy `planning-format`/`planning-review`의 `## 결정 보드` output도 여전히 metadata로 읽힌다.
   - 기대: 신규 `planning-review`의 `## 검토 근거 요약`과 `## 상세 추적`은 발견 본문에 합류하지 않는다.

6. **Default save canonical fixture**
   - 옵션 없는 기본 실행 결과 파일에는 정책서/기능설계서 본문만 있다.
   - 옵션 없는 기본 실행 화면 출력에는 정책서/기능설계서 전문이 없다.
   - `체크해야 할 항목`, `출처/누락 요약`, `상세 추적`은 저장 파일에 없다.
   - legacy `--save` 입력도 옵션 없는 기본 실행과 같은 결과를 만든다.

7. **No-save fixture**
   - `--no-save` 실행은 로컬 파일을 만들지 않는다.
   - 헤더 `저장` 줄은 `없음 (--no-save)`로 표시한다.
   - 화면 출력 구조는 `정책서 -> 기능설계서 -> 체크해야 할 항목` 순서를 유지한다.
   - `## 정책서`가 첫 H2다.

8. **`planning-publish-confluence` 저장 폴더 fixture**
   - 입력: `planning/Zone-관리--YYYY-MM-DD-HHMMSS/` 저장 폴더 1개.
   - 기대: 폴더 바로 아래 `*_정책서.md`, `*_기능설계서.md` 두 파일만 읽는다.
   - 기대: 화면 출력의 `## 저장 파일`, `## 체크해야 할 항목`, `## 출처/누락 요약`, `## 상세 추적`은 child page 본문으로 발행하지 않는다.
   - 기대: 정책서·기능설계서 파일이 0개 또는 2개 이상이면 Confluence parent 조회 전에 실패한다.
   - 기대: URL, 임의 단일 `.md`, 여러 저장 폴더 입력은 실패한다.
   - 기대: 최종 쓰기 확인과 write 후 readback 검증은 0.2.13과 동일하게 유지한다.

9. **`planning-publish-confluence` context-body fixture**
   - 입력: 현재 context memory에 정책서 1개와 기능설계서 1개 전문이 있는 `planning-format --no-save` 결과.
   - 기대: 인자 없이도 0.2.13과 동일하게 발행 후보를 구성한다.
   - 기대: `## 체크해야 할 항목` 이후 내용은 child page body에 합류하지 않는다.

## 13. 롤아웃 계획

1. `planning-format` output contract에서 기본 저장 public order를 `저장 파일 -> 체크해야 할 항목`으로 변경한다. 저장 성공 화면에는 정책서/기능설계서 전문을 출력하지 않는다.
2. `planning-format --no-save` output contract는 `정책서 -> 기능설계서 -> 체크해야 할 항목`으로 유지한다.
3. `planning-format` 저장 계약을 default-on으로 변경한다. 옵션 없는 호출은 저장하고, `--no-save`만 화면 only로 처리하며, legacy `--save`는 no-op alias로 허용한다.
4. `planning-review` output contract에서 public order를 `결론 -> 검토 결과 -> 체크해야 할 항목`으로 변경하고, 신규 출력에서 `## 결정 보드`, `## 최우선 수정 항목`, `## 작업 백로그` 반복 출력을 제거한다.
5. `planning-publish-confluence` context gate를 확장해 명시적 저장 폴더 입력을 지원하고, canonical 정책서·기능설계서 두 파일 검증을 추가한다.
6. `planning-review`와 `planning-publish-confluence` parser boundary에 `## 저장 파일`, `## 체크해야 할 항목`, `## 출처/누락 요약`, `## 검토 결과`, `## 검토 근거 요약`을 추가한다.
7. README, workflow guide, fixtures를 0.2.14 구조로 갱신한다.
8. legacy 0.2.10~0.2.13 readable projection parser 호환을 유지한다.
9. manifest/marketplace/cache 버전 동기화는 실제 구현 완료 후 별도 release step에서 처리한다.

## 14. 롤백 기준

다음 중 하나라도 발생하면 0.2.12/0.2.13 출력 계약으로 롤백한다.

- 사용자가 체크리스트를 놓쳐서 출시 전 해결 필요 항목을 반복적으로 누락한다.
- parser가 `## 체크해야 할 항목`을 기능설계서 본문으로 잘못 합류한다.
- `planning-review`가 0.2.14 `planning-format` 화면 출력에서 정책서·기능설계서를 안정적으로 추출하지 못한다.
- 0.2.14 `planning-review` 출력에서 필수 수정·문서 보강·확인 필요 항목이 `## 결정 보드` 제거 이후 더 찾기 어려워진다.
- `planning-publish-confluence`가 체크리스트나 상세 추적을 Confluence child page 본문에 발행한다.
- `planning-publish-confluence` 저장 폴더 입력이 잘못된 정책서·기능설계서 파일을 선택하거나, 여러 후보 중 하나를 자동 선택한다.
- `planning-publish-confluence`가 저장 폴더 입력만으로 최종 사용자 확인 없이 Confluence에 쓴다.
- `planning-publish-confluence`에 URL fetch나 임의 `.md` 추론이 섞여 발행 대상 경계가 불명확해진다.
- `출처/누락 요약`으로 합친 뒤 원시 검증 피드백 추적성이 사라진다.

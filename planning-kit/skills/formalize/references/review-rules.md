# Review Rules

`formalize`의 자동 리뷰 단계에서 main이 단일 패스로 점검하는 2축 기준이다. 변환 본문(메모리)·입력·SSOT corpus만 근거로 본다. 대화 컨텍스트는 근거가 아니다.

## 용어

- **변환 본문**: 같은 턴에서 main이 메모리에 작성한 정책서·기능설계서 markdown.
- **입력**: 사용자가 `formalize`에 넘긴 텍스트·파일·디렉터리·URL·이미지 원문 + 재귀 fetch한 외부 페이지 본문 + multimodal 해석 텍스트의 통합.
- **SSOT corpus**: **현재 프로젝트 폴더 안 모든 `*.md` 파일만**. `.git/`, `node_modules/` 자동 제외. `--ssot-include <glob>`이 있으면 해당 glob으로 좁힌다. fetch한 외부 URL 본문·multimodal 이미지 해석 텍스트는 SSOT corpus에 포함하지 않는다 (외부·일회성).
- **확정 문장**: 변환 본문 중 [TBD]가 아닌 단정 표현.

## A. 본문 자체 품질 (Self-Review)

정책서·기능설계서 두 본문 자체와 입력만으로 점검한다. SSOT corpus 매칭 여부와 무관하다.

### A1. 섹션 충실도

- [TBD] 비율: 한 섹션에서 [TBD] 셀이 50% 초과면 발견.
- 빈 row: 표 헤더만 있고 데이터 row 0이면 발견.
- 빈 섹션: 섹션 헤더만 남고 본문·표 모두 비면 발견.

### A2. 라벨 cross-bleed

- 정책서 본문에 `화면`, `버튼`, `입력 폼`, `클릭`, `이동` 등 화면·동작 단어가 핵심 규칙을 차지하면 발견.
- 기능설계서 본문에 `허용`, `금지`, `예외 승인`, `판단 기준` 같은 정책 단어가 동작 row 자리를 차지하면 발견.
- 경계 사례: 정책서가 화면 이름을 단순 참조(`주문 화면에서`)하는 정도는 cross-bleed 아님.

### A3. 두 문서 간 용어 일관성

- 같은 대상의 표기가 다르면 발견. 비교 대상:
  - 역할명 (예: `관리자` vs `Admin` vs `운영자`)
  - 상태명 (예: `취소` vs `cancelled` vs `취소됨`)
  - 권한명 (예: `읽기` vs `read` vs `조회`)
  - 도메인 stem (예: `주문` vs `order` vs `주문서`)
- 한 문서 안에서 표기가 흔들려도 발견.
- 본문에 `[TBD]`만 들어간 셀은 비교 대상이 아니다.

### A4. 정책-기능 매핑

- 정책서 §5 세부 규칙 또는 §6 상태 처리에 있는 규칙이 기능설계서 §5 기능 동작·§7 예외에서 누락되면 발견.
- 정책서가 `금지`로 정한 액션이 기능설계서에서 정상 흐름으로 표기되면 발견.
- 정책서 §7 역할 권한이 기능설계서 §6 권한·데이터 접근과 어긋나면 발견.

### A5. 누락 핵심 정보

- 입력에 있던 명시적 사실(역할·상태·기능명·수치 임계 등)이 두 본문 어디에도 없고 §1.5 입력 제외 추적에도 기록 안 됐으면 발견.
- 입력의 대화 메모·진행 톤은 누락 발견 대상이 아니다.

## B. SSOT 충돌

확정 문장이 같은 프로젝트 폴더 안 다른 `*.md`와 어긋나는지 점검한다. 문서 종류·역할(정책/PRD/회의록/README) 구분하지 않는다. archive/draft 분류, version 정렬, 인덱스 스캔 단계는 두지 않는다.

### B1. SSOT corpus 추출

1. 변환 본문에서 키워드 추출: 기능명, 도메인 stem, 역할명, 상태명, 권한명, 정책 핵심어.
2. 추출 키워드 list는 **출력 §리뷰 결과 헤더 줄에 그대로 노출**한다 (사용자가 검색 범위·매칭 근거를 검증할 수 있도록). 카테고리 구분 없이 단순 list. 매칭 0건이거나 SSOT 점검 skip이라도 키워드 줄은 출력한다 — 단, `--no-review`로 리뷰 자체를 건너뛰면 키워드 줄도 없음.
3. 프로젝트 폴더(`pwd` 기준)에서 `find . -name '*.md'` 실행. 노이즈 폴더 자동 제외 (`.git`, `node_modules`).
4. `--ssot-include <glob>` 인자가 있으면 해당 glob으로 좁힌다.
5. 키워드를 `grep -l` 또는 `rg -l`로 본문 매칭 → 매칭 file 목록 확정.
6. 매칭 file을 `Read` 툴로 직접 읽는다 (인덱스 스캔 단계 없음).
7. fetch한 외부 URL 본문·multimodal 이미지 해석 텍스트는 SSOT corpus에 포함하지 않는다 (외부 문서·일회성, 충돌 비교 대상 아님).

### B2. 매칭 0건 처리

- 매칭 file 0건이면 B축은 `검증 대상 없음`. 출력에 `SSOT 매칭 파일 0개 (관련 Markdown 부재)`로만 표시.
- 결과를 낮추지 않는다.

### B3. 매칭 ≥1건 처리

- 변환 본문 확정 문장과 SSOT 매칭 파일 본문을 직접 비교한다.
- 같은 대상(역할·상태·정책 규칙·임계)이 양쪽에 있고 표기·결정·임계값이 어긋나면 발견.
- 같은 대상에 대해 SSOT가 침묵하면 발견 아님.
- archive/old/draft 신호가 있는 SSOT 파일도 grep 매칭만으로 비교에 포함한다 (별도 분류 안 함).

## 발견 사항 형식

각 발견 항목은 다음 필드를 갖는다 (`SKILL.md` §출력 포맷 §정상 list 항목과 동일 구조):

- 자체 품질: `카테고리`(충실도/cross-bleed/용어 일관성/정책-기능 매핑/누락) + `위치`(정책서/기능설계서 §섹션) + `근거`(변환 본문 인용) + `영향`(한 줄) + `제안`(최소 수정 또는 확인 조건).
- SSOT 충돌: `위치`(변환 본문 §섹션 vs SSOT 파일 §섹션) + `근거`(양쪽 인용) + `영향`(한 줄) + `제안`(최소 수정 또는 확인 조건).

같은 발견이 두 축에 걸치면 한 번만 기록한다. 분류는 더 보수적인 쪽(영향이 큰 쪽)으로.

## 결과 결정

- 자체 품질 발견 0건 + SSOT 충돌 발견 0건 → `통과`
- 어느 한쪽이라도 ≥1건 → `발견 N건` (N = 자체 품질 + SSOT 충돌 합계)

조건부 통과·수정 필요 같은 3분 결과는 두지 않는다 (`product-team-kit/plan-review`는 3분, `planning-kit/formalize`는 2분).

# Conversion

이미지 처리, 소스 병합, 두 템플릿 생성, 최소 추적성, 제외 추적을 다룬다.

## 소스 병합

- 텍스트/파일/디렉터리 입력은 source 0.
- URL과 하위 URL은 BFS source 순서.
- 이미지는 입력 파일·디렉터리·markdown/HTML 참조·image content-type 응답·인라인 `data:image`에서 올 수 있다. 보이는 텍스트를 옮기고 화면/흐름/다이어그램 의미를 기술한다. 불확실 추론은 `추정:` 접두.

## 기능명

명시적 사용자 주제 → URL 제목/H1 → 파일 stem → 디렉터리명 → 반복 헤딩 → 첫 핵심 명사구 순으로 고른다. 기능명은 하나만. 다른 후보는 제외 입력으로 추적.

## 템플릿 생성

같은 턴에 두 템플릿을 읽는다:

- `templates/정책서.md`: 11섹션 정책 문서 (목적·적용 범위·용어·원칙·세부 규칙·상태·역할·예외·연동·미결 사항·AI 검증 제외 사항).
- `templates/기능설계서.md`: 기획 레벨 기능 문서 (개요·범위·사용자 흐름·화면과 입력 항목·기능 동작·권한·예외와 메시지·미결 사항·AI 검증 제외 사항; 번호 8·9 결번).

기본은 필드 리스트와 `### 항목` 카드. 표는 본질적으로 표인 내용(상태 전이·메시지 사례 등)에만 쓰고 강제하지 않는다. 빈 placeholder 행을 남기지 말 것. 근거가 없으면 `[TBD]` + 미결 사항 미러.

**생성하지 않는 것** — 구현 상세(데이터 모델·DDL·API 계약·NFR 수치·테스트 시나리오·ERD·옵저버빌리티)는 개발자 영역, PM 전략 장식(RACI·Power×Interest·RICE/MoSCoW·리스크 레지스터·로드맵 진입/종료 게이트·페르소나·여정 감정곡선)은 조직 영역이다. 두 문서 어디에도 넣지 않는다.

## 매핑

정책서:

- 규칙·한계·허용/금지/제한 기준·용어·범위·원칙 → 정책서 1-5.
- 상태 전이·처리 기준·예외·승인 권한·외부 연동 → 정책서 6, 8, 9.
- 역할·책임·권한 → 정책서 7.
- 결정 안 됐거나 근거 부족한 항목 → 정책서 10 미결 사항 (비-MVP는 `(Non-MVP)` 표기).

기능설계서:

- 메뉴·진입 채널·단계별 사용자 행동·트리거·시스템 동작·결과 → 기능설계서 3 사용자 흐름.
- UI·필드·표시/입력·필수·기본값·검증 규칙 → 기능설계서 4 화면과 입력 항목.
- 액션·사전 조건·처리 결과·실패/부분 성공 → 기능설계서 5 기능 동작.
- 역할별 가능 행위·접근/제한 데이터 → 기능설계서 6 권한과 데이터 접근.
- 예외 상황·처리 등급·사용자 메시지·운영 조치 → 기능설계서 7 예외와 메시지.
- 미정 → 기능설계서 10 미결 사항.

- 매핑되지 않는 것 → 제외 추적.

## 최소 추적성 (POL↔FUNC)

- 정책 규칙에는 `POL-001`처럼 순차 ID를 선택적으로 붙일 수 있다. 기능 흐름·동작에는 `FUNC-001`.
- 두 문서의 연결은 헤더 `관련 문서`와 인라인 참조(`관련 기능 동작: FUNC-XXX`, `관련 정책: POL-XXX`)로만 한다. 별도 ID 컬럼이나 매트릭스를 만들지 않는다.
- `POL-`·`FUNC-` 외 prefix(BIZ/RSK/DEC/AC/DATA/API/NFR/TEST)는 쓰지 않는다.

## 용어

정책서는 도메인/시스템 용어를 선호. 기능설계서 UI 필드는 한글 라벨 우선, 시스템 용어는 괄호로 (예: `존 코드 (Zone Code)`).

## 메시지 작성 가이드 (기능설계서 7)

- 오류 메시지 순서: 무엇이 일어났는가 → 왜 → 다음에 무엇을 할지.
- 길이: 버튼 라벨 ≤4단어, 토스트 ≤2문장, 인라인 오류 1-2문장.
- 금지: 행동 없는 사과(`죄송합니다만`, 단독 `다시 시도해주세요`), 원인·후속 없는 일반 오류(`알 수 없는 오류`, `Something went wrong`, 디테일 없는 `Invalid input`).

## 제외 추적

변환 후 정책서·기능설계서에 들어가지 못한 입력 조각을 추적한다.

- catch-all: 비지 않은 모든 입력 조각은 문서 안에 있거나 제외 목록에 있다.
- 불확실 마커는 `[TBD]`만 쓴다 (`[미정]`, `[가정]`, `[확인 필요]`, `해당 없음` 금지).
- 카테고리: duplicate / out of scope / structural / fetch failed / source missing / ambiguous / conflict candidate / other feature / unsupported media / detail summarized / unmapped.
- 의미 있는 제외는 source / location / category / handling / reason 5필드를 남긴다.
- fetch 실패가 사용자 흐름·화면·연동·정책 근거에 영향을 주면 `체크해야 할 항목 > 출처/누락 참고`에 노출한다.

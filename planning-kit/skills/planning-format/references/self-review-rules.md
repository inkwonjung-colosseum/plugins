# Self-Review Rules

`planning-format` 자체 품질 검증의 6 카테고리 기준. **0.2.5부터 6패스 체크리스트** — 카테고리당 1패스, 항목별 yes/no 검사(0.2.8 F6 legacy backlink 헤더 금지와 0.2.9 readable boundary 점검 포함). 체크리스트 □ 중 unchecked 1개 = 발견 1건.

0.2.9부터 self-review는 의미 수정 pass가 아니라 feedback gate다. 고칠 수 있어 보이는 F2/F3/F4/F6 발견도 사용자 승인 전 정책서·기능설계서 canonical 본문에 자동 반영하지 않고 `## 검증 피드백`에 먼저 노출한다.

0.2.10부터 사용자/외부 결정이 필요한 self-review 발견은 `## 결정 보드`의 D*/A* 항목으로 승격할 수 있다. 승격은 상단 action projection일 뿐이며, 원시 F* 발견은 `## 검증 피드백`, `## 상세 추적`, structured mapping에 유지한다.

0.2.12부터 self-review가 끝난 화면 출력은 본문 전에 `## 생성 결과 요약`을 항상 둔다. 검증 피드백은 7열 표가 아니라 카드/필드 목록을 기본으로 하며, 첫 화면에는 `결정 1 (D1)`, `작업 1 (A1)`, `출시 전 해결 1 (T1)`처럼 자연어 라벨을 먼저 쓴다.

## 용어

- **변환 본문**: 같은 턴에서 main이 작성한 정책서·기능설계서 markdown.
- **canonical 본문**: 정책서·기능설계서의 의미 기준. `--save` 파일은 이 canonical Markdown 구조를 우선 보존한다.
- **화면 렌더링**: 기본 응답에서 사람이 읽기 좋게 보여주는 projection. 넓은 표 분해, 코드 펜스 wrapper 제거 같은 표시 변환은 가능하지만 의미 변경은 금지한다.
- **검증 피드백**: self-review 발견과 수정 제안을 사용자에게 먼저 노출하는 섹션.
- **입력**: 사용자가 넘긴 텍스트·파일·디렉터리·URL·이미지 원문 + 재귀 fetch 본문 + multimodal 해석 통합.
- **확정 문장**: 변환 본문 중 `[TBD]`가 아닌 단정 표현.

## 0.2.9 Feedback Gate

self-review 순서:

1. 정책서·기능설계서 초안을 생성한다.
2. F1~F6 6패스 체크리스트를 실행한다.
3. 발견을 `기계적 안정화`, `화면 전용 표시 변환`, `수정 제안 가능`, `사용자/외부 결정 필요`로 분류한다.
4. `기계적 안정화`는 의미를 바꾸지 않는 범위에서 canonical 본문과 저장 파일에 반영할 수 있다.
5. `화면 전용 표시 변환`은 의미를 바꾸지 않는 범위에서 화면 렌더링에만 반영할 수 있다.
6. `수정 제안 가능`과 `사용자/외부 결정 필요`는 canonical 본문에 자동 반영하지 않는다.
7. 최종 출력에는 생성된 정책서·기능설계서 본문과 함께 `## 검증 피드백`을 싣는다.
8. 사용자가 명시적으로 "반영해" 또는 특정 ID 반영을 요청한 뒤에만 다음 응답에서 의미 변경이 포함된 수정 본문을 만든다.

## 0.2.10 결정 보드 승격

self-review 발견을 다음 순서로 결정 보드 후보화한다.

| 발견 유형 | 처리 |
|---|---|
| `사용자/외부 결정 필요`이고 정책 선택·입력 항목 허용 여부·상태/권한/외부 인터페이스 의미가 바뀜 | D* 생성. 반영 작업이 필요하면 A* 생성 |
| 문서 수정만으로 해소되는 P0/P1급 누락·불일치 | D* 없이 A* 생성 가능 |
| 출시/구현/QA 판정을 막는 `[TBD]`, 원문 정의 부재, 충돌 후보 | 사용자 선택 필요 시 D*, 문서 보강만 필요 시 A*. 연결된 D*/A*에 `[출시 전 해결]` badge |
| 기계적 안정화 또는 화면 전용 표시 변환 | 결정 보드에 올리지 않음. 검증 피드백 또는 상세 추적에만 보정 사실 유지 |

D* 카드는 `결정 질문`, `선택지`, `초안 추천(확정 필요)`, `결정 필요자`, `반영 위치`, `연결`을 포함한다. 선택지가 원문에서 충분하지 않으면 `선택지: 확정 필요`로 둔다.

A* 상세 record는 `ID`, `연결`, `유형`, `의존성`, `대상`, `작업`, `완료 조건`, `검증 방법`, `담당/결정 필요자`, `상태`를 포함한다. P0/P1급 A*의 `검증 방법`은 Given/When/Then 또는 동등한 관찰 가능한 문장이어야 한다. `테스트 작성 가능`, `테스트 케이스 작성 가능`, `체크리스트 작성 가능`처럼 가능 여부만 말하는 문장은 검증 방법으로 인정하지 않는다. 관찰 가능한 신호가 부족해 검증 문장을 만들 수 없으면 해당 항목을 `구현/QA 차단` 사유로 표시한다.

상단 결정 보드의 `연결` 필드에서는 원시 F* ID를 직접 나열하지 않고 `관련 발견 N건 (상세 추적의 결정 보드 연결 맵에서 D1로 확인)`처럼 접는다.

분류 기준:

| 분류 | 자동 반영 | 예 |
|---|---|---|
| `기계적 안정화` | canonical + 저장 파일 + 화면 렌더링 | 정책서·기능설계서 전체를 감싼 외부 코드 펜스 wrapper 제거, 명확한 표 구분선 보정 |
| `화면 전용 표시 변환` | 화면 렌더링만 | 5열 이상 표를 행 단위 필드 목록으로 표시, 긴 셀 bullet화 |
| `수정 제안 가능` | 자동 반영 금지 | 정책서 핵심 규칙 자리에 `배너`, `클릭` 같은 UI 표현이 있음. `Zone Code`와 `존 이름` 표기가 같은 UI 표 안에서 흔들림 |
| `사용자/외부 결정 필요` | 자동 반영 금지 | `[TBD]`, 원문 정의 부재, 충돌 후보, 정책 의사결정, SSOT 충돌 |

검증 피드백 형식:

```markdown
## 검증 피드백

- 피드백: 2건
- 사용자 확인 필요: 2건

### 피드백 1 (F2-1) 정책서와 화면 동작 표현 혼재

- 위치: 정책서 6
- 구분: cross-bleed
- 문제: `배너 유지`가 정책서 핵심 처리 기준에 있습니다.
- 영향: 정책/화면 레이어가 섞여 구현 기준이 흐려질 수 있습니다.
- 제안: 정책 표현으로 바꾸고 배너는 기능설계서에만 둡니다.
- 사용자 확인: 필요
- 본문 반영 여부: 미반영, 의미 변경 가능
- 결정 보드 연결: 결정 1 (D1)

### 피드백 2 (F3-1) 용어 표기 기준 흔들림

- 위치: 기능설계서 4.3
- 구분: 용어 일관성
- 문제: UI label과 시스템 용어가 같은 필드에서 섞여 있습니다.
- 영향: 같은 필드의 화면 표기 기준이 불명확합니다.
- 제안: `존 유형 (Zone Type)` 형식으로 통일합니다.
- 사용자 확인: 필요
- 본문 반영 여부: 미반영, 의미 변경 가능
- 결정 보드 연결: 작업 1 (A1)
```

피드백 ID는 같은 출력 안에서만 stable하면 된다. Markdown 표는 기본 형식이 아니며 7열 이상 표는 실패다. 표는 5열 이하이고 모든 표시 문자열 셀이 60자 이하일 때만 보조적으로 쓸 수 있다. self-review를 실행했고 피드백이 0건이면 `## 검증 피드백` 섹션은 유지하고 `없음`을 표시한다. `--no-self-review`가 지정되면 `## 검증 피드백` 섹션은 생략한다.

## F1. 섹션 충실도

- `[TBD]` 비율 50% 초과 → 발견. **보조 표(`### N.M ... 보조 표`) 본문도 포함해서 카운트** (0.2.4).
- 빈 row (표 헤더만 있고 데이터 row 0) → 발견. **보조 표 헤더만 있고 row 0이면 빈 row 발견** (0.2.4).
- 빈 섹션 (헤더만 남고 본문·표 모두 비어 있음) → 발견. **빈 보조 표도 동일 기준** (0.2.4).

### F1 체크리스트 (5 항목, 0.2.5)

```
□ 정책서 1~10 각각 본문 row ≥1 있나
□ 기능설계서 1~8 각각 본문 row ≥1 있나
□ 보조 표 N.M 각각 데이터 row ≥1 있나
□ 정책서 [TBD] / 본문 셀 비율 ≤50%
□ 기능설계서 [TBD] / 본문 셀 비율 ≤50%
```

## F2. 라벨 cross-bleed

- 정책서에 `화면`/`버튼`/`입력 폼`/`클릭`/`이동`/`배너` 등 화면·동작 단어가 핵심 규칙 자리 차지 → 발견.
- 기능설계서에 `허용`/`금지`/`예외 승인`/`판단 기준` 같은 정책 단어가 동작 row 자리 차지 → 발견.
- 경계: 정책서가 화면 이름 단순 참조(`주문 화면에서`)는 cross-bleed 아님.
- **보조 표(`### N.M ... 보조 표`) 본문도 점검 대상** — 정책서 보조 표 안 화면·동작 단어, 기능설계서 보조 표 안 정책 단어는 상위 섹션 룰 그대로 보조 표 확장 (0.2.4).
- 0.2.9: 의미 변경이 필요한 cross-bleed 수정은 canonical 본문에 자동 반영하지 않는다. 예: 정책서 6의 `배너 유지`는 `상태 유지 및 운영자 알림 조건 해소 대기` 같은 정책 표현으로 바꾸는 제안을 `## 검증 피드백`에 올리고, 배너 표현은 기능설계서에만 두도록 제안한다.

### F2 체크리스트 (4 항목, 0.2.5)

```
□ 정책서 3~10 본문에 "화면"/"버튼"/"입력 폼"/"클릭"/"배너" 단어 부재
□ 기능설계서 4~7 본문에 "허용"/"금지"/"예외 승인" 단어 부재
□ 정책서 보조 표 본문에 화면 동작 단어 부재
□ 기능설계서 보조 표 본문에 정책 단어 부재
```

## F3. 두 문서 간 용어 일관성

- 같은 대상의 표기가 다르면 발견. 비교 대상:
  - 역할명 (`관리자` vs `Admin` vs `운영자`)
  - 상태명 (`취소` vs `cancelled` vs `취소됨`)
  - 권한명 (`읽기` vs `read` vs `조회`)
  - 도메인 stem (`주문` vs `order` vs `주문서`)
- 한 문서 안에서 흔들려도 발견.
- `[TBD]`만 들어간 셀은 비교 대상 아님.
- 0.2.9 레이어 원칙: 기능설계서 UI label은 한국어 표기 우선 + 시스템 용어 괄호 병기(`존 코드 (Zone Code)`)를 권장한다. 정책서는 시스템/도메인 용어(`Zone Code`, `Closing Planned`)를 우선한다. 문제는 영문과 한국어가 함께 등장했다는 사실이 아니라, 같은 레이어 안에서 표기 기준이 흔들리는 것이다.

### F3 체크리스트 (4 항목, 0.2.5)

```
□ 역할명 표기 통일 (1 표기/entity)
□ 상태명 표기 통일
□ 권한명 표기 통일
□ 도메인 stem 통일
```

## F4. 정책-기능 매핑

- 정책서 5(세부 규칙)·6(상태 처리) 규칙이 기능설계서 5(기능 동작)·7(예외)에 누락 → 발견.
- 정책서 `금지` 액션이 기능설계서에서 정상 흐름으로 표기 → 발견.
- 정책서 7 역할 권한이 기능설계서 6 권한·데이터 접근과 어긋남 → 발견.

### F4 체크리스트 (4 항목, 0.2.5)

```
□ 정책서 5 규칙 1개당 기능설계서 5 또는 7 매핑 ≥1
□ 정책서 6 상태 전이 1개당 기능설계서 5 액션 매핑 ≥1
□ 정책서 7 권한 1개당 기능설계서 6 행 매핑 ≥1
□ 정책서 `금지` 액션이 기능설계서 정상 흐름 부재
```

## F5. 누락 핵심 정보

### F5.1 본문 누락 (기존 점검)

- 입력의 명시 사실(역할·상태·기능명·수치 임계)이 두 본문·입력 제외 추적에 모두 부재 → 발견.
- 입력의 대화 메모·진행 톤은 누락 대상 아님.

### F5.2 cross-reference 점검 (신규)

입력 제외 섹션은 본문에 합류하지 않은 모든 입력 조각의 단일 추적 위치다. 다음 3 cross-reference가 어긋나면 발견.

#### F5.2.1 sub: `cross-ref-fetch`

- `## 출처` list에 `본문 사용 = X` 행이 ≥1건이고, 해당 자원이 입력에서 단순 부수 링크가 아닌 경우(인용·참조 문장에 언급).
- 입력 제외 섹션에 같은 자원에 대한 `fetch 실패` 카테고리 항목이 없으면 발견.

#### F5.2.2 sub: `cross-ref-scope`

- 정책서 2 / 기능설계서 2 제외 범위 표 cell에서 키워드 추출 + 입력 본문에서 grep 매칭.
- 매칭 키워드가 입력 본문에 있는데 입력 제외 섹션에 `범위 외` 카테고리 항목이 없으면 발견.

#### F5.2.3 sub: `cross-ref-tbd`

- 정책서 10 / 기능설계서 8 미결 항목 중 다음 표현이 들어간 항목을 추출:
  - `원문 명시 없음` / `원문 정의 부재` / `입력 미정` / `원본 본문에 없음`
- 위 표현이 미결 사항 섹션에 있는데 입력 제외 섹션에 `원문 정의 부재` 카테고리 항목이 없으면 발견.

### F5.3 발견 사항 형식

cross-reference 발견은 카테고리 표기에 sub-label 표시:

```markdown
1. fetch 실패 항목이 입력 제외 섹션에 추적 안 됨
   - 카테고리: 누락 (sub: cross-ref-fetch)
   - 위치: 출처 list #3 (Figma board) ↔ 입력 제외 섹션 (해당 카테고리 항목 부재)
   - 근거: "출처 list 행에 인증 실패. 입력 2 사용자 흐름에서 다이어그램으로 인용됨"
   - 영향: 사용자가 다이어그램 누락을 입력 제외 섹션에서 확인 못 함
   - 제안: 입력 제외 섹션에 `fetch 실패` 카테고리 항목 추가 (출처 list #3 cross-reference)
```

### F5 체크리스트 (4 항목, 0.2.5)

```

## F6. Markdown syntax lint

본문 Markdown, 저장 파일, 화면 렌더링이 깨지면 downstream parser와 사용자 검토가 무너진다. 다음만 점검:

- **펜스 짝**: 본문 안 코드 예시의 ` ``` ` 짝 (열고 안 닫음 / 닫음 부족 / inline에 잘못 등장). 기본 화면에서 정책서·기능설계서 전체를 감싸는 외부 코드 펜스 wrapper는 금지한다.
- **표 컬럼 수**: 헤더 `|---|---|` 컬럼 수와 row `|` 카운트 불일치.
- **헤더 레벨 점프**: `#` 다음 첫 자식 헤더가 `###` 이상 (`[TBD]` 셀로 인한 점프는 예외). **`## N → ### N.M [용도] 보조 표` 정상 case는 점프 아님** — 0.2.3 보조 표 도입 후속.
- **보조 표 legacy backlink 헤더**: 0.2.8 이후 신규 출력에서 `### N.M ... 보조 표 (§N row M)`, `### N.M ... 보조 표 (N row M)`, `### N.M ... 보조 표 (N)` 패턴이 남으면 syntax 발견. legacy 문서를 `planning-review`가 읽는 경우에는 강제 발견하지 않는다.
- **빈 인용 부호**: `> ` 한 줄만 + 다음 줄 비어 있음.
- **list marker 일관성**: 같은 list 안 `-`와 `*` 혼용 / `1.`·`2.` 순서 깨짐.
- **reserved wrapper heading 충돌**: 생성된 정책서·기능설계서 본문 안에서 `## 생성 결과 요약`, `## 결정 보드`, `## 검증 피드백`, `## 출처 요약`, `## 입력 제외 요약`, `## 상세 추적`을 최상위 wrapper heading으로 쓰면 readable projection 경계가 모호하므로 발견한다.

위치는 line 번호로 명시. 카테고리 라벨 = `syntax`.

### F6 체크리스트 (0.2.9)

```
□ 내부 코드 펜스 짝 맞음
□ 정책서·기능설계서 전체 외부 코드 펜스 wrapper 없음
□ 표 컬럼 수 일치
□ 헤더 레벨 점프 없음 (보조 표 정상 case 제외)
□ 신규 보조 표 헤더에 legacy backlink 괄호 없음
□ 빈 인용 부호 없음
□ list marker 일관
□ 본문 안 reserved wrapper heading 충돌 없음 (`## 생성 결과 요약`, `## 결정 보드` 포함)
```

## 6패스 진행 (0.2.5)

체크리스트는 6 카테고리 단위로 묶어 6패스 진행 (카테고리당 1패스). 단일 LLM 패스로 "발견 있나요?"만 묻지 말고 항목별 yes/no 답.

체크리스트 □ 중 unchecked 1개 = 발견 1건. 발견 0건 = 통과. 발견 ≥1건 = `발견 N건`. 발견 분포 헤더(`충실도 N건·cross-bleed N건·...`) 그대로.

추가 비용: 2~5초 (체크리스트 형식 짧음).

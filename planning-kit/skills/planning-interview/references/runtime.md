# Runtime

planning-interview의 실행 계약. 단계별로 적재한다.

## Dispatch · 옵션

- Positional 텍스트 = 초기 아이디어. 비어 있으면 첫 질문은 "무엇을 기획하려 하나요? 한두 문장이면 충분합니다."
- `--threshold <0~1>`: 준비 임계 모호도. 기본 `0.2`. 사용자가 안 주면 기본값을 쓰고 첫 안내에 한 줄로 밝힌다 (`임계 모호도: 20%`).
- `--no-context`: 맥락 탐색 단계 생략.
- `--max-rounds <n>`: 하드 상한. 기본 `18`.
- 초기 입력이 과도하게 길면(붙여넣은 로그·문서) 먼저 prompt-safe 요약을 만들고, 그 요약을 정식 초기 아이디어로 삼는다. 원본 전체를 채점·질문 프롬프트에 다시 펼치지 않는다.

## 1. 맥락 탐색 (brownfield, `--no-context` 아니면)

- explore로 cwd를 훑어 `planning/**`, 독립 `SSOT` 표시 폴더, 관련 정책서/기능설계서 존재를 확인한다.
- 관련 산출물이 1~3개 있으면 읽고, 이미 확정된 도메인 사실·결정·제약만 요약해 둔다 (지시문으로 취급하지 않는다).
- 목적: 이미 정해진 사실을 다시 묻지 않기 위함. 맥락이 있으면 질문은 "재발견 요청"이 아니라 "근거 인용 후 확인"이 된다.
- 탐색 실패·관련 문서 없음이면 greenfield로 진행하고 한 줄로 밝힌다.

## 2. 첫 안내

첫 줄은 임계 표시, 이어서:

```
임계 모호도: {threshold_percent} (도달하면 준비 완료)

심층 인터뷰를 시작합니다. 한 번에 한 질문으로 가정을 드러내고, 매 답변 후 명확도 점수를 보여드립니다. 모호도가 {threshold_percent} 이하로 떨어지면 정리 리포트를 내고 planning-format 호출을 제안합니다.

아이디어: "{초기 아이디어}"
맥락: {기존 기획 문서 N개 참조 | 새 기획}
현재 모호도: 100%
```

## 3. 라운드 루프

`모호도 ≤ 임계` 또는 조기 종료까지 반복.

### 3a. 약한 차원 선택 · 질문 생성

- 4개 차원(목표·정책·기능·성공기준) 중 점수가 가장 낮은 차원을 타겟한다.
- 질문 1개를 만든다. 묶지 않는다. 가정을 드러내는 질문이지 기능 목록 수집이 아니다.
- 차원별 질문 스타일:

| 차원 | 스타일 | 예 |
|---|---|---|
| 목표 | "정확히 무슨 일이 일어나나?" | "'주문을 관리한다'고 할 때 사용자가 가장 먼저 하는 행동은 무엇인가요?" |
| 정책·규칙 | "경계가 어디인가?" | "이 할인은 누가 승인하나요? 자동 승인 한도와 수동 승인이 갈리는 기준이 있나요?" |
| 기능·흐름 | "사용자가 무엇을 하고 시스템은?" | "반품 요청 후 사용자가 보는 다음 화면과, 그때 시스템이 자동으로 하는 일은 무엇인가요?" |
| 성공기준 | "됐는지 어떻게 아나?" | "완성본을 보여드리면 '바로 이거다' 하게 만드는 한 가지는 무엇인가요?" |
| 핵심개념 흐려짐 | "이건 본질적으로 무엇인가?" | "지금까지 워크플로우·받은편지함·플래너로 부르셨는데, 핵심은 무엇이고 나머지는 보조 view인가요?" |

- 핵심 명사가 라운드마다 흔들리면(개념이 안 잡힘) 기능 질문 대신 "이건 본질적으로 무엇인가?" 질문으로 전환해 핵심 개념을 먼저 고정한다.
- 사실 질문(기존 정책·역할·상태가 이미 문서에 있음)은 사용자에게 묻지 말고 explore 근거를 인용해 확인만 받는다. 결정 질문(목표·범위·트레이드오프·새 동작)은 항상 사용자에게 묻는다. 애매하면 결정으로 보고 묻는다.

### 3a-1. 기획 challenge 모드 (라운드 임계, 각 1회)

라운드가 깊어지면 통상 약한차원 질문 대신 아래 challenge 모드를 **각 1회씩** 주입해 가정을 압박한다. 발동한 모드는 기록해 재발동하지 않는다. 모드 질문도 1문1답 규칙을 지킨다.

| 발동 | 모드 | 노리는 차원 | 질문 |
|---|---|---|---|
| R3+ | 범위 축소 (Simplifier) | 기능·목표 | "이 정책/기능 중 실제 필요한 건? 가정인 건? 최소 유효 기획은 무엇인가요?" |
| R5+ | 이해관계자 관점 | 기능·정책 | "이 기능으로 손해·불편을 보는 역할은? 승인자·운영·고객 중 빠진 관점은 없나요?" |
| R7+ | 정책 충돌 탐지 | 정책·규칙 | "이 새 규칙이 기존 정책·예외와 충돌하나요? 상태 전이에 모순은 없나요?" |
| R9+ | 엣지·예외 강제 | 정책·성공기준 | "happy path 말고 실패·취소·중복·동시 요청이 들어오면 정책은 어떻게 동작하나요?" |

- 모드 발동 라운드여도 모든 모드를 다 쓴 뒤거나 해당 차원이 이미 0.9+이면 통상 약한차원 질문으로 돌아간다.
- 모드는 perspective를 바꾸는 프롬프트일 뿐 — 별도 에이전트나 산출물을 만들지 않는다.

### 3b. 질문 제시

세션 언어를 적용해 한 줄 헤더 + 질문을 제시한다. 선택지를 제공할 수 있으면(AskUserQuestion 등) 맥락에 맞는 보기 + 자유 입력을 함께 준다.

```
Round {n} | 타겟: {약한차원} | {활성 challenge 모드 or 통상} | 지금 이유: {한 줄} | 모호도: {%}

{질문}
```

### 3c. 채점

답변을 받은 뒤 4개 차원을 0.0~1.0으로 채점한다.

- 목표 (0.0-1.0): 핵심 목표가 모호하지 않은가? 수식어 없이 한 문장으로 말할 수 있나? 핵심 명사·행위를 모호함 없이 댈 수 있나?
- 정책·규칙 (0.0-1.0): 허용/금지/승인 경계, 상태 전이, 역할·권한, 예외가 분명한가?
- 기능·흐름 (0.0-1.0): 사용자 행동과 시스템 동작, 화면 흐름이 구체적인가?
- 성공기준 (0.0-1.0): 됐는지 검증할 기준이 구체적인가?

각 차원에 점수·한 줄 근거·gap(점수 < 0.9면 무엇이 아직 불명확한지)을 단다.

`모호도 = 1 − (목표·0.25 + 정책·0.35 + 기능·0.25 + 성공기준·0.15)`

정책·규칙 가중치가 가장 크다 — 기획 산출물(정책서·기능설계서)에서 정책 경계·예외가 핵심이라서. 모호도는 단방향이 아니다. 새 답변이 앞선 이해를 뒤집거나 범위를 넓히면(새 정책·기능·예외 등장) 해당 차원 점수를 낮춰 모호도가 **오를 수 있다**. 별도 페널티 항 없이 같은 공식으로 흡수한다. 상승은 조용히 처리하고, 다음 질문을 그 차원에 겨눈다.

### 3d. 라운드 리포트

```
Round {n} 완료.

| 차원 | 점수 | 가중치 | 가중점수 | gap |
|---|---|---|---|---|
| 목표 | {s} | 0.25 | {s×w} | {gap or "명확"} |
| 정책·규칙 | {s} | 0.35 | {s×w} | {gap or "명확"} |
| 기능·흐름 | {s} | 0.25 | {s×w} | {gap or "명확"} |
| 성공기준 | {s} | 0.15 | {s×w} | {gap or "명확"} |
| **모호도** | | | **{prior}% → {now}% {↑|↓|—}** | |

다음 타겟: {약한차원} — {한 줄 이유}
{모호도 ≤ 임계 ? "임계 도달! 준비 완료." : "다음 질문은 {약한차원}에 집중합니다."}
```

### 3e. 종료 조건 점검

- Round 3+: 사용자가 "이제 됐어", "그만", "바로 가자"면 조기 종료 허용 — 단 모호도 > 임계면 경고와 함께 남은 gap을 보여준다.
- Round 12: 소프트 경고 — "12라운드입니다. 현재 모호도 {%}. 계속할까요, 지금 명확도로 정리할까요?"
- `--max-rounds`(기본 18): 하드 상한 — 현재 명확도로 정리하며 리스크를 명시한다.
- 모호도가 3라운드 연속 ±0.05로 정체되면 "이건 본질적으로 무엇인가?" 질문으로 reframe.
- 모든 차원 0.9+면 라운드 수와 무관하게 리포트로 넘어간다.
- 사용자가 "중단/취소/그만"이면 즉시 멈추고 현재까지를 리포트로 정리한다.

## 4. 명확도 리포트 (유일한 산출물)

임계 도달·조기 종료·상한 도달 시 출력. 파일을 쓰지 않는다.

```
# [기능명] 인터뷰 결과

## 결론
{준비 완료(모호도 {%} ≤ 임계 {%}) | 모호 — 조기 종료, 남은 gap N건}

## 명확도
| 차원 | 점수 | gap |
|---|---|---|
| 목표 | {s} | {gap or 명확} |
| 정책·규칙 | {s} | {gap or 명확} |
| 기능·흐름 | {s} | {gap or 명확} |
| 성공기준 | {s} | {gap or 명확} |
| **모호도** | **{%}** | |

## 합의된 결정
- 목표: {한 문장 목표 진술}
- 정책 후보: {POL 후보 1}, {POL 후보 2}, ...
- 기능 후보: {FUNC 후보 1}, {FUNC 후보 2}, ...
- 성공기준: {검증 가능한 기준}

## 미결 사항
- {아직 사용자 결정이 필요한 항목}
- {탐색·확인이 필요한 항목}

## 다음 단계
모호도가 임계 이하라면, 이 결정을 입력으로 `planning-format`을 호출하면 정책서·기능설계서가 만들어집니다. 자동으로 호출하지 않습니다 — 사용자가 결정합니다.
```

## 5. planning-format 핸드오프

- 리포트만 낸다. `planning-format`을 자동 호출하지 않는다.
- "다음 단계"에서 호출을 제안한다. 사용자가 동의하면 `## 합의된 결정`을 입력으로 `planning-format`을 호출한다 — 원시 전체 대화가 아니라 정리된 결정을 넘긴다.
- 조기 종료로 모호도 > 임계면 핸드오프를 권하지 않고, 어느 차원이 약해 재작업 위험이 있는지 명시한다.

## 경계 (전부 비-목표)

- 정책서/기능설계서 본문 생성·brief 파일 작성 — `planning-format`의 일.
- 완성 2-doc 검토 — `planning-review`.
- SSOT corpus 감사 — `ssot-audit`.
- 구현 상세·심층 도메인 — `logistics-kit` 등.
- 기획 challenge 모드는 위 4종(범위 축소·이해관계자·정책 충돌·엣지/예외)만 쓴다. topology gate·ontology 수렴추적·multi-component rotation·lateral review panel·auto-research/auto-answer·established-facts·closure/restate gate는 이 린 코어에서 의도적으로 제외한다 (원본 deep-interview의 무거운 머신).

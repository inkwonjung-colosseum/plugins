# Deps Rules (R3 — 의존·영향 분석)

## 용어

- **SSOT corpus**: R1과 동일 set 공유 (`--ssot-include` 같이 적용).
- **영향 후보**: 변환 본문 변경이 영향을 줄 가능성이 있는 SSOT 파일.
- **보조 표 heading 호환**: 0.2.8 clean header(`### N.M ... 보조 표`)와 0.2.4~0.2.7 legacy backlink header(`### N.M ... 보조 표 (§N row M)`)를 모두 sub-§으로 인식한다. legacy header 자체는 R3 발견으로 강제하지 않는다.

## R3.1 4 sub-category

| 카테고리 | 점검 기준 | 영향 후보 산출 |
|---|---|---|
| **정책 변경** | 정책서 §5·§6에 새/변경 규칙 | 같은 도메인 stem 매칭 SSOT 파일 list. 도메인 stem은 R1.1 키워드 set에서 도출. |
| **상태 전이** | 정책서 §6 상태 전이 규칙 변경 | 같은 도메인의 기능설계서·README·정책서 후보. 상태명(`pending`/`approved`/`cancelled`) grep 확장. |
| **권한·역할** | 정책서 §7 역할 권한 변경 | 권한 매트릭스 문서·인증 정책 문서 후보. 역할명·권한명(`관리자`/`Admin`/`read`/`write`) grep. |
| **외부 의존** | fetch한 외부 URL 본문(planning-format 합류 외부 출처 + **0.2.2부터 R1 link follow 합류 외부 본문**)에 등장하는 도메인 stem이 변환 본문 정책과 충돌·일치 | 외부 fetch 본문 vs 변환 본문 비교. 외부 fetch 0건이면 카테고리 skip. |

R1 link follow가 가져온 외부 fetch 본문을 **자동으로** 외부 의존 sub-category 영향 후보로 분류하지는 않는다. 본문 안 도메인 stem이 변환 본문 정책과 충돌·일치할 때만 본 절차로 발견·권고 분류 — corpus 확장 효과지만 점검 절차 자체는 변경 없음.

## R3.2 corpus 매칭

R1.1 키워드 + R3.1 카테고리별 추가 grep 키워드(상태명·권한명·도메인 stem)를 OR로 조합 → `grep -l`/`rg -l` 매칭 → 영향 후보 set 누적. 변환 본문이 가리키는 자기 자신(같은 기능명 file) 자동 제외.

**sub-§ 인식 (0.2.4)**: 변환 본문 정의 = 부모 § + sub-§(`### N.M ... 보조 표`) 합집합. 영향 후보 산출 키워드 추출에 sub-§ 본문도 포함. 발견 위치 표기는 부모 § + sub-§ + row 식별 (`정책서 §5.1 row 3 (보조 표 안)`). 부모 § 단독 가능.

R1 link follow 활성 시 매칭 *.md + 외부 fetch 본문을 모두 corpus로 본다. R3 단독 활성(`--axes deps`)에서도 R3 트리거로 link follow 진입하므로 corpus 확장 효과 발생.

## R3.2.1 입력 제외 § 보조 신호 (0.2.2 신규)

`planning-review` Step 1에서 분리된 `## 입력 제외 항목` 블록을 R3 영향 후보 산출의 **보조 신호**로 활용. R3 비활성이면 본 단계 skip.

| 입력 제외 카테고리 | R3 처리 | 헤더 카운트 K 포함 |
|---|---|---|
| `fetch 실패` | 영향 후보 추가 신호 — 외부 자원이 corpus 미합류라 정책 충돌 가능성. R3 "외부 의존" sub-category로 권고. | O |
| `범위 외` | 인근 도메인 영향 후보 약신호. 같은 도메인 stem grep 매칭 file이 있으면 R3 "정책 변경" sub-category로 권고. | O |
| `구조 변환` | 분해 위치(처리 줄) 참조. 분해된 §1·§2가 SSOT 다른 file과 매칭되면 R3 약신호로 권고. | O |
| `디테일 축약` | 인접 도메인 라벨이 다른 SSOT file과 매칭되면 R3 약신호로 권고. | O |
| `원문 정의 부재` | 미결 [TBD] 항목과 cross-reference. R3 영향 후보 강화 안 함 (충돌 단정 불가). 발견·권고 모두 안 만들고 R3 corpus 매칭에서 제외. | **X** (R3 영향 없음) |
| `다른 기능 후보` / `라벨 미매핑` / `중복` / `근거 부족 무시` / `포맷 노이즈` | 무시 (R3 신호 아님). | X |

**도메인 stem grep 기준**: R1.1 키워드 set (변환 본문 추출 키워드) + 입력 제외 § 항목 본문에서 추가 추출한 stem. 두 set 합집합으로 grep.

**R3 신호로 만든 항목 분류**: 단정 충돌 단서 없으므로 default `권고` 분류 (§R3.3에서 `발견`은 단정 충돌, `권고`는 검토 권장).

**신호 강도**: `fetch 실패` > `범위 외` > `구조 변환` ≈ `디테일 축약`.

## R3.3 발견 vs 권고 분류

| 분류 | 조건 |
|---|---|
| **발견** | 영향 후보 file 안에 변환 본문 확정 문장과 양립 불가능한 단정 문장. 같은 대상 어긋남이 아니라 **연쇄 영향**(이 변경이 들어가면 그 file도 같이 수정돼야). |
| **권고** | 영향 후보 file이 있지만 명시 충돌은 아님. "이 파일도 함께 검토하세요" 수준. |

같은 영향 후보 file이 여러 카테고리에 걸치면 1회만 (가장 영향 큰 카테고리로).

## R3.4 우선순위와 backlog grouping (0.2.9)

R3 항목은 기본적으로 P1/P2로 분류한다.

| 우선순위 | 적용 기준 |
|---|---|
| P1 | 외부 시스템, 권한, 상태 전이, 정책 변경이 다른 기준 문서나 기능에 직접 수정 영향을 준다는 단정 근거가 있는 발견 |
| P2 | cross-link, 동기화 workflow, 주변 문서 검토, SSOT 보강처럼 후속 관리가 필요한 권고 |

R3 발견 ID는 `R3-1`, `R3-2` 형식을 쓴다. R3 `발견`은 `최우선 수정 항목` 후보가 될 수 있고, R3 `권고`는 보통 `작업 백로그`와 `발견 요약`에 압축한다.

작업 백로그 유형 신호:

| R3 신호 | 기본 backlog 유형 |
|---|---|
| 정책 변경 | `문서 수정` 또는 `동기화 워크플로` |
| 상태 전이 | `문서 수정` |
| 권한·역할 | `문서 수정` 또는 `정책 결정` |
| 외부 의존 | `외부 인터페이스` |
| 입력 제외 § `fetch 실패` | `외부 인터페이스` 또는 `SSOT 보강` |
| 입력 제외 § `범위 외` / `구조 변환` / `디테일 축약` | `동기화 워크플로` 또는 `SSOT 보강` |

## R1과의 분리

- R1: 같은 대상의 표기·결정 어긋남.
- R3: 이번 변경이 들어가면 다른 SSOT도 같이 손봐야 하는 연쇄 영향.

같은 발견이 R1·R3 모두에 걸리면 R1로 1회만 (R1이 더 단정적).

## 제안 형식

`X.md §Y 섹션을 함께 수정` / `권한 매트릭스 문서 갱신 필요` 형태 — 후속 검토 조건.

# product-team-kit Evolution Roadmap

기획팀이 `product-team-kit`을 실사용한 뒤 자연스럽게 떠오를 진화 방향을 단기, 중기, 장기로 정리한다.

이 문서는 기능 추가 아이디어 목록이 아니라, 현재 플러그인의 핵심 경계를 유지하면서 실제 팀 사용 데이터가 쌓였을 때 어떤 순서로 확장할지 판단하기 위한 로드맵이다.

## 단기: 도입 1~2개월

### 1. 팀 용어집/역할명 누적 SSOT 구축 스킬

- 제안 스킬명: `team-glossary-build`
- 핵심 목적: `plan-review`의 근거 품질을 높이기 위한 팀 용어·역할명 SSOT 축적
- 추천 시점: 즉시

`plan-review`의 실효성은 SSOT 밀도에 크게 의존한다. 현재 SSOT가 부족하면 검토는 템플릿 품질 확인 수준에 머물 수 있다.

`plan-format` 산출물에서 반복 등장하는 canonical 역할명, 업무 용어, 상태명, 정책 용어를 수집해 `docs/glossary-candidates.md`, `docs/roles-candidates.md` 같은 후보 문서를 생성한다. 사람이 검토해 승인한 항목만 `docs/glossary.md`, `docs/roles.md`로 승격한다.

권장 흐름:

1. `planning/` 하위 누적 산출물에서 역할명과 용어를 빈도 분석한다.
2. 후보 용어와 출처 파일을 함께 정리한다.
3. 후보 문서를 생성하거나 PR로 제안한다.
4. 사람이 승인한 항목만 SSOT 문서로 반영한다.
5. 이후 `plan-review`가 해당 SSOT를 근거로 활용한다.

### 2. 사용 metric 가시화

- 제안 명령: `/product-team-kit:stats` 또는 별도 stats 스킬
- 핵심 목적: 팀 회고와 운영 개선에 필요한 사용 지표 제공
- 추천 시점: 도입 1개월 후

팀 단위로 추적할 지표:

- 저장 보류 사유 분포: 정보 부족, 디자인 heavy, 기존 산출물 부족 등
- `plan-review` 결과 분포: `pass`, `conditional pass`, `수정 필요`
- 자주 발생하는 `[미정]` 항목 top N
- 평균 수정 라운드: `FIX-001` 발생부터 재검토 후 pass까지

이 지표는 기능 성능 평가가 아니라 팀 기획 프로세스의 병목과 반복되는 누락 항목을 찾기 위한 회고 자료로 사용한다.

### 3. 좋은/나쁜 기획초안 사례 누적

- 대상 문서: `docs/examples.md`
- 핵심 목적: 신규 기획자 온보딩과 팀 내 작성 품질 기준 축적
- 추천 시점: 도입 1개월 후

사용자가 명시적으로 동의한 산출물만 익명화해 사례 라이브러리로 누적한다. 좋은 예시는 통과 기준을 보여주고, 나쁜 예시는 왜 저장 보류 또는 수정 필요가 되었는지 함께 남긴다.

자동 보강 대상:

- 입력이 충분해 바로 초안 생성된 사례
- 저장 보류된 입력과 부족 항목
- `plan-review`에서 `수정 필요`가 나온 사례와 수정 후 pass된 사례
- 익명화된 역할명/정책명/상태명

## 중기: 3~6개월

### 4. Multi-feature 정책 일관성 검토

- 제안 스킬명: `plan-review-cross`
- 핵심 목적: 여러 기능 설계서와 정책서 사이의 정책·역할·상태 일관성 검토
- 추천 시점: 도입 3개월 후

현재 `plan-review`는 한 기능 단위 검토에 집중한다. 실제 팀 사용에서는 여러 기능 사이에서 다음 문제가 발생할 수 있다.

- 같은 역할명이 기능마다 다르게 정의됨
- 기능 A에서는 허용한 정책을 기능 B에서는 금지함
- 상태 전이 모델이 기능별로 다르게 표현됨

`plan-review-cross`는 여러 `planning/` 폴더와 Project Docs SSOT를 함께 읽어 cross-document 일관성을 검토한다. 단, `planning/` 산출물은 여전히 SSOT 근거가 아니라 비교 대상이어야 한다.

### 5. Iteration/Version 관리

- 핵심 목적: 같은 기능을 여러 번 생성했을 때 최신 버전과 변경 이력을 추적
- 추천 시점: 도입 3개월 후

현재 구조에서는 같은 기능을 여러 번 `plan-format` 실행하면 `기능명--timestamp/` 폴더가 N개 쌓이고, 어느 버전이 최신인지 추적하기 어렵다.

검토 가능한 해결안:

- `planning/[기능명]/v1--timestamp/`, `v2--timestamp/` 구조
- `planning/[기능명]--latest` symlink
- `plan-review` 출력에 이전 버전 대비 차이점 N개 포함

버전 관리는 단순 폴더 정리보다 발행 전 변경 영향 파악에 가깝다. 이전 버전과 달라진 정책, 역할, 상태, 확인 기준을 명시하면 팀 리뷰 비용을 줄일 수 있다.

### 6. 도메인별 템플릿 분기

- 대상 파일: `schemas/doc-types.yaml`
- 핵심 목적: 기획 유형별로 필요한 섹션과 검토 관점을 분리
- 추천 시점: 도입 6개월 후

현재 기능설계서/정책서 템플릿은 단일 구조다. 실제 팀 산출물은 성격이 다를 수 있다.

- 운영툴 기획: 내부 사용자, 권한 매트릭스, 상태 전이 중요
- 고객 화면 기획: UX 흐름, 노출 문구, 예외 처리 중요
- 정책 단독 기획: 화면보다 규칙, 조건, 예외, 적용 범위 중요

`schemas/doc-types.yaml`에 domain variant를 추가하고, `plan-format`에서 사용자 선택 또는 입력 기반 자동 감지로 템플릿을 분기한다.

### 7. 결정 권한 & 출처 추적

- 핵심 목적: 팀 단위 사용 시 결정의 책임자, 일자, 근거를 추적
- 추천 시점: 도입 3개월 후

현재는 사용자 답변과 로컬 확인 정도만 구분한다. 팀 모드에서는 결정 메타데이터가 중요해진다.

추가할 메타데이터:

- 결정자: 이름 또는 역할
- 결정 일자
- 근거: 회의록 경로, Slack URL, 외부 문서 snapshot 경로 등

기획초안 섹션 9에 결정 출처 메타를 추가해 이후 `plan-format`, `plan-review`, postmortem 흐름에서 계속 추적할 수 있게 한다.

## 장기: 6~12개월

### 8. 반영 후 피드백 루프

- 제안 스킬명: `plan-postmortem`
- 핵심 목적: 발행 이후 구현·운영 중 발견된 모호함을 다음 기획 질문과 검토 기준에 반영
- 추천 시점: 도입 6개월 후

현재 워크플로우는 발행 준비 증적에서 끝난다. 실제로는 팀 문서 반영, 개발 시작, 구현 중 정책 모호 발견, 기획 수정의 흐름이 이어진다.

`plan-postmortem`은 발행된 초안에서 실제 발생한 모호함이나 정책 충돌을 기록하고, `docs/postmortem-patterns.md`에 누적한다. 이후 `plan-draft`의 질문 우선순위에 자주 빠뜨리는 항목을 반영한다.

### 9. 다른 팀 hand-off 플러그인 분리

- 핵심 목적: product-team-kit의 책임 경계를 유지하면서 개발, QA, 운영 후속 플러그인과 연결
- 추천 시점: 도입 12개월 후

`product-team-kit`의 책임은 기획자의 제품·업무 판단 경계까지다. 이후 산출은 별도 플러그인으로 분리하는 편이 명확하다.

후속 플러그인 후보:

- `dev-spec-kit`: 기능설계서에서 API 명세, DB 스키마, 작업 분해 생성
- `qa-test-kit`: 정책서에서 테스트 케이스 생성
- `ops-runbook-kit`: 예외, 상태, 운영 판단 기준에서 런북 생성

현재 `classification-contract.md`의 제외 항목은 이 hand-off 경계와 잘 맞는다. 따라서 후속 플러그인은 product-team-kit 산출을 입력으로 받되, product-team-kit 내부 책임을 확장하지 않는 방향이 적합하다.

### 10. 외부 문서 시스템 read-only 연동

- 핵심 목적: Confluence/Notion 등 외부 문서 snapshot을 SSOT corpus 후보로 포함
- 추천 시점: 도입 9개월 후

외부 문서 자동 수정은 위험하지만, read-only 참조는 SSOT 밀도를 높이는 데 유효하다.

검토 방향:

- Confluence/Notion export snapshot을 SSOT corpus 옵션으로 포함
- `evidence_sources`에 `external_snapshot` 종류 추가
- snapshot freshness/staleness 명시
- vendor-neutral 정책은 유지하고 export adapter는 별도 플러그인으로 분리

### 11. 협업 충돌 방지

- 핵심 목적: 여러 기획자가 같은 기능명으로 동시에 작업할 때 충돌을 감지하고 안내
- 추천 시점: 필요시

현재 atomic `mkdir`은 파일 시스템 race condition은 줄일 수 있지만, 의도적인 동시 작업 상황을 안내하기에는 부족하다.

검토 가능한 보완:

- `.lock` 파일
- git branch 안내
- 같은 기능명으로 진행 중인 작업 감지
- 기존 작업자와 작업 시작 시각 표시

초기에는 git branch 운영으로 우회 가능하므로 우선순위는 낮다.

## 진화 중 지켜야 할 invariant

현재 강점이 기능 확장 과정에서 깨지지 않도록 아래 invariant를 PR 리뷰의 첫 체크리스트로 사용한다.

1. `planning/ != SSOT`: 어떤 기능도 `planning/` 산출물을 SSOT 근거로 승격하지 않는다.
2. Anti-ping-pong: 자동 루프를 추가하지 않는다. 모든 새 기능은 사용자 결정 지점을 명시한다.
3. 3-스킬 책임 분리: `plan-draft`는 검토하지 않고, `plan-review`는 생성하지 않는다.
4. 로컬 초안 경계: 자동 외부 발행은 금지한다. 사람의 reflection 단계를 보존한다.
5. 계약 단일 출처: 새 기능은 먼저 `references/`에 contract를 두고, `SKILL.md`는 이를 참조한다.

이 invariant가 깨지면 플러그인의 정체성이 흔들린다. 기능 진화 PR에서는 구현 편의보다 이 경계 유지 여부를 먼저 확인한다.

## 가장 추천하는 첫 진화 작업

첫 진화 작업은 `team-glossary-build` 스킬 추가를 추천한다.

이유:

- 현재 가장 큰 약점인 SSOT 의존성을 직접 보완한다.
- 누적 산출물에서 자동 추출할 수 있어 수동 작성 부담이 낮다.
- `plan-review`의 효과가 즉시 증가한다.
- cross-feature 검토와 postmortem 루프의 기반이 된다.

권장 구현 범위:

1. `planning/` 누적 산출에서 canonical 역할명과 용어 후보를 추출한다.
2. 후보의 빈도, 출처 파일, 주변 문맥을 함께 기록한다.
3. `docs/glossary-candidates.md`와 `docs/roles-candidates.md`를 생성한다.
4. 사람이 승인한 항목만 `docs/glossary.md`, `docs/roles.md`로 승격한다.
5. `plan-review`는 승인된 glossary/roles 문서를 Project Docs SSOT로 사용한다.

초기 구현은 자동 승격이 아니라 후보 생성까지만 맡기는 것이 안전하다. SSOT 성장은 사람이 승인하는 흐름을 유지해야 한다.

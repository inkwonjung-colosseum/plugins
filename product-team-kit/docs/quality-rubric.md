# product-team-kit Quality Rubric

`plan-draft`는 핵심 모호함을 질문으로 해소하거나 명시하고, 필요한 로컬 맥락 확인으로 `plan-format`에 넘길 기획초안을 만든다. Codex에서는 Plan mode의 사용자 질문 도구를 우선 사용하고, 질문 도구가 없어도 현재 대화를 이어갈 수 있으면 일반 대화 fallback으로 질문 흐름을 진행한다. 비대화형 실행처럼 사용자 답변을 이어받을 수 없는 경우에만 저장하지 않고 `질문 필요로 저장 보류`를 반환한다.

`plan-review`는 `plan-format`이 저장한 기능설계서와 정책서를 발행 전에 근거, 결정·범위, 실행·검증 가능성 관점에서 확인한다. 먼저 검토 대상 파일과 필요한 Project Docs SSOT Markdown 및 linked local resource를 읽어 근거 패키지를 만들고, 각 관점은 현재 대화 컨텍스트가 아니라 검토 대상 파일과 근거 패키지로 판단한다.

`plan-review`는 템플릿 구조 검증 도구가 아니다. 발행 전에 근거가 맞는지, 결정 범위가 충분한지, 개발·운영·QA가 같은 기준으로 움직일 수 있는지만 확인한다.

`planning/` 아래 생성되는 산출물은 로컬 초안 템플릿이며 공식 팀 문서가 아니다. 따라서 `pass`나 `conditional pass`도 팀 문서 반영 완료가 아니라 사람이 반영 절차로 넘길 수 있는 준비 상태만 뜻한다.

`plan-format`은 formatter다. 먼저 초안 생성 가능성을 점검하고, 통과한 입력만 템플릿에 맞게 구조화한다. Project Docs SSOT 충돌 검증과 발행 가능성 판단은 `plan-review`에서 수행한다.

`plan-draft`와 `plan-format`의 상세 사용자 출력은 `../references/output-contract.md`를 따른다. `plan-format`의 기능설계서/정책서 분류는 `../skills/plan-format/references/classification-contract.md`를 따른다.

`plan-draft`는 기능설계서와 정책서를 직접 만들지 않는다. 사용자 답변, 로컬 확인 내용, `[미정]`, `[가정]`, 확인 필요 질문을 분리한 기획초안을 저장한다.

입력이 기능설계서/정책서 초안을 만들 최소 수준에 못 미치면 `plan-format`은 저장 보류를 반환하고 파일을 만들지 않는다. 일반 입력 부족은 `plan-draft` 보완으로 연결할 수 있지만, `plan-draft` 산출 `_기획초안.md`도 부족하면 `사용자 결정 필요`로 종료해 자동 왕복을 끊는다.

## 검토 결과

| 결과 | 의미 | 발행 판단 |
|---|---|---|
| `pass` | 치명적인 누락이나 충돌이 없다 | 발행 후보 |
| `conditional pass` | 남은 조건을 기획자가 인지하고 확인하면 반영 가능하다 | 조건 확인 후 발행 후보 |
| `수정 필요` | 구현 또는 운영 판단에 필요한 정보가 부족하다 | 불가 |

최종 결과는 관점별 결과 중 가장 보수적인 값을 사용한다: `수정 필요 > conditional pass > pass`.

`수정 필요` 결과의 수정 작업 블록은 실패를 완화하지 않는다. P0/P1 수정 포인트를 후속 수정 작업과 재검토 루프로 넘기기 위한 구조화 출력 계약이며, `plan-review`가 초안이나 SSOT 문서를 직접 수정한다는 뜻이 아니다.

`pass`와 `conditional pass` 결과의 `publish_readiness` 블록은 발행 실행이 아니라 발행 준비 체크리스트다. `plan-review`는 외부 시스템에 직접 게시하지 않고, `planning/` 산출물을 Project Docs SSOT 근거로 승격하지 않으며, Project Docs SSOT Markdown 또는 팀 문서 export snapshot을 자동 수정하지 않는다.

## 발견 사항 분류

`plan-review`는 구조화된 발견 사항을 사용해 검토 결과를 합성한다. 발견 사항은 `관점`, `위치`, `심각도`, `발견 유형`, `신뢰도 앵커`, `근거 인용`, `영향`, `최소 수정 포인트 또는 확인 조건`, `출력 버킷`을 가진다.

- 발견 유형은 `오류`와 `누락`으로 구분한다.
- 심각도: P0은 검토 불가 또는 필수 근거 미확인, P1은 문서 수정 없이는 구현·운영·QA 판단이 달라지는 항목, P2는 기획자 확인으로 닫을 수 있는 항목, P3는 참고 관찰이다.
- P2의 `오류`는 기획자가 명시적으로 수용하면 문서 수정 없이 발행 후보가 될 수 있는 경우에만 사용한다. 문서 수정 없이는 판단이 달라지는 오류는 P1이다.
- 신뢰도 앵커: 100은 Project Docs SSOT 직접 근거, 75는 명시 문장 기반 단일 추론, 50은 후보 미확인이나 검증 한계가 있는 관찰이다.
- 출력 버킷: 수정 포인트 / 확인 조건 / 참고 관찰.
- 수정 포인트: 발행 전 문서 수정 없이는 구현 또는 운영 판단이 달라지는 항목.
- 확인 조건: 기획자가 명시적으로 확인하거나 수용하면 발행 후보가 될 수 있는 항목.
- 참고 관찰: 사실 기반 관찰이지만 발행 판단을 낮추지 않는 항목.
- 참고 관찰은 최종 검토 결과를 낮추지 않는다.

Coverage의 `구조화된 발견 사항` 수는 필수 필드가 유효하고 최종 합성 후 출력에 남는 수정 포인트, 확인 조건, 참고 관찰의 합계다. 필수 필드가 빠져 제외한 항목은 count하지 않고 검증 한계에 기록한다.

구조화 출력 상태는 `completed`, `limited`, `failed`로 기록한다.
`limited` 또는 `failed`가 있으면 `pass`를 반환하지 않는다.
`limited`는 조건이 명확할 때만 `conditional pass`가 될 수 있다.
`failed`는 항상 `수정 필요`다. failed 관점은 관점별 검토 결과를 `failed: 결과 없음`으로 기록한다.

## 근거

확인 항목:

- Project Docs SSOT 근거와 충돌하지 않는다.
- 출처가 필요한 주장은 관련 Markdown 문서나 linked local resource를 근거로 가진다.
- `[가정]` 항목은 실제 결정이 필요한지 구분되어 있다.
- `planning/` 산출물은 SSOT 근거로 사용하지 않는다.
- archive, old, deprecated, draft 신호가 있는 문서는 현재 정책처럼 사용하지 않는다.
- 초안의 근거는 입력값에 명시된 내용과 별도 검토 문서로 구분되어 있다.
- 직접 관련 Markdown뿐 아니라 그 Markdown이 상대경로로 참조한 로컬 resource 중 충돌 가능성이 있는 관련 근거를 필요한 범위에서 읽는다.
- 읽지 않은 관련 후보와 검증 한계를 남긴다.

## 결정·범위

확인 항목:

- 문서 타입이 기능설계서, 정책서 중 하나로 명확하다.
- 적용 대상, 비대상, 예외가 분리되어 있다.
- 확정된 결정의 적용/비적용/예외 범위가 닫혀 있다.
- 관련 정책서/기능설계서가 필요한 항목은 문서명이나 경로로 연결된다.
- 선택적 세부의 `[미정]` 항목은 검토 결과를 낮추는 근거로 사용하지 않는다.
- 구현·운영·QA 판단에 필요한 정책, 예외, 권한, 상태, 확인 기준이 `[미정]`이면 P1 또는 P2로 판단한다.
- 부서 소유 상세 산출물이 본문에 완성본처럼 섞였는지 확인하고, 필요하면 관련 문서 또는 확인 필요 사항으로 분리한다.

## 실행·검증 가능성

확인 항목:

- 상태, 조건, 권한, 사용자 노출 결과, 예외 처리 기준이 명확하다.
- 정상 기준과 주요 예외 기준이 확인 기준으로 있다.
- 수정 문서라면 `[기존]`과 `[변경]` 차이가 명확하다.
- 후속 검증에서 확인할 수 있는 체크포인트가 있다.
- 업무 연동 경계, 업무 데이터, 외부 채널, 실패 대응, 운영 영향이 필요한 수준으로 드러난다.

## Review Gate

발행 가능성 판단은 `plan-review`에서 수행한다. 아래 항목 중 하나라도 남아 있으면 발행 전에 검토 결과 또는 명시적 의사결정이 필요하다.

- `[가정]`
- 확인 필요 질문
- Project Docs SSOT 근거와의 충돌 경고

## 대화형 기획초안

좋은 기획초안 기준:

- 중요한 모호함이 질문으로 해소되었거나 `[미정]`, `[가정]`, `[확인 필요]`, `[충돌 후보]`로 명시되어 있다.
- 문제/목적, 사용자/범위, 핵심 흐름, 정책/조건, 예외/권한/상태, 확인 기준의 우선순위로 정리되어 있다.
- 확인 필요 항목에는 이유와 결정 주체가 있다.
- `[충돌 후보]`는 확정 사실로 쓰지 않고 사용자 주장, 로컬 근거 경로, 후속 확인 방법을 포함한다.
- 산출물이 확정안이 아니라 질문으로 정리된 plan-format 입력자료임이 드러난다.
- 저장 경로는 `planning/[안전기능명]--YYYY-MM-DD-HHMMSS/[안전기능명]_기획초안.md`이며 기존 산출물을 덮어쓰지 않는다.
- `plan-format`은 저장된 `_기획초안.md`를 입력받으면 기획초안 폴더를 재사용한다.
- `plan-format` 저장 보류에서 온 기획초안이면 optional `## 11. 재실행 맥락` 섹션으로 보류 사유와 보완 대상 부족 항목을 남긴다.

`plan-draft` 저장 가능 조건:

- 기능명·문제·목적 중 한 문장 요약 가능하다.
- 주요 사용자 또는 업무 범위를 설명할 수 있다.
- 핵심 사용자 행동과 기대 결과가 1개 이상 있다.
- 정책/조건/제약 중 최소 1개 이상 있다.

`plan-draft`는 로컬 프로젝트에서 확인한 내용과 사용자 답변을 구분해야 하며, 로컬 근거가 부족하면 추측하지 않고 질문으로 남긴다.

질문은 최대 3라운드까지만 진행한다. 일반 대화 fallback 질문도 라운드 수에 포함한다. 3라운드 후에도 저장 가능 조건을 충족하지 못하면 저장 보류한다. 저장 가능 조건 4개 중 하나라도 문서화 불가하면 저장 보류하고, 정책/조건/제약을 전혀 설명할 수 없는 경우도 저장 보류다. 세부 권한, 예외, 상태, 문구, QA 상세처럼 초안 골격을 막지 않는 항목은 저장을 막지 않고 확인 필요 항목으로 남긴다. `plan-draft` 자체의 저장 보류가 나오면 부족 항목의 답변을 보완해 다시 `plan-draft`를 실행한다.

## 초안 생성 가능성

초안 생성 가능성 검증은 생성 전 판단이다.

- `초안 생성 가능: 예`: 기능 목적/기능명, 적용 대상 또는 업무 범위, 핵심 사용자 행동과 기대 결과, 주요 조건/정책/제약이 식별되어 문서 생성 가능.
- `초안 생성 가능: 아니오`: 문서 초안을 만들 최소 입력이 부족하여 저장 보류 또는 `사용자 결정 필요`.
- `사용자 결정 필요`: `plan-draft` 보완 후에도 `plan-format`이 초안을 만들 최소 입력이 부족하다고 판단한 terminal hold. 실패가 아니라 자동 ping-pong을 끊는 상태이며, 사용자가 직접 보완, 새 기획 인터뷰 명시 시작, 생성 범위 축소 중 하나를 결정해야 한다.
- 예외, 권한, 상태, 근거, 알림 같은 세부 항목은 부족해도 문서 생성 가능하며, 생성된 문서 안에 `[미정]`, `[가정]`, 확인 필요 질문으로 남긴다.

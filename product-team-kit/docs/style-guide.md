# product-team-kit Style Guide

## 문서 원칙

- Project Docs SSOT를 source of truth로 둔다.
- Project Docs SSOT는 `planning/`을 제외한 현재 프로젝트의 Markdown 문서와 그 문서가 상대경로로 참조한 로컬 resource만 포함한다.
- 코드, 테스트, 설정 파일, 빌드 산출물, dependency/vendor, 외부 URL은 SSOT 근거로 사용하지 않는다.
- `planning/` 산출물은 로컬 초안 템플릿이며 공식 팀 문서가 아니다. 경계 상세: README "로컬 초안 템플릿 경계" 참조.
- 확인된 사실, 가정, 미정 항목을 섞지 않는다.
- `plan-draft`는 핵심 모호함을 질문으로 해소하거나 명시해 `plan-format` 입력용 기획초안을 만든다.
- `plan-draft`는 필요한 경우 현재 로컬 프로젝트의 관련 파일을 최소로 확인한다.
- Codex에서 `plan-draft`는 Plan mode의 사용자 질문 도구를 우선 사용하고, 질문 도구가 없어도 현재 대화를 이어갈 수 있으면 일반 대화 fallback으로 질문 흐름을 진행한다.
- Codex 비대화형 실행처럼 사용자 답변을 이어받을 수 없는 경우에만 `질문 필요로 저장 보류`를 반환한다.
- `plan-draft`는 중요한 모호함이 남아 있으면 최대 3라운드까지 추가 질문하되, 세부 미확정 항목은 저장을 막지 않고 확인 필요 항목으로 남긴다.
- `plan-format`은 생성 전 초안 생성 가능성을 점검하고, 통과한 입력만 템플릿에 맞게 정리한다.
- `plan-format`은 입력 해석과 공통 정리 기준 확정은 순차로 처리하고, 기능설계서/정책서 본문 작성만 병렬화한다.
- `plan-format`은 인터뷰 스킬이 아니므로 입력이 부족하면 질문 루프를 만들지 않고 저장 보류와 `plan-draft` 보완 안내를 반환한다.
- `plan-format`은 `plan-draft` 산출 `_기획초안.md`를 입력받으면 기획초안 폴더를 재사용한다. 그 외 일반 입력은 새 timestamp 폴더에 저장한다.
- 자동 보완 왕복은 1회까지만 허용한다. `_기획초안.md` 입력이 다시 부족하면 `사용자 결정 필요`로 종료하고 자동 재질문을 중단한다.
- 깊은 기획 정리와 저장 가능 조건 보완은 `plan-draft` 책임이다.
- `plan-format`은 Project Docs SSOT 검색이나 근거 검증을 수행하지 않는다.
- Project Docs SSOT 근거 검증과 발행 전 결정·실행 가능성 판단은 `plan-review`에서 수행한다. `plan-review`는 근거 패키지를 먼저 만들고 그 기준으로 결정·범위와 실행·검증 가능성을 확인한다.
- 기획자가 결정해야 하는 기능 동작, 조건, 예외를 읽기 좋은 형식으로 정리한다.
- Project Docs SSOT 문서는 정책/기능 판단 계약을 소유한다.
- 부서별 상세 산출물은 본문에 완성본처럼 생성하지 않는다.
- 부서별 상세 산출물이 필요하면 관련 문서 또는 확인 필요 사항으로만 남긴다.
- 표는 조건, 권한, 상태, 예외, 확인 기준처럼 비교가 필요한 곳에만 사용한다.
- Mermaid는 표시 가능한 흐름, 상태, 분기, 관계 구조가 있으면 기본적으로 추가한다.
- Mermaid는 표나 본문에 이미 있는 흐름·상태·분기·관계만 요약하며 새 사실을 만들지 않는다.
- Mermaid가 표나 본문과 불일치하면 제거하거나 수정한다.
- 입력 판정, 저장 절차, 출력 형식, marker 의미, 재실행 제어의 세부 계약은 `../references/input-dispatch.md`, `../references/storage-contract.md`, `../references/output-contract.md`, `../references/markers-contract.md`, `../references/rerun-contract.md`를 따른다.

## 표현

- 확인되지 않은 내용, 결정되지 않은 내용, 검증이 필요한 내용은 `../references/markers-contract.md` 기준으로 `[가정]`, `[미정]`, `[확인 필요]` 또는 `[충돌 후보]`로 분리한다.
- `plan-draft`에서 사용자 답변과 로컬 확인 내용은 출처를 구분한다.
- 확인 필요 항목에는 이유와 결정 주체를 함께 쓴다.
- 기존 문서와의 충돌 판정은 `plan-review`에서 수행한다.
- 검토 발견 사항은 P0/P1/P2/P3 심각도와 100/75/50 신뢰도 앵커로 구분한다.
- 정책 조건은 "조건 → 처리 방식 → 비고" 순서로 쓴다.

## 문서 타입

| 타입 | 사용 기준 |
|---|---|
| 기능설계서 | 개요, 범위, 진입점, 사용자 흐름, 화면·입력 항목, 기능 동작, 권한, 예외, 확인 기준을 정리한다 |
| 정책서 | 정책 목적, 적용 범위, 비즈니스 규칙, 조건, 상태·처리 기준, 역할·권한, 예외·승인 기준을 정리한다 |

기능설계서와 정책서의 세부 분류 기준은 `../skills/plan-format/references/classification-contract.md`를 따른다. 상태·권한·예외가 양쪽에 걸리면 정책서는 업무 판단 기준만, 기능설계서는 사용자 노출 결과와 가능 행위만 쓴다.

`plan-format`은 `planning/[안전기능명]--YYYY-MM-DD-HHMMSS/[안전기능명]_기획초안.md` 입력을 받으면 같은 폴더에 기능설계서와 정책서를 저장한다. 일반 입력은 새 timestamp 폴더에 저장한다. 대상 폴더에 기능설계서나 정책서가 이미 있으면 덮어쓰지 않고 저장 보류한다. `_기획초안.md` 입력도 부족하면 `사용자 결정 필요`를 출력하고 자동 `plan-draft` 안내를 하지 않는다.

## 출력 문구

`plan-draft`와 `plan-format`의 상세 출력 형식은 `../references/output-contract.md`를 따른다. 저장 완료, 일반 대화 질문 진행, 저장 보류, 질문 필요로 저장 보류, 사용자 결정 필요, 저장 실패 출력은 이 계약의 템플릿을 사용한다.

출력에는 생성 전 판단인 초안 생성 가능성만 포함한다. 발행 전 근거·결정·실행 가능성 판단은 `plan-review`에서 수행한다. 0개 섹션 생략과 복사 가능한 재실행 블록도 `output-contract.md` 기준을 따른다.

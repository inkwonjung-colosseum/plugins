# plan-draft

사용자와 대화하면서 기능 목적, 사용자, 범위, 정책 판단, 화면 흐름, 예외, 확인 기준을 좁혀 **기획초안**을 만드는 기획 인터뷰 스킬이다. `plan-draft`는 기능설계서/정책서 최종 초안을 직접 만들지 않고, 핵심 모호함을 질문으로 해소하거나 명시해 `plan-format`에 넘길 수 있는 정리된 입력을 만든다. 산출물은 확정안이 아니라 질문으로 정리된 plan-format 입력자료다.

## 호출

- Claude Code: `/product-team-kit:plan-draft <기획 의도, 주제, 파일경로, 또는 로컬 프로젝트 경로>`
- Codex: `$plan-draft <기획 의도, 주제, 파일경로, 또는 로컬 프로젝트 경로>`

## 암묵 호출 라우팅

다음 의도에서는 `plan-draft`를 선택한다.

- 질문하면서 기획을 잡기
- 핵심 모호함 해소
- 기능 방향, 문제, 사용자, 범위, 정책 조건을 대화로 정리
- `plan-format` 저장 보류 후 부족 항목 보완
- 기능설계서/정책서 초안 생성 전에 기획 입력을 만들기

다음 의도에서는 `plan-draft`를 선택하지 않는다.

- 충분한 기획 입력을 기능설계서와 정책서로 바로 정리하려는 경우 → `plan-format`
- 기존 기능설계서/정책서 초안을 평가하거나 pass 판단하려는 경우 → `plan-review`

## 실행 환경

- 질문 도구는 구조화된 질문을 위한 우선 경로다. 입력만으로 저장 가능 조건을 충족하면 질문 도구 없이 저장 절차로 진행할 수 있다.
- Claude Code에서는 `AskUserQuestion`을 사용할 수 있으면 선택지형 질문을 한다. `AskUserQuestion`이 없으면 일반 대화형 질문으로 대체한다.
- Codex에서는 질문이 필요한 경우 Plan mode의 `request_user_input` 계열 사용자 질문 도구를 우선 사용한다.
- Codex에서 질문 도구가 없지만 현재 대화가 이어질 수 있으면 **일반 대화 fallback**을 사용한다. 질문 도구가 없더라도 바로 저장 보류로 종료하지 않는다. 파일을 만들지 않고 1~3개 질문을 일반 메시지로 묻고, 현재 대화의 다음 사용자 답변을 같은 plan-draft 실행의 답변으로 이어받는다.
- Codex 비대화형 실행, detached automation, batch 실행처럼 사용자 답변을 이어받을 수 없는 환경에서는 일반 대화 fallback을 사용하지 않는다. 이때만 파일을 만들지 않고 `질문 필요로 저장 보류` 출력 형식으로 필요한 답변을 출력한다.
- 질문 도구가 있는 환경에서도 한 번에 1~3개 질문만 묻는다.
- 사용자가 이미 답한 내용은 다시 묻지 않는다.

## 동작 순서

1. 입력 확인과 디스패치
2. 로컬 프로젝트 맥락 확인 여부 판단
3. 필요한 로컬 파일 최소 탐색
4. 질문 단계 진행
5. 답변을 기획초안으로 정리
6. 초안 충분성과 저장 가능성 단일 판정
7A. 저장 완료
7B. 일반 대화 질문 진행
7C. 초안 부족으로 저장 보류
7D. 초안 충분하지만 저장 실패
8. 출력 형식에 맞춰 다음 단계 안내

### 1. 입력 확인과 디스패치

입력 종류와 첫 행동은 `../../references/input-dispatch.md`의 `plan-draft` 기준을 따른다. 저장 기준 루트는 `../../references/storage-contract.md`의 `plan-draft` 저장 기준 루트를 따른다. 사용자 출력은 `../../references/output-contract.md`의 `plan-draft` 기준을 따른다. 입력에 `재실행 상태: format-insufficient-hold` 또는 `plan-format 저장 보류 사유`가 있으면 `../../references/rerun-contract.md`의 기획초안 재실행 맥락 규칙도 따른다.

### 2. 로컬 프로젝트 맥락 확인 여부 판단

현재 로컬 프로젝트에 필요한 정보가 있을 가능성이 있으면 사용자가 준 경로나 현재 작업 디렉터리에서 관련 파일을 좁게 확인한다.

확인 대상 예:

- 기존 기획 문서, 회의록, PRD
- 현재 프로젝트의 Markdown 기획 문서와 그 문서가 상대경로로 참조한 로컬 resource
- 용어집, 도메인 정의, 비즈니스 규칙 문서
- README, docs 중 기획 관련 섹션

규칙:

- 전체 repo를 무작정 읽지 않는다.
- 먼저 파일명과 검색 결과로 후보를 좁힌다.
- `planning/` 하위 산출물은 SSOT 근거 후보로 사용하지 않는다. 사용자가 명시한 경우에도 과거 초안 맥락으로만 다룬다.
- 코드, 테스트, 설정 파일, 빌드 산출물, dependency/vendor, 외부 URL은 기획 SSOT 근거로 사용하지 않는다.
- 로컬 파일에서 확인한 내용과 사용자 답변은 구분해 기록한다.

### 3. 필요한 로컬 파일 최소 탐색

로컬 프로젝트 확인이 필요한 경우 다음 순서와 hard cap 안에서만 좁게 탐색한다.

1. 검색 쿼리 최대 3개로 관련 후보 확인
2. 검색 결과 후보 최대 20개까지 검토
3. 관련성이 높은 파일 최대 5개만 선택
4. 파일당 필요한 섹션 또는 최대 200라인 window만 읽기
5. 선택한 Markdown이 상대경로로 참조한 로컬 resource는 필요한 범위만 읽기
6. 확인한 사실과 불확실한 추정을 분리

cap에 걸리면 더 넓히지 않고 질문으로 돌리거나 `[미정]`으로 남긴다. 로컬 근거가 부족하면 추측하지 않고 질문으로 돌린다.

로컬 파일 근거는 읽은 시점의 snapshot으로 취급한다. 초안에는 읽은 파일 경로와 확인한 섹션을 남기고, 필요한 경우 확인 시각을 남긴다. 저장 직전 임의로 추가 파일을 읽어 새 사실을 섞지 않는다.

### 4. 질문 단계 진행

질문은 사용자의 답변과 로컬 맥락에 따라 필요한 단계만 진행한다.

기본 강화 원칙:

- 중요한 모호함이 남아 있으면 추가 질문한다.
- 질문 우선순위는 `문제/목적 → 사용자/범위 → 핵심 흐름 → 정책/조건 → 예외/권한/상태 → 확인 기준` 순서로 둔다.
- 답변이 추상적이면 `누가 / 언제 / 무엇을 보고 / 어떤 선택을 하고 / 성공·실패 시 결과가 무엇인지` 단위로 재질문한다.
- 질문은 최대 3라운드까지만 진행한다. 각 라운드는 사용자에게 보낸 1~3개 질문 묶음 1회다.
- 저장 보류 후 재실행하면 질문 라운드 카운터는 새로 시작한다. 이전 실행의 질문 횟수는 이어받지 않는다.
- 한 라운드의 질문 중 일부만 답해도 해당 라운드는 소비된다.
- 공백, 무응답, `모름`, `정하지 않음`만 있는 답변은 해당 항목을 `[미정]`으로 기록한다.
- 모든 핵심 항목이 빈 답변이면 저장 보류한다.
- 일부 항목만 비어 있고 저장 가능 조건을 충족하면 저장하고 남은 항목은 `[미정]`, `[가정]`, `[확인 필요]`, `[충돌 후보]`로 남긴다.
- 3라운드 후에도 저장 가능 조건을 충족하지 못하면 추가 질문하지 않고 저장 보류를 출력한다.
- 질문은 품질을 높이기 위한 인터뷰이며, 모든 항목을 강제로 확정하는 게 아니다.
- 세부 권한, 예외, 상태, 문구, QA 상세처럼 초안 골격을 막지 않는 항목은 저장을 막지 않고 확인 필요 항목으로 남긴다.
- 일반 대화 fallback으로 보낸 질문도 질문 라운드로 카운트한다.
- 일반 대화 fallback에서는 현재 응답에서 파일을 만들지 않는다. 사용자가 다음 답변을 주면 명시적으로 `$plan-draft`를 다시 쓰지 않아도 같은 plan-draft 흐름으로 이어서 저장 가능성을 판단한다.

| 단계 | 목적 | 대표 질문 |
| --- | --- | --- |
| 문제 | 왜 필요한지 확인 | 어떤 업무 문제가 있나요? |
| 사용자 | 누가 쓰는지 확인 | 주요 사용자는 누구인가요? |
| 범위 | 포함/제외를 나눔 | 이번 초안에 포함하지 않을 것은 무엇인가요? |
| 흐름 | 사용자가 무엇을 하는지 확인 | 사용자는 어떤 순서로 행동하나요? |
| 정책 | 규칙과 조건 확인 | 허용/금지/예외 기준은 무엇인가요? |
| 상태 | 상태와 전이 확인 | 어떤 상태가 있고 언제 바뀌나요? |
| 권한 | 역할별 가능 행위 확인 | 누가 조회/등록/수정/승인할 수 있나요? |
| 예외 | 실패와 운영 대응 확인 | 실패하면 사용자는 무엇을 보나요? |
| 확인 기준 | 완료 판단 확인 | 어떤 결과가 나오면 맞게 동작한 건가요? |

질문 원칙:

- 자유 입력보다 선택지가 도움이 되면 2~3개 선택지를 제시한다.
- 선택지만으로 부족하면 짧은 추가 설명 입력을 허용한다.
- 디자인·개발 산출물은 확정하지 않는다. 금지: 디자인 상세(컬러·폰트·스펙·Figma), 최종 UX copy, QA 테스트 케이스, API 명세, DB schema, 운영 런북, 개발 작업 분해.
- 사용자가 디자인·개발 산출물을 요청하거나 입력에 섞어도 기획 판단에 필요한 최소 맥락만 한 줄로 요약하고, 상세는 확인 필요 항목으로 분리한다.
- 답변이 모호하면 다음 질문으로 구체화한다.
- 사용자가 모르면 `[미정]`으로 남긴다.
- `[충돌 후보]`는 근거 있는 불일치가 있을 때만 남긴다. 가능성만으로 붙이지 않는다.
- `[충돌 후보]`는 확정 사실로 쓰지 않는다. 사용자 답변과 Project Docs SSOT 근거가 다르면 어느 쪽도 우선 확정하지 않고 충돌 항목, 사용자 주장, 로컬 근거 경로, 후속 확인 방법을 남긴다.

### 5. 답변을 기획초안으로 정리

기획초안은 `plan-format` 입력으로 바로 쓸 수 있게 작성한다.

필수 섹션:

```md
# [기능명] 기획초안

## 1. 문제와 목적

## 2. 사용자와 업무 범위

## 3. 포함 범위와 제외 범위

## 4. 사용자 흐름

## 5. 정책과 조건

## 6. 상태 / 권한 / 예외

## 7. 화면 또는 입력 정보

## 8. 확인 기준

## 9. 로컬 프로젝트에서 확인한 출처 목록

## 10. 미정 / 가정 / 확인 필요 질문
```

입력에 `재실행 상태: format-insufficient-hold` 또는 `plan-format 저장 보류 사유`가 있으면 저장 문서 끝에 optional `## 11. 재실행 맥락` 섹션을 추가한다. 일반 `plan-draft` 실행에는 만들지 않는다.

```md
## 11. 재실행 맥락

- 출처: plan-format 저장 보류
- 보류 사유: [plan-format 저장 보류 사유]
- 보완 대상 부족 항목: [부족 항목 요약]
- 자동 왕복 횟수: 1
```

출처와 상태 표기는 `../../references/markers-contract.md`의 `plan-draft` 적용 기준을 따른다.

`로컬 프로젝트에서 확인한 출처 목록` 섹션은 읽은 파일과 확인한 섹션만 나열한다. 본문과 같은 내용을 중복 요약하지 않는다. 개별 주장에는 인라인으로 `사용자 답변` 또는 `로컬 확인: <파일경로>`를 붙인다.

로컬 확인이 없으면 `## 9. 로컬 프로젝트에서 확인한 출처 목록`에 다음과 같이 쓴다.

```md
해당 없음 - 로컬 파일을 읽지 않음
```

`미정 / 가정 / 확인 필요 질문` 섹션에는 각 항목의 이유, 결정 주체, 후속 확인 방법을 함께 남긴다. 항목이 없으면 `## 10. 미정 / 가정 / 확인 필요 질문`에 다음과 같이 쓴다.

```md
해당 없음 - 저장 시점에 별도 미정/가정/확인 필요 질문 없음
```

`[충돌 후보]` 사용 기준과 필수 기록 항목은 `../../references/markers-contract.md`를 따른다.

### 6. 초안 충분성과 저장 가능성 단일 판정

저장 가능 조건은 모두 충족해야 한다.

- 기능명이 있음
- 문제 또는 목적을 한 문장으로 설명할 수 있음
- 주요 사용자 또는 업무 범위를 설명할 수 있음
- 핵심 사용자 행동과 기대 결과가 1개 이상 있음
- 정책/조건/제약 중 최소 1개 이상 있음

판정 결과:

| 결과 | 조건 | 파일 생성 | 다음 행동 |
| --- | --- | --- | --- |
| 저장 완료 | 저장 가능 조건 모두 충족 + 저장 절차 성공 | 예 | `plan-format`으로 전달 |
| 일반 대화 질문 진행 | 저장 가능 조건 충족 전 질문이 필요함 + 구조화된 질문 도구 없음 + 현재 대화에서 사용자 답변을 이어받을 수 있음 | 아니오 | 일반 메시지로 1~3개 질문 후 사용자 답변을 기다림 |
| 초안 부족으로 저장 보류 | 저장 가능 조건 중 하나 이상 문서화 불가. 특히 질문을 1회 이상 했지만 핵심 답변이 없어 초안을 구성할 수 없음 | 아니오 | 부족 항목에 답한 뒤 `plan-draft` 재실행 |
| 질문 필요로 저장 보류 | 저장 가능 조건 충족 전 질문이 필요하지만 현재 환경에서 사용자 답변을 이어받을 수 없음. 비대화형 실행이거나 detached automation/batch 실행인 경우 | 아니오 | 필요한 답변을 보완해 `plan-draft` 재실행 |
| 초안 충분하지만 저장 실패 | 저장 가능 조건 모두 충족 + timestamp/mkdir/write/rename 실패 | 아니오 | 추가 기획 질문이 아니라 저장 환경 확인 후 재실행 |

저장 보류는 초안 골격이 없는 경우에만 사용한다. 예외, 권한, 상태, 문구, QA 상세처럼 초안 골격을 막지 않는 세부 항목은 저장을 막지 않고 `[미정]`, `[가정]`, `[확인 필요]`, `[충돌 후보]`로 남긴다.

`[충돌 후보]`는 저장 차단 사유가 아니다. 충돌 후보가 있어도 저장 가능 조건을 충족하면 저장하고 충돌 항목으로 남긴다.

### 7A. 저장 완료: 파일 저장

저장 가능 조건을 충족하면 `../../references/storage-contract.md`의 기능명/안전기능명 추출 규칙과 `plan-draft` 저장 절차에 따라 기획초안을 저장한다.

### 7B. 일반 대화 질문 진행

질문 도구가 없지만 현재 대화를 이어갈 수 있으면 파일을 만들지 않고 `../../references/output-contract.md`의 `일반 대화 질문 진행` 형식으로 필요한 질문을 출력한다. 이 출력은 terminal hold가 아니다. 답변을 받으면 같은 `plan-draft` 흐름으로 이어서 판단한다.

### 7C. 초안 부족으로 저장 보류

초안 부족으로 저장 보류 조건에 해당하면 파일을 만들지 않고 `../../references/output-contract.md`의 `초안 부족으로 저장 보류` 형식으로 부족 항목과 필요한 답변을 출력한다.
저장 보류 출력에는 사용자가 그대로 복사해 재실행할 수 있는 `바로 재실행 가능한 입력 블록`을 항상 포함한다.

### 7D. 초안 충분하지만 저장 실패

저장 가능 조건은 충족했지만 timestamp, mkdir, write, rename 단계에서 실패하면 파일을 만들지 않았다고 보고 `../../references/output-contract.md`의 `초안 충분하지만 저장 실패` 형식으로 출력한다. 이 경우 추가 기획 질문을 하지 않는다.

### 8. 출력 계약 적용

저장 완료, 일반 대화 질문 진행, 초안 부족으로 저장 보류, 질문 필요로 저장 보류, 초안 충분하지만 저장 실패의 사용자 출력은 `../../references/output-contract.md`의 `plan-draft` 템플릿을 따른다. 0개 섹션 생략, 복사 가능한 재실행 블록, 저장 실패 다음 행동도 같은 계약을 따른다.

## 규칙

- 기능설계서와 정책서를 직접 생성하지 않는다. 그 작업은 `plan-format` 책임이다.
- 발행 전 근거 검증을 하지 않는다. 그 작업은 `plan-review` 책임이다.
- 핵심 모호함은 질문으로 줄이되, 모든 내용을 확정하려고 하지 않는다.
- 사용자의 답변과 로컬 파일에서 확인한 내용을 섞어 확정 사실처럼 쓰지 않는다.
- 현재 대화에만 있는 내용은 사용자 답변으로 표시한다.
- 로컬 프로젝트를 읽을 때는 관련 파일만 최소로 읽는다.
- 외부 발행 시스템에 직접 게시하지 않는다.
- Project Docs SSOT 문서와 linked local resource를 임의 수정하지 않는다.
- Codex에서 질문 도구가 없는 실행 모드라도 질문이 필요 없을 만큼 입력이 충분하면 저장 절차를 진행할 수 있다.
- Codex에서 질문이 필요한데 질문 도구가 없으면 현재 대화를 이어갈 수 있는지 먼저 판단한다. 이어갈 수 있으면 일반 대화 fallback으로 묻고, 비대화형 실행에서는 저장하지 않고 `질문 필요로 저장 보류`를 반환한다.

# plan-format

기획 입력이 **정책서 + 기능 설계서** 두 로컬 초안으로 변환 가능한지 먼저 판정하고, 변환 가능할 때만 두 문서를 생성·저장하는 formatter 스킬이다. 생성된 문서는 `planning/` 아래 로컬 초안 템플릿이며 공식 팀 문서가 아니다. Product Docs SSOT 검증과 착수 가능성 판단은 `plan-review`가 담당한다.

## Gate First

파일 생성 금지 조건을 먼저 적용한다. 이 gate를 통과하기 전에는 초안 파일, 임시 파일, 저장 폴더를 만들지 않는다.

- 변환 가능 조건: 기능 목적/기능명, 적용 대상/업무 범위, 핵심 사용자 행동과 기대 결과, 주요 조건/정책/제약이 모두 식별되어야 한다.
- 기능설계서 최소 내용: 사용자 행동과 사용자에게 보이는 결과가 1개 이상 있어야 한다.
- 정책서 최소 내용: 허용/금지/조건/예외/제한/판단 기준 중 업무 판단 기준이 1개 이상 있어야 한다.
- 저장 보류: 위 조건 중 하나라도 부족하거나 한쪽 문서가 빈 골격만 될 경우 파일을 만들지 않고 보류 출력만 반환한다.
- `[미정]`, `[가정]`, `[확인 필요]`은 변환 가능 판정 통과 후 세부 보강용으로만 사용한다. gate 통과 전 부족분을 채우는 용도로 쓰지 않는다.

## 호출

- Claude Code: `/product-team-kit:plan-format <기획 입력 또는 파일/디렉터리 경로>`
- Codex: `$plan-format <기획 입력 또는 파일/디렉터리 경로>`

기능명은 별도 인자로 받지 않는다. 입력 본문, 파일명, 디렉터리명에서 추출한다.

## 역할 경계

- `plan-format`은 사용자가 준 입력, 파일, 디렉터리만 읽고 변환 가능성을 판단한다.
- `plan-format`은 Product Docs SSOT를 검색하거나 검증하지 않는다.
- `[충돌 후보]`는 입력 내부의 모순, 중복, 상충에만 사용한다.
- Product Docs SSOT와의 충돌, 근거 검증, 착수 가능성 판단은 `plan-review` 책임이다.
- 상위설계서는 지원하지 않는다.
- 기존 산출물은 덮어쓰지 않는다.

## 암묵 호출 라우팅

다음 의도에서는 `plan-format`을 선택한다.

- 기획 노트, 회의록, AI 대화 결과물, 초안 문서 스크랩을 기능설계서와 정책서로 정리
- 기능설계서와 정책서 초안 생성 또는 로컬 저장
- 기획자료 디렉터리의 텍스트 파일들을 통합해 기능설계서/정책서로 변환
- 저장 보류 후 부족 항목을 보강한 입력을 다시 기능설계서/정책서로 변환

다음 의도에서는 `plan-format`을 선택하지 않는다.

- 이미 생성된 기능설계서/정책서 초안을 검토하거나 pass 판단하려는 경우 -> `plan-review`
- 기능설계서/정책서 생성 없이 단순 질의응답이나 아이디어 탐색만 원하는 경우 -> 일반 답변

생성과 검토가 함께 요청되면 먼저 `plan-format`으로 초안을 저장하고 `plan-review`를 안내한다. 사용자가 명시적으로 바로 검토까지 요청한 경우에만 저장 경로를 대상으로 `plan-review`를 이어서 수행한다.

## 동작 순서

1. `references/input-dispatch.md` 기준으로 입력을 판정하고 읽은 텍스트, 제외 항목, 입력 처리 타입을 확보한다.
2. Gate First 기준으로 변환 가능성을 판정한다.
3. 부족하면 파일 생성 없이 `references/output-contract.md`의 저장 보류 출력을 반환한다.
4. 충분하면 공통 정리 기준을 만든 뒤 `references/classification-contract.md`에 따라 기능설계서/정책서 내용을 분리한다.
5. `templates/`의 섹션 스펙과 `references/worker-contract.md`에 따라 두 문서 본문을 작성한다.
6. `references/storage-contract.md` 기준으로 저장 폴더와 안전기능명을 확정한다.
7. 두 파일을 하나의 저장 단위로 저장한다.
8. `references/output-contract.md`의 저장 완료 또는 저장 실패 출력을 반환한다.

## 입력과 저장

이 스킬은 Python, Node.js, 별도 CLI helper 설치를 전제하지 않는다. 실행자는 현재 환경에서 가능한 기본 파일 읽기/쓰기 수단을 사용하되, 아래 계약을 지킨다.

- 입력 판정과 파일 제외 기준은 `references/input-dispatch.md`를 따른다.
- 저장 위치, 안전기능명, timestamp, two-file 저장 단위는 `references/storage-contract.md`를 따른다.
- 디렉터리 입력은 기본 제외 경로를 적용한다: `.git`, `node_modules`, `planning`, `dist`, `build`, `coverage`, `.cache`, `vendor`, `__pycache__`.
- 디렉터리 입력 기본 상한은 파일 100개, 파일당 512KB, 총 2MB다.
- 제외된 파일은 사용자 출력의 `[입력 제외 항목]`에 남긴다.

## 문서 작성 규칙

- 결과물에는 빈 표 행, 예시 placeholder, 값 없는 metadata, 빈 섹션을 남기지 않는다.
- 내용이 있는 섹션만 생성한다. 필요한데 확정할 수 없는 항목은 `[미정]`, `[가정]`, `[확인 필요]`로 표시한다.
- `[미정]`, `[가정]`, `[확인 필요]`, `[충돌 후보]`는 `references/markers-contract.md`에 따라 inline 위치, 문서 끝 색인, 사용자 출력 요약에 일관되게 반영한다.
- 기능설계서의 `관련 정책서`와 정책서의 `관련 기능설계서`는 같은 output folder의 상대 링크를 기본으로 쓴다.
- `외부/타시스템 연동`, `운영 조치`, `관련 문서`, `접속 환경`은 입력 근거가 있을 때만 생성한다.
- 정책서 세부 규칙은 허용/금지/조건/예외 판단 기준만 쓴다. 화면 동작, 입력 방식, 사용자 노출 결과는 기능설계서에 쓴다.

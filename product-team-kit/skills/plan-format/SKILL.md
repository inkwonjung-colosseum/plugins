# plan-format

기획 입력을 검증해 통과시 **기능설계서·정책서** 두 문서를 병렬 생성·저장하는 formatting 스킬. 입력 형태(AI 대화·비구조 노트·초안 문서 스크랩) 무관. 부족한 세부는 `[미정]`/`[가정]`/확인 필요 질문으로 남김. **Project Docs SSOT 근거 검증은 plan-review.**

## 로컬 초안 템플릿 경계

`planning/` 아래 저장되는 기능설계서·정책서는 **로컬 초안 템플릿**이며 **공식 팀 문서가 아니다**. 경계 상세: README "로컬 초안 템플릿 경계" 참조.

## 호출

- Claude Code: `/product-team-kit:plan-format <기획 입력 또는 파일경로>`
- Codex: `$plan-format <기획 입력 또는 파일경로>`

인자에 직접 붙여넣기 또는 파일 경로 전달. 기능명은 별도 인자 없음 — 입력 본문/파일명에서 추출.

## 암묵 호출 라우팅

다음 의도에서는 `plan-format`을 선택한다.

- 기획 노트, 회의록, AI 대화 결과물, 초안 문서 스크랩을 기능설계서와 정책서로 정리
- 기능설계서와 정책서 초안 생성 또는 로컬 저장
- `plan-draft` 산출 `_기획초안.md`를 기능설계서/정책서로 변환
- 충분한 제품·업무 판단 정보가 있는 입력을 템플릿에 맞춰 구조화

다음 의도에서는 `plan-format`을 선택하지 않는다.

- 질문하면서 기획 방향을 잡거나 부족 항목을 보완해야 하는 경우 → `plan-draft`
- 이미 생성된 기능설계서/정책서 초안을 검토하거나 pass 판단하려는 경우 → `plan-review`

사용자가 “정리하고 검토”를 함께 요청하면 먼저 `plan-format`을 수행한다. 초안 저장이 성공하면 `plan-review`를 다음 단계로 안내하며, 사용자가 명시적으로 바로 검토까지 요청한 경우에만 저장 경로를 대상으로 `plan-review`를 이어서 수행한다.

## 동작 순서

1. 입력 확인과 디스패치
2. 기능명과 안전기능명 추출
3. 초안 생성 가능성과 저장 가능성 단일 판정
4A. 부족하면 저장하지 않고 피드백 반환
4B. 충분하면 입력 내용을 기능설계서/정책서로 분류
5. 템플릿에 맞춰 채우기
6. 일부 미확정은 `[미정]` / `[가정]` / 확인 필요 질문으로 남기기
7. 두 파일 저장 단위로 파일 저장
8. 출력 형식에 맞춰 다음 단계 안내

분류 기준은 `references/classification-contract.md`를 따른다. 병렬화 원칙과 worker 계약은 `references/worker-contract.md`를 따른다.

### 1. 입력 확인과 디스패치

입력 종류와 첫 행동은 `../../references/input-dispatch.md`의 `plan-format` 기준을 따른다. 저장 기준 루트와 `plan-draft` 산출 `_기획초안.md` 식별 후 저장 위치는 `../../references/storage-contract.md`를 따른다. 사용자 출력은 `../../references/output-contract.md`의 `plan-format` 기준을 따른다. `draft artifact input`의 정보 부족 재실행 제어는 `../../references/rerun-contract.md`를 따른다.

### 2. 기능명과 안전기능명 추출

기능명과 안전기능명은 `../../references/storage-contract.md`의 기능명/안전기능명 규칙을 따른다.

### 3. 초안 생성 가능성과 저장 가능성 단일 판정

생성 전 판단한다. `식별 가능` = 원 입력에 명시되어 있거나 같은 문맥에서 직접 재구성 가능한 최소 증거. 일반 도메인 지식 추측이나 기능명만으로는 식별 불가.

저장 가능 조건은 각 항목을 1개 이상 충족해야 한다.

- 기능 목적/기능명: 기능명·문제·목적 중 한 문장 요약 가능
- 적용 대상/업무 범위: 사용자·역할·조직·업무 대상·포함 범위 중 확인 가능
- 핵심 사용자 행동과 기대 결과: 행동 1개 + 결과 1개
- 주요 조건/정책/제약: 허용·금지·조건·예외·제한·판단 기준 중 확인 가능

판정 결과:

| 결과 | 조건 | 파일 생성 | 다음 행동 |
| --- | --- | --- | --- |
| 저장 완료 | 저장 가능 조건 충족 + 두 문서로 나눌 내용 있음 + 두 파일 저장 단위 성공 | 예 | `plan-review`로 전달 |
| 정보 부족 저장 보류 | 저장 가능 조건 중 하나 이상 문서화 불가, 두 문서로 나눌 내용 거의 없음, 단순 키워드·제목·의도만 있음 | 아니오 | `plan-draft`로 보완 |
| 사용자 결정 필요 | `draft artifact input`이 정보 부족 저장 보류 조건에 해당함 | 아니오 | 자동 `plan-draft` 안내 없이 사용자가 보완 방식 결정 |
| 디자인·개발 heavy 저장 보류 | 디자인/API/DB/QA/운영/작업분해 상세가 주된 내용이고 저장 가능 조건을 충족하지 못함 | 아니오 | 제품·업무 판단 정보로 재구성 후 `plan-format` 재실행 |
| 기존 산출물 존재 저장 보류 | 대상 폴더에 `[안전기능명]_기능설계서.md` 또는 `[안전기능명]_정책서.md` final 파일이 이미 있음 | 아니오 | 기존 산출물 확인 또는 명시적 새 run |
| 저장 실패 | 저장 가능 조건 충족 + timestamp/mkdir/write/rename/cleanup 실패 | 아니오 | 저장 환경과 partial artifact 확인 후 재실행 |

판정 예시:

- 통과: `견적 승인 요청 등록. 영업 담당자가 견적서를 선택해 승인자에게 요청, 승인자는 승인/반려. 1천만원 이상은 팀장 승인 필요.`
- 통과: `파트너 정산 내역 조회 화면. 정산 담당자가 월별 정산 금액·상태 확인, 확정 전 금액 조정 사유 입력 가능.`
- 통과: `입고 보류 해제. 창고관리자가 보류 사유 확인 후 해제, 입고 가능 상태로 전환. 파손 의심은 관리자만 해제.`
- 보류: `승인 기능 개선` / `정산 화면 필요. 보기 좋게 정리` / `알림 정책 만들기`

예외·권한·상태·근거·알림 등 세부는 부족해도 저장 가능. `[미정]`/`[가정]`/확인 필요 질문으로 남김.

### 4A. 부족하면 저장하지 않고 피드백 반환

파일을 만들지 않는다. 추가 질문 없음. 보류 유형과 다음 단계만 반환한다.
모든 저장 보류 출력에는 사용자가 그대로 복사해 재실행할 수 있는 `바로 재실행 가능한 입력 블록`을 항상 포함한다.

일반 입력 정보 부족, draft artifact 입력 부족, 디자인·개발 heavy, 기존 산출물 존재 보류의 사용자 출력은 `../../references/output-contract.md`의 `plan-format` 보류 템플릿을 따른다.

### 4B. 충분하면 입력 내용을 기능설계서/정책서로 분류

입력 전체를 스캔해 `references/classification-contract.md` 기준으로 두 문서에 배치한다. 상태·권한·예외처럼 양쪽에 걸리는 항목도 같은 계약을 따른다.

### 5. 템플릿에 맞춰 채우기

공통 정리 기준 확정, handoff artifact, worker 시작 조건, 병렬/순차 worker 실행, Mermaid, 작성 규칙, 원본 문서 피드백, 저장 전 최종 조정 체크리스트는 `references/worker-contract.md`를 따른다.

### 6. `[미정]` / `[가정]` / 확인 필요 질문 규칙 (단일 정의)

단일 패스이며 반복 질문 루프를 만들지 않는다. `[미정]`, `[가정]`, 확인 필요 질문, `[충돌 후보]`, inline 표시, 문서 끝 색인, 화면 출력 합산 규칙은 `../../references/markers-contract.md`의 `plan-format` 적용 기준을 따른다.

### 7. 두 파일 저장 단위로 파일 저장

두 문서는 하나의 two-file 저장 단위로 취급한다. 저장 위치, Project Docs SSOT 제외, timestamp, atomic `mkdir`, final 파일 precheck, tmp write, rename, cleanup, 저장 완료 성공 조건은 `../../references/storage-contract.md`의 `plan-format` 저장 규칙을 따른다.

### 8. 출력 계약 적용

저장 완료, 저장 보류, 사용자 결정 필요, 부분 저장 실패의 사용자 출력은 `../../references/output-contract.md`의 `plan-format` 템플릿을 따른다. 0개 섹션 생략, 복사 가능한 재실행 블록, `plan-review` 다음 단계 안내도 같은 계약을 따른다.

## 규칙

- 상위설계서는 지원하지 않는다.
- 초안은 항상 로컬에만 저장된다. 외부 발행 반영은 별도 절차다.
- 생성 문서는 로컬 초안 템플릿이며 공식 팀 문서가 아니다.
- Project Docs SSOT 근거 검증은 plan-review 책임.
- plan-format은 인터뷰 스킬이 아니다. 일반 입력이 부족하면 질문 루프를 만들지 않고 `plan-draft`로 보완을 유도한다. draft artifact input도 부족하면 `../../references/rerun-contract.md` 기준으로 `사용자 결정 필요`를 출력한다.
- 기존 산출물은 덮어쓰지 않는다.
- 정책서 세부 규칙은 허용/금지/조건/예외 판단 기준만. 화면 동작·입력 방식·사용자 노출 결과는 기능설계서.

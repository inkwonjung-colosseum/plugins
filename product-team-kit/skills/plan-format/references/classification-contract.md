# plan-format Classification Contract

`plan-format`이 충분한 기획 입력을 기능설계서와 정책서로 나눌 때 따르는 단일 분류 기준이다.

## 기본 귀속

| 입력 성격 | 귀속 문서 |
|:--|:--|
| 화면, 사용자 흐름, 진입점, 입력 항목, UI, 기능 동작, 사용자에게 보이는 결과, 가능 행위 | 기능설계서 |
| 업무 판단 기준, 규칙, 조건, 제한, 정책, 원칙, 예외 승인 기준, 상태 처리 기준 | 정책서 |

## 양쪽에 걸리는 항목

상태·권한·예외가 두 문서에 걸리면 아래 기준으로 나눈다.

- 정책서는 업무 판단 기준만 쓴다.
- 기능설계서는 사용자에게 보이는 결과와 가능 행위만 쓴다.
- 전체 상태표·권한표·예외목록을 양쪽에 중복하지 않는다.
- 같은 내용을 여러 섹션에 반복하지 않고 가장 적합한 한 곳에 배치한다.

## 항목별 판단 기준

| 항목 | 정책서에 쓸 내용 | 기능설계서에 쓸 내용 |
|:--|:--|:--|
| 상태 | 상태의 업무상 의미, 전이 조건, 허용/금지 기준 | 화면 표시 상태, 사용자가 할 수 있는 행동, 전이 후 보이는 결과 |
| 권한 | 역할별 허용/금지 판단 기준, 승인 기준 | 역할별 버튼/입력/조회 가능 여부, 접근 실패 시 사용자 결과 |
| 예외 | 예외 인정 조건, 승인/운영 판단 기준 | 오류/예외 발생 시 화면 메시지, 사용자 후속 행동, 재시도 가능 여부 |
| 조건 | 정책 적용 기준, 제한 조건, 기준값 | 조건 충족/미충족 시 기능 동작과 노출 결과 |

## 부서 경계

- 포함: 기능 목적, 정책 판단 기준, 사용자 흐름, 화면 입력·결과, 권한, 예외, 확인 기준처럼 기획자가 결정해야 하는 제품·업무 계약.
- 제외: 디자인 상세(컬러·폰트·스펙·Figma), 최종 UX copy, QA 테스트 케이스, API 명세, DB schema, 운영 런북, 개발 작업 분해.
- 제외된 상세가 입력에 섞여 있으면 기획 판단에 필요한 최소 맥락만 한 줄로 요약하고, 상세는 원본 문서 피드백에 남긴다.
- 입력의 주된 내용이 디자인·개발 산출물이고 저장 가능 조건을 충족하지 못하면 디자인·개발 heavy 저장 보류를 반환한다.

## Worker 적용

worker는 이 계약과 handoff artifact를 함께 따른다. worker가 새 역할, 정책, 범위, 상태를 만들거나 기존 canonical 값을 재판단해서 문서별 배치를 바꾸면 안 된다.

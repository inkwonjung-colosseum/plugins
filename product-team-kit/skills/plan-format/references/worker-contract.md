# plan-format Worker Contract

`plan-format`은 공통 분석을 먼저 끝낸 뒤 기능설계서/정책서 본문만 worker 계약에 따라 병렬 또는 순차 작성한다.

## 병렬화 원칙

공통 분석은 순차로 수행한다. 문서 본문 작성만 병렬화한다. 최종 조정과 파일 write/rename은 단일 실행 흐름으로 수행한다.

subagent 또는 분리 컨텍스트로 병렬 worker를 실행할 수 없는 환경에서는 같은 worker 계약을 유지한 채 동일 세션에서 기능설계서 본문 작성 후 정책서 본문 작성을 순차 수행한다.

## Handoff Artifact

먼저 단일 실행 흐름에서 공통 정리 기준을 handoff artifact로 확정한다. 이 artifact는 저장 문서에 포함하지 않는다.

```markdown
## 공통 정리 기준 (handoff, 저장 안 함)

### 기능 식별
- 추출 기능명 (canonical): ...
- 안전기능명 (canonical): ...

### 범위 (canonical)
- 적용 범위: ...
- 제외 범위: ...

### 핵심 사용자 행동
- [역할]: [행동] -> [기대 결과]

### 주요 정책·제약
- ...

### 역할명 set (canonical)
- [역할명]: [설명]

### 용어 dict (canonical)
- [용어]: [정의]

### synonym dict
- [canonical 용어 또는 역할명]: [허용 동의어 목록]

### 문서별 배치
- 기능설계서: ...
- 정책서: ...

### 확정/미확정 상태 (canonical)
- [미정] [섹션명]: [이유]
- [가정] [섹션명]: [내용]
- [확인 필요] [섹션명]: [결정 주체와 후속 확인 방법]
- [충돌 후보] [섹션명]: [입력 내부 상충 표현]

### 원본 문서 피드백 후보
- [유형]: [관찰]
```

## Worker 시작 조건

- canonical 값(기능명, 안전기능명, 적용 범위, 제외 범위, 역할명 set, 용어 dict, 확정/미확정 상태)이 확정값 또는 명시적 marker(`[미정]`, `[가정]`, `[확인 필요]`, `[충돌 후보]`)로 채워졌는가.
- synonym dict가 필요한 동의어를 포함하거나, 동의어가 없음을 명시했는가.
- 미확정 항목, 확인 필요 질문, 입력 내부 충돌 후보가 확정 사실과 분리되었는가.
- 조건을 만족하지 못하면 병렬 worker로 넘기지 않고 단일 실행 흐름에서 공통 정리 기준을 보완한다.

## Worker 실행

- 기능설계서 worker: `skills/plan-format/templates/기능설계서.md`와 `classification-contract.md` 기준으로 기능설계서 본문을 담당한다.
- 정책서 worker: `skills/plan-format/templates/정책서.md`와 `classification-contract.md` 기준으로 정책서 본문을 담당한다.
- 병렬 worker를 실행할 수 없으면 동일 세션에서 기능설계서 worker 산출을 먼저 작성하고 이어서 정책서 worker 산출을 작성한다. 이 fallback에서도 아래 worker 계약은 동일하게 적용하며, 첫 worker 산출에서 새 canonical 값·역할·정책·범위를 만들 수 없다.

각 worker는 공통 정리 기준과 원 입력만 근거로 사용한다. 템플릿은 최종 문서 골격이며 복사용 체크리스트가 아니다. 섹션 참조는 `기능설계서 6. 권한과 데이터 접근`처럼 직접 표기한다.

## Worker 계약

- 금지: canonical 값 재명명·추가·삭제
- 금지: 새 사실·역할·정책·범위 생성
- 금지: 확정/미확정 상태 재판단
- 금지: synonym dict에 없는 동의어 치환. dict 밖 표현은 canonical 값으로 통일하거나 `[미정]`/확인 필요 질문으로 남긴다.
- 허용: 의미를 보존하는 문서체 정리, 능동/수동 변환, 표 셀에 맞춘 축약, 한 줄 요약
- 허용: 기능설계서/정책서 템플릿에 맞춘 문서별 세부 배치와 문장 구성

## Mermaid

- 표현 가능하면 그린다. 표·본문에 이미 있는 내용만 시각화하고 새 사실은 만들지 않는다.
- 기능설계서 `3. 진입점과 사용자 흐름`: 사용자 행동이 있으면 `flowchart`.
- 정책서 `6. 상태 및 처리 기준`: 상태가 있으면 `stateDiagram`, 판단 분기가 있으면 `flowchart`.
- 미확정 노드·라벨은 `[미정]` 표시하고 임의 확정하지 않는다.

## 작성 규칙

- 작성 가이드, HTML 주석, 예시 placeholder, `[기능명]`, `[정책명]`, 값 없는 `- 항목:`, 빈 표/행, 값 없는 표 행, 빈 metadata, 빈 섹션, handoff artifact heading, 생성 과정 설명(`원본`, `원문`, `입력 반영 요약`, `섹션 적용 체크리스트` 등)은 결과물에서 제거한다. 내용이 필요한데 확정할 수 없으면 빈칸을 남기지 않고 `[미정]`/`[가정]`/`[확인 필요]`로 표현한다.
- 문서별 배치와 중복 방지는 `classification-contract.md`를 따른다. 같은 내용이 여러 섹션에 해당하면 가장 적합한 1곳에만 배치한다. 단, marker inline 표시는 원위치 계약이고 문서 끝 `미확정·가정·확인 필요` 섹션은 메타 색인이므로 중복 배치로 보지 않는다.
- 기능설계서 6장·정책서 7장 역할명은 입력에서 추출하고 두 문서에 동일하게 쓴다. 감지 불가시 `[미정]`으로 남긴다.
- 기능설계서의 `관련 정책서`와 정책서의 `관련 기능설계서`는 같은 output folder의 상대 링크를 기본값으로 사용한다.
- `외부/타시스템 연동`, `운영 조치`, `관련 문서`, `접속 환경`은 입력 근거가 있을 때만 생성한다.

## 원본 문서 피드백

원본 정리 중 품질 이슈는 별도 수집한다. 본문에 섞지 않고 화면 출력에만 요약한다. 문서 확정에 영향 주는 항목은 본문에도 `[미정]`/`[가정]`/`[확인 필요]`로 남긴다.

대상: 중복 내용, 상충/모순, 용어 불일치, 범위 혼입, 구조 문제, 근거 부족, 표현/품질 문제.

입력 내부에 `[충돌 후보]`가 있으면 확정 사실로 바꾸지 않고 원본 문서 피드백 후보 또는 확인 필요 질문으로 보존한다. `plan-format`은 Product Docs SSOT를 검색하거나 검증하지 않는다.

## 저장 전 최종 조정 체크리스트

- 역할명·기능명·범위·용어 두 문서 일치
- 기능설계서와 정책서 양쪽 모두 저장 가능한 실질 내용이 있으며 한쪽이 빈 골격만 남지 않음
- 부적절한 중복 없음, 배치 기준 준수
- `[기능명]`, `[정책명]`, 값 없는 `- 항목:`, 빈 템플릿 행, 값 없는 표 행, 빈 섹션, 예시 placeholder, handoff artifact heading 없음
- `[미정]`/`[가정]`/`[확인 필요]`/`[충돌 후보]`가 inline, 문서 끝 색인, 화면 출력 합산 기준대로 취합
- 원본 문서 피드백이 화면 출력에 포함
- Mermaid가 표/본문과 일치하고 새 사실을 만들지 않음

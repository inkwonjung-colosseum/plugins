# Output Format

`plan-review`의 최종 출력 단일 기준이다. 판정과 합성 규칙은 `review-rules.md`를 따른다. 출력은 사람용 리포트 하나로 통일하며 별도 YAML manifest 블록은 사용하지 않는다.

> **출력 금지 — fence wrapper**: 아래 3종 템플릿(`통과`/`조건부 통과`/`수정 필요`)은 docs 가독성 위해 ````text ... ```` 4-backtick fence로 감싸 두었다. 실제 사용자 출력에는 이 fence를 포함하지 않는다. fence **내부 본문만** raw markdown(헤더·표·체크박스 list·`---` 구분선 등)으로 그대로 출력한다. ` ```text `/` ``` ` 같은 fence 라인을 출력에 포함하면 사용자 화면에서 전체 리포트가 코드 블록으로 렌더되어 표·체크박스가 깨진다. (`올바른 검토 대상이 아님`/`치명 설정 오류` 템플릿은 3-backtick fence를 사용하며 동일 원칙 적용 — 본문만 출력.)

## 출력 2층 구조

리포트는 항상 두 층으로 구성한다.

1. **상단 — 합의 결과 (사용자 행동용)**: dedup·보수 합성된 통합 list. 축·내부 ID는 표시하지 않는다.
2. **하단 — Agent별 원본 발견 (참고용)**: 각 worker(또는 main A축)가 반환한 원본 발견을 그대로 노출한다. 합의 결과는 상단을 우선한다.

상단은 기획자의 행동 가능성을 위한 면이고, 하단은 검토 추적성을 위한 면이다. 같은 발견이 여러 agent에 걸치면 상단에는 1회만, 하단에는 각 agent 블록에 그대로 남는다.

## 라벨 체계

판정 라벨:

| 내부 값 | 출력 표시 |
|---|---|
| `통과` | 통과 |
| `조건부 통과` | 조건부 통과 |
| `수정 필요` | 수정 필요 |
| unsupported input | 올바른 검토 대상이 아님 |
| config fatal | 치명 설정 오류 |

발견 분류 라벨:

| 분류 | 출력 표시 |
|---|---|
| 필수 수정 | 필수 수정 |
| 발행 전 확인 | 발행 전 확인 |
| 참고 | 참고 |

## 상단 — 공통 본문 블록

3종 출력이 공유한다.

1. **판정 헤더**: `판정`, `검토 대상`.
2. **한 줄 결론**: 1~2문장.
3. **먼저 할 일 / 먼저 고칠 항목**: 결과별 다음 행동 1~3개. 축·ID 표기 금지. 위치 + 어떻게 할지만 노출한다.
4. **기준 문서와의 충돌** 표: 항목, 초안 내용, 기준 문서, 판단.
5. **결과별 추가 블록**: 필수 수정 항목 표 / 발행 전 확인 항목 표 / 체크리스트.
6. **상세 검토 기록**:
   - Coverage 표 (검토 축, 상태, 발견 항목 수, 근거)
   - 읽은 근거 list
   - 읽지 않은 관련 후보 list
   - 제외 후보 list
   - 검증 한계 list

상단 표에는 축·ID 컬럼을 두지 않는다. 컬럼 구성은 결과별 템플릿을 따른다.

## 하단 — Agent별 원본 발견

상단 직후에 다음 블록을 둔다. 각 agent 별 단일 표로 노출한다. 발견 0건이면 표 대신 `발견 사항 없음` 한 줄을 둔다. main A축이 SSOT corpus 0건(추출 성공)으로 `검증 대상 없음`이면 `검증 대상 없음 (SSOT corpus 0건)` 한 줄을 둔다.

| 컬럼 | 값 |
|---|---|
| 제목 | 한 문장 요약 |
| 위치 | 문서 경로 + 섹션 |
| 분류 | 필수 수정 / 발행 전 확인 / 참고 |
| 발견 유형 | 오류 / 누락 |
| 근거 인용 | 짧은 원문 인용 또는 파일 근거 |
| 영향 | 발행, 디자인, 구현, 운영, QA 판단에 미치는 영향 |
| 최소 수정 또는 확인 조건 | 필요한 최소 수정 또는 기획자 확인 조건 |

축은 블록 헤더가 표시하므로 표에는 축 컬럼을 두지 않는다. 내부 ID는 표시하지 않는다. dedup·보수 합성을 적용하지 않은 raw 그대로 노출한다.

표 출력 형식은 `review-rules.md ## 발견 사항 필드 → 표 출력 형식 (GFM)`을 단일 진실 소스로 따른다. 핵심:

- 헤더와 데이터 행 모두 leading/trailing `|`로 감싼다.
- 헤더 바로 아래에 `|---|---|---|---|---|---|---|` separator 행 1개(7 컬럼).
- cell 안 `|`는 `\|`로 escape (전각 `｜` 치환 금지).
- cell 안 줄바꿈은 공백 또는 `<br>`로 치환.

이 규칙을 어긴 worker 출력은 main이 cell escape·separator 행 보정 후 노출하고 `검증 한계`에 보정 사실을 남긴다. 보정으로 컬럼 수를 맞출 수 없으면 해당 worker 블록을 fenced ` ```text ``` `로 노출한다.

## 결과별 추가 블록

- **통과**: 발행 준비 체크리스트.
- **조건부 통과**: 발행 전 확인 항목 표 + 발행 준비 체크리스트.
- **수정 필요**: 필수 수정 항목 표 + 재검토 안내 체크리스트.
- **올바른 검토 대상이 아님**: 다음 행동 안내만. 하단 agent 블록도 출력하지 않는다.
- **치명 설정 오류**: 사유 + `set-config` 안내만. 하단 agent 블록도 출력하지 않는다.

`발행 준비 체크리스트`와 `재검토 안내 체크리스트`는 사람용 markdown 체크박스 list로만 출력한다. YAML manifest는 사용하지 않는다.

````text
1. 기능/화면설계서와 정책서 묶음이 팀에 공유할 대상인지 최종 확인하세요.
2. 팀의 외부 반영 절차에 따라 문서 반영 여부를 결정하세요.

기준 문서와의 충돌:
| 항목 | 초안 내용 | 기준 문서 | 판단 |
|---|---|---|---|

발행 준비 체크리스트:
- [ ] 검토 대상 초안의 기능설계서/정책서 쌍을 확인한다.
- [ ] 팀 문서 반영 후 팀 문서 ID와 update timestamp를 별도 운영 기록에 남긴다.
- [ ] plan-review가 외부 시스템에 직접 게시하지 않는다.
- [ ] <outputRoot>/ 산출물을 Product Docs SSOT 근거로 승격하지 않는다.
- [ ] Product Docs SSOT Markdown 또는 팀 문서 export snapshot을 자동 수정하지 않는다.

상세 검토 기록:

검토 기준: 2축 점검 (SSOT 충돌, 용어 일관성)

Coverage (`통과`는 필수 수정·발행 전 확인 0건이 조건이며, 참고 항목은 ≥0건 가능):
| 검토 | 상태 | 발견 항목 수 (필수 수정 / 발행 전 확인 / 참고) | 근거 |
|---|---|---|---|

| B. 용어 일관성 | completed | 0 / 0 / [참고 건수] | 본문 직접 점검 |

참고 항목 (≥1건일 때만 출력):
| 제목 | 위치 | 근거 인용 | 영향 |
|---|---|---|---|
| [제목] | [문서 > 섹션] | [짧은 인용] | [영향] |

읽은 근거:
- path: [상대경로] / kind: [markdown|linked_local_resource] / source_type: [policy|prd|requirement|feature|screen|operations|qa|unknown] / role: [primary|supporting|conflict_candidate|context_only] / version: [vX.Y|unversioned|unknown] / current_evidence: [true|false] / status: [current|draft|archive|deprecated|unknown] / freshness: [explicit_current|dated|undated|unknown]
- (SSOT corpus 추출 성공, 매칭 0건이면) `SSOT corpus 0건 (관련 Markdown 부재) — A. SSOT 충돌 축 검증 대상 없음`

읽지 않은 관련 후보: 없음

제외 후보:
- [외부 URL, 코드, 설정, <outputRoot>/ 하위 등 / 제외 사유 또는 없음]

검증 한계: 없음

---

이하 각 agent 원본 발견 (참고용). 합의 결과는 상단. 같은 발견이 여러 agent에 걸치면 양쪽 모두 노출됨.

### A. SSOT 충돌 (main)

(corpus 0건이면 대신: `검증 대상 없음 (SSOT corpus 0건)`)

발견 사항 없음.
````

## 수정 필요

````text
판정: 수정 필요
검토 대상: [파일경로]

한 줄 결론:
- 기준 문서와의 충돌 또는 필수 정보 누락이 있어 발행 전에 초안 수정이 필요합니다.

먼저 고칠 항목:
1. [문서 > 섹션 / 어떻게 고칠지]
2. [문서 > 섹션 / 어떻게 고칠지 또는 없음]
3. (SSOT corpus 추출 실패인 경우) ssot.include glob 또는 파일 권한을 확인한 뒤 plan-review를 다시 실행하세요.
4. 수정 후 같은 경로로 plan-review를 다시 실행하세요.

기준 문서와의 충돌:
| 항목 | 초안 내용 | 기준 문서 | 판단 |
|---|---|---|---|
| [항목 또는 없음] | [초안 내용 또는 없음] | [기준 문서 요약 또는 없음] | [충돌 / 근거 부족 / 확인 필요] |

| 제목 | 위치 | 근거 인용 | 영향 | 어떻게 고칠지 | 수용 기준 |
|---|---|---|---|---|---|
| [제목] | [문서 > 섹션] | [짧은 인용] | [영향] | [수정 포인트] | [확인 기준] |

발행 전 확인 항목:
| 제목 | 위치 | 근거 인용 | 영향 | 확인할 내용 | 확인 후 처리 |
|---|---|---|---|---|---|
| [제목 또는 없음] | [문서 > 섹션 또는 없음] | [짧은 인용 또는 없음] | [영향 또는 없음] | [확인 조건 또는 없음] | [문서 반영 여부 또는 없음] |

재검토 안내 체크리스트:
- [ ] 위 필수 수정 항목을 초안에서 직접 수정한다.
- [ ] 새 사실은 만들지 않고, 근거 인용 또는 검토 대상 본문에 없는 내용은 [확인 필요]로 남긴다.
````

## 올바른 검토 대상이 아님

```text
판정: 올바른 검토 대상이 아님
검토 대상: [파일경로]

사유: plan-review는 plan-format으로 작성한 기능/화면설계서 또는 정책서 초안만 검토합니다. 상위설계서나 다른 문서 타입은 이 gate의 지원 대상이 아닙니다.

다음 행동:
1. 기능/화면설계서와 정책서 초안 폴더를 지정하세요.
2. 단일 파일을 지정할 경우 같은 폴더에 짝문서가 있는지 확인하세요.
3. Claude Code: /product-team-kit:plan-review <초안 폴더 또는 기능설계서/정책서 파일경로>
4. Codex: $plan-review <초안 폴더 또는 기능설계서/정책서 파일경로>
```

## 치명 설정 오류

`.product-team-kit/config.json`이 없거나 검증을 통과하지 못하면 plan-review는 사전 점검 1에서 즉시 종료한다. step 헤더는 출력하지 않는다 (`SKILL.md ## 진행 표시 원칙` 참조). 사유는 `references/config-contract.md ## 치명 설정 오류`의 항목 중 해당하는 것만 한 줄로 명시한다.

```text
판정: 치명 설정 오류
검토 대상: [입력 경로]

사유: .product-team-kit/config.json 검증 실패. plan-review는 이후 단계(입력 타입 검증·SSOT 탐색·2축 점검)를 수행하지 않습니다.
- [구체 사유: 파일 없음 / JSON 파싱 실패 / 파일 읽기 실패 / version 누락·불일치 / outputRoot 검증 거부 중 해당 항목]

다음 행동:
1. set-config로 .product-team-kit/config.json을 생성하거나 갱신하세요.
   - Claude Code: /product-team-kit:set-config
   - Codex: $set-config
2. 설정 저장 후 같은 경로로 plan-review를 다시 실행하세요.
   - Claude Code: /product-team-kit:plan-review [검토 대상 경로]
   - Codex: $plan-review [검토 대상 경로]
```

치명 오류는 본 사유 라인에 한 번만 명시한다. 비치명 경고만 `[설정 경고]` 블록을 사용한다.

## 출력 순서

상단에서 하단으로 다음 순서를 지킨다.

1. 판정과 검토 대상
2. 한 줄 결론
3. 먼저 할 일 / 먼저 고칠 항목
4. 기준 문서와의 충돌
5. 결과별 추가 블록 (필수 수정 항목 / 발행 전 확인 항목 / 재검토 안내 / 발행 준비 체크리스트)
6. 상세 검토 기록 (Coverage, 읽은 근거, 읽지 않은 후보, 제외 후보, 검증 한계)
7. `---` 구분선 + "이하 각 agent 원본 발견 (참고용)" 안내
8. Agent별 원본 블록 (A → B 순)
9. `[설정 경고]` 블록 (있을 때만, 한 번)

올바른 검토 대상이 아님·치명 설정 오류 분기는 8번 블록을 출력하지 않는다. 치명 설정 오류 분기는 5·6·7번도 출력하지 않으며 1~3번(판정·검토 대상·사유·다음 행동)만 출력한다.

## 금지 행동

- plan-review는 외부 시스템에 직접 게시하지 않는다.
- `<outputRoot>/` 산출물을 Product Docs SSOT 근거로 승격하지 않는다.
- Product Docs SSOT Markdown, 팀 문서 export snapshot, linked local resource를 자동 수정하지 않는다.
- 코드, 설정 파일을 수정 대상으로 제안하지 않는다.
- 검토 대상 본문 또는 SSOT 근거에 없는 사실을 새로 만들지 않는다.
- 상단 통합 표에 축·내부 ID 컬럼을 추가하지 않는다.
- 하단 agent 블록의 발견을 dedup·재합성하지 않는다 (raw 그대로).

# Review Gate

`plan-format` 결과물을 외부 발행 절차에 넘길 수 있는지 판단할 때 사용하는 단일 참조 기준이다. `plan-review`는 검토 대상 파일과 Project Docs SSOT 근거를 직접 읽고 판단한다. 현재 대화는 근거가 아니다.

출력 형식은 `output-templates.md`, 근거 패키지 형식은 `evidence-package-schema.md`, 역할별 portable prompt는 `reviewer-prompts.md`를 따른다.

## 용어

- **Project Docs SSOT**: `planning/`을 제외한 현재 프로젝트의 Markdown 문서와, 그 Markdown이 상대경로로 명시 참조한 로컬 resource.
- **SSOT corpus**: Project Docs SSOT 후보 탐색 범위. 코드, 테스트, 설정, 빌드 산출물, dependency/vendor, 외부 URL은 제외한다.
- **review target**: `plan-format`이 저장한 기능설계서/정책서 초안. `planning/` 아래에 있어도 검토 대상으로 읽는다.
- **evidence source**: 검토 주장과 직접 관련되어 읽은 Markdown 또는 linked local resource.
- **linked local resource**: 선택된 Markdown에서 상대경로로 링크하거나 임베드한 프로젝트 내부 파일.

## 필수 검토 입력

- 검토 대상 초안 폴더 또는 기능설계서/정책서 파일 경로.
- 각 관점이 직접 읽은 초안 본문.
- 초안에 명시된 관련 문서.
- 구체적인 주장과 충돌 가능성이 있는 Project Docs SSOT 근거.
- `evidence-package-schema.md` 형식의 근거 패키지.
- 검토자 역할과 관점별 범위.

어떤 사실이 대화 맥락에만 있고 초안이나 선택한 근거 문서에 없으면 근거 부족으로 본다.

## 실행 모델

1. 입력 문서가 기능설계서 또는 정책서인지 확인한다. 상위설계서나 다른 문서 타입은 지원하지 않으며 내부 판정은 P0 gate failure다. 사용자 출력은 `output-templates.md`의 입력 오류 템플릿을 사용한다.
2. 폴더 입력이면 기능설계서와 정책서를 함께 읽는다. 단일 파일 입력이면 같은 폴더에서 `plan-format` 산출 파일명인 `[안전기능명]_기능설계서.md` / `[안전기능명]_정책서.md`의 같은 stem을 우선해 짝문서를 찾고, 없으면 검증 한계에 남긴다.
3. 근거 검토자가 Project Docs SSOT 근거를 선택하고 근거 패키지를 만든다.
4. 근거 패키지 상태가 `failed`이면 후속 두 관점을 실행하지 않고 최종 결과를 `수정 필요`로 취합한다.
5. 근거 패키지 상태가 `completed` 또는 `limited`이면 결정·범위 관점과 실행·검증 가능성 관점은 검토 대상 파일과 근거 패키지를 사용한다. 실행 환경이 지원하면 두 관점은 병렬 또는 분리된 독립 컨텍스트로 수행한다.
6. 최종 취합은 근거 없이 검토 결과를 완화하지 않고 가장 보수적인 결과를 사용한다.

독립 검토 컨텍스트를 만들 수 없는 실행 환경은 `limited`로 기록하고 `pass`를 반환하지 않는다. 이 제한은 근거 패키지와 후속 관점의 검증 한계에 전파한다. 문서 수정 없이는 개발·운영·QA 판단이 달라지는 발견 사항이 있으면 `수정 필요`다.

## Project Docs SSOT 근거 선택

1. 검토 대상은 항상 읽는다. 단, 검토 대상이 `planning/` 아래에 있으면 SSOT 근거가 아니라 review target으로만 사용한다.
2. 프로젝트 루트에서 `planning/`, `.git/`, dependency/vendor/build/cache/generated 경로를 SSOT corpus에서 제외한다.
3. 검토 대상에서 기능명, 정책명, 도메인, 역할명, 상태명, 권한명, 화면명, 핵심 조건·예외 키워드를 추출한다.
4. 위 키워드로 프로젝트 내 `*.md`, `*.markdown` 후보를 좁힌다. 코드, 테스트, 설정 파일은 후보에서 제외한다.
5. 선택한 Markdown이 상대경로로 명시 참조한 로컬 resource만 필요한 범위에서 추가 확인한다.
6. 외부 URL은 읽지 않는다. 외부 URL이 핵심 근거라면 `verification_limits` 또는 `excluded_candidates`에 남긴다.
7. 같은 주장과 직접 충돌 가능성이 있는 Markdown 후보를 찾는다. 충돌 후보를 읽지 않으면 `unread_candidates`에 이유를 남긴다.
8. `archive`, `old`, `deprecated`, `draft` 신호가 있는 문서는 현재 근거가 아니라 과거/초안 맥락으로만 사용하고 `use_as_current_evidence: false`로 기록한다.
9. 관련 Markdown이 없거나 핵심 linked local resource를 읽을 수 없으면 `limited` 또는 `failed`로 기록한다.

전체 프로젝트를 한 번에 읽지 않는다. 관련 후보를 넓히되 확인할 주장과 충돌 가능성이 있는 Markdown 및 그 Markdown이 참조한 로컬 resource로 제한한다. 파일 상태나 최신성을 추론할 수 없으면 `unknown`으로 기록하고, 그 한계가 발행 판단에 영향을 주면 `pass`를 반환하지 않는다.

## 검토자 역할

### 근거

출처 지원 여부, Project Docs SSOT와의 충돌, 근거 없는 가정, 오래된 문서 신호, 발행 가능성에 영향을 주는 `[가정]` 항목을 확인한다. 관련 Markdown과 linked local resource 탐색을 주도하고 근거 패키지를 만든다.

### 결정·범위

확정된 결정의 누락/충돌, 적용/비적용/예외 범위, 지원하지 않는 문서 타입, 관련 정책서/기능설계서 문서 연결을 확인한다. 부서 소유 상세 산출물이 본문에 완성본처럼 섞였는지 확인하고, 필요하면 관련 문서 또는 확인 필요 사항으로 분리하도록 제안한다.

### 실행·검증 가능성

개발·운영·QA가 대화 기억 없이 초안만 보고 움직일 수 있는지 확인한다. 조건, 상태, 예외, 권한, 업무 연동 경계, 업무 데이터, 외부 채널, 실패 대응, 운영 영향, 확인 기준을 필요한 수준으로 점검한다.

## 구조화된 발견 사항

각 발견 사항은 아래 필드를 가진다.

| 필드 | 값 |
|---|---|
| 관점 | 근거 / 결정·범위 / 실행·검증 가능성 |
| 제목 | 발견 사항을 한 문장으로 요약 |
| 위치 | 문서 경로와 섹션 |
| 심각도 | P0/P1/P2/P3 |
| 발견 유형 | 오류 / 누락 |
| 신뢰도 앵커 | 50 / 75 / 100 |
| 근거 인용 | 짧은 원문 인용 또는 파일 근거 |
| 영향 | 발행, 구현, 운영, QA 판단에 미치는 영향 |
| 최소 수정 포인트 또는 확인 조건 | 필요한 최소 문서 수정 또는 기획자 확인 조건 |
| 출력 버킷 | 수정 포인트 / 확인 조건 / 참고 관찰 |

### 심각도

- `P0`: 검토 불가, 지원하지 않는 입력, 필수 근거 미확인, 구조화 출력 실패처럼 gate 자체가 성립하지 않는 문제. 출력 버킷은 `수정 포인트`이며 결과는 `수정 필요`다.
- `P1`: 발행 전 문서 수정 없이는 개발·운영·QA 판단이 달라질 수 있는 오류 또는 누락. 출력 버킷은 `수정 포인트`이며 결과는 `수정 필요`다.
- `P2`: 기획자가 명시적으로 확인하거나 수용하면 문서 수정 없이 발행 후보가 될 수 있는 문제. 출력 버킷은 `확인 조건`이며 결과는 `conditional pass`다.
- `P3`: 사실 기반 관찰이지만 발행 판단을 낮추지 않는 항목. 출력 버킷은 `참고 관찰`이며 결과를 낮추지 않는다.

P2의 `오류`는 사실 충돌이 경미하거나 의도 변경 가능성이 있어 기획자가 명시적으로 수용하면 문서 수정 없이 발행 후보가 될 수 있는 경우에만 사용한다. 문서 수정 없이는 개발·운영·QA 판단이 달라지는 오류는 P1이다.

### 신뢰도 앵커

- `100`: 검토 대상 문서와 Project Docs SSOT 근거가 직접 뒷받침한다.
- `75`: 명시 문장에 기반한 단일 추론이며 반대 근거가 없다.
- `50`: 후보 미확인, 상태·최신성 불명확, linked local resource 미확인, 간접 근거처럼 검증 한계가 있다.

신뢰도는 표시와 병합 보조 기준이다. 신뢰도만으로 출력 버킷을 낮추지 않는다. gate 상태는 `completed`, `limited`, `failed`가 결정한다. 신뢰도 앵커가 `50`이면 `verification_limits` 또는 발견 사항의 영향에 그 이유가 드러나야 한다.

### `[미정]`과 `[가정]`

- `[미정]`이 선택적 세부, 후속 부서 산출물, 발행 판단에 영향이 없는 열린 질문이면 결과를 낮추지 않는다.
- `[미정]`이 구현·운영·QA 판단에 필요한 정책, 예외, 권한, 상태, 확인 기준이면 P1 또는 P2로 분류한다.
- `[가정]`이 현 근거로 확인되거나 발행 판단에 영향이 없으면 참고 관찰로 둘 수 있다.
- `[가정]`이 기획자 확인으로 닫힐 수 있으면 P2 확인 조건이다.
- `[가정]` 때문에 문서 수정 없이는 정책 또는 기능 판단이 달라지면 P1 수정 포인트다.
- `[미정]`이 아닌 확정 문장과 Project Docs SSOT 근거가 충돌하면 충돌로 판단한다.

## 구조화 출력 상태

- `completed`: 검토 대상과 필요한 근거를 읽었고, 관점별 결과와 모든 필수 발견 필드가 있다.
- `limited`: 관점별 결과는 있으나 일부 finding 필드 누락, 관련 Markdown 부재, 상태·최신성 불명확, linked local resource 일부 미확인, 독립 컨텍스트 제한 같은 검증 한계가 있다.
- `failed`: 필요한 검토 결과, 필수 필드, 검토 대상 본문, 또는 근거 패키지가 없어 gate 판정 자체가 불가능한 상태다.

발견 사항이 0개인 것은 실패가 아니다. 필요한 근거를 읽고 관점별 결과와 필수 출력 필드가 있으면 발견 사항 0개로도 `completed`가 될 수 있다.

`limited` 또는 `failed`가 있으면 `pass` 금지다.
`failed`는 항상 P0이며 최종 결과는 `수정 필요`다.
Coverage 상태가 `failed`인 관점은 관점별 검토 결과를 `failed: 결과 없음`으로 기록한다.

## 근거 제한

- 관련 Markdown 근거가 없으면 pass 금지.
- 핵심 linked local resource를 읽지 못했으면 pass 금지.
- SSOT corpus 범위가 불명확하면 pass 금지.
- `planning/` 하위 파일을 SSOT 근거로 사용했으면 pass 금지이며, 판단에 영향을 주면 `수정 필요`다.
- 외부 URL, 코드, 테스트, 설정 파일만 핵심 근거로 남아 있으면 pass 금지다.
- 독립 검토 컨텍스트를 만들 수 없으면 `limited`로 기록하고 pass 금지.

위 경우 중 `limited`는 누락된 근거가 외부 발행에 중요하지 않고 남은 확인 조건이 명확할 때만 `conditional pass`가 될 수 있다. `failed`는 항상 P0이며 최종 결과를 `수정 필요`로 고정한다.

## 구조화된 발견 사항 합성

1. 필수 필드가 빠진 발견 사항은 최종 판단에 사용하지 않고 검증 한계에 기록한다.
2. `위치 + 제목 + 근거 인용`을 정규화해 중복 발견을 병합한다.
3. `위치`는 repo 상대 경로와 섹션 경로로 정규화한다.
4. `제목`은 앞뒤 공백을 제거하고 연속 공백을 1칸으로 줄이며 ASCII 문자는 lower-case로 맞춘다.
5. `근거 인용`은 앞뒤 공백을 제거하고 연속 공백을 1칸으로 줄이며 120자 이내 핵심 인용으로 맞춘다.
6. 같은 위치에서 제목 또는 인용이 달라도 영향과 최소 수정 포인트 또는 확인 조건이 동일하면 하나의 발견 사항으로 병합한다.
7. 병합 시 더 높은 심각도, 더 높은 신뢰도, 더 보수적인 출력 버킷을 채택한다.
8. 같은 위치에서 관점 간 판단이 충돌하면 하나의 발견 사항으로 병합하고 확인 조건 또는 수정 포인트로 남긴다.
9. 수정 포인트가 하나라도 있으면 최종 결과는 수정 필요.
10. 수정 포인트가 없고 확인 조건만 있으면 conditional pass.
11. 참고 관찰만 있으면 최종 검토 결과를 낮추지 않는다.
12. 관점별 결과와 발견 사항의 출력 버킷이 충돌하면 더 보수적인 결과를 채택하고, 충돌 사실을 해당 발견 사항의 `영향` 또는 `검증 한계`에 남긴다.

## 검토 결과 취합

현재 컨텍스트는 관점별 결과를 정리하고 요약할 수 있지만, 파일 기반 근거 없이 어떤 검토 결과도 완화할 수 없다.

최종 검토 결과는 관점별 검토 결과 중 가장 보수적인 값을 사용한다. 보수 순서: `수정 필요 > conditional pass > pass`.

- 검토자 중 하나라도 `수정 필요`를 반환하면 최종 검토 결과는 `수정 필요`.
- 관점별 검토 결과에 `failed: 결과 없음`이 있으면 최종 취합에서 P0으로 처리하고 최종 검토 결과는 `수정 필요`.
- `failed`가 없고 P0/P1 수정 포인트가 없으며, P2 확인 조건이 있거나 `limited`가 있으나 남은 조건이 명시적이면 최종 검토 결과는 `conditional pass`.
- 세 관점이 모두 `pass`이고 모든 구조화 출력 상태가 `completed`이며 P0/P1/P2와 verification limit이 없을 때만 최종 검토 결과는 `pass`.

현재 컨텍스트와 관점별 판단이 다르면 더 보수적인 검토 결과를 사용한다.

## 결과 기준

### pass

중요한 `[가정]`, 충돌 문제, 수정 포인트, 확인 조건, verification limit이 남아 있지 않고, 관련 Project Docs SSOT Markdown 및 필요한 linked local resource를 충분히 읽었으며, 개발 또는 운영이 움직일 만큼 초안이 구체적일 때만 사용한다. 발견 사항이 없거나 P3 참고 관찰만 남은 경우에만 가능하다.

### conditional pass

남은 문제가 명시적이고 기획자가 발행 전에 확인하거나 수용할 수 있을 때 사용한다. 확인 내용이 향후 근거가 되어야 하면 초안 또는 Project Docs SSOT 문서에 반영하도록 안내한다.

### 수정 필요

누락된 결정, 충돌, 불명확한 규칙, 근거 없는 가정, 지원하지 않는 문서 타입 때문에 구현 또는 운영 판단이 달라질 수 있으면 사용한다.

## 검토 경계

- 초안을 직접 다시 쓰지 않는다.
- 필요한 최소 수정 사항만 짚는다.
- 대화 기억을 근거로 사용하지 않는다.
- `planning/` 산출물은 현재 근거가 아니라 review target 또는 과거 초안 맥락으로만 취급한다.
- 로컬 근거가 오래되었거나 부족하면 가정으로 채우지 말고 어떤 근거가 부족한지 말한다.

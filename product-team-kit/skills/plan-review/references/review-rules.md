# Review Rules

`plan-review`의 단일 검토 기준이다. 검토 대상 파일과 필요한 Product Docs SSOT 근거를 직접 읽고 2축으로 점검한 뒤 결과를 합성한다. 출력 형식은 `output-format.md`를 따른다. 현재 대화 컨텍스트는 근거가 아니다.

## 용어

- **Product Docs SSOT**: `<outputRoot>/`을 제외한 현재 프로젝트의 Markdown 문서 중 제품 정책, PRD/요구사항, 기능/화면 설계, 운영/QA 판단을 담은 문서와, 그 Markdown이 상대경로로 명시 참조한 로컬 resource.
- **SSOT corpus**: Product Docs SSOT 후보 탐색 범위. 코드, 설정, 빌드 산출물, dependency/vendor, 외부 URL은 제외한다.
- **document bundle**: 같은 기능명의 기능/화면설계서와 정책서 묶음. 단일 파일 입력도 허용하며, 같은 폴더에서 짝문서를 찾아 함께 읽는다.
- **review target**: `plan-format`이 저장한 기능설계서/정책서 초안. `<outputRoot>/` 아래에 있어도 검토 대상으로 읽는다.
- **evidence source**: 검토 주장과 직접 관련되어 읽은 Markdown 또는 linked local resource.
- **linked local resource**: 선택된 Markdown에서 상대경로로 링크하거나 임베드한 프로젝트 내부 파일.

## 검토 대상 타입 판정

검토 대상이 기능설계서/정책서 초안인지 아래 룰로 판정한다. 모두 만족하지 않으면 `올바른 검토 대상이 아님`으로 종료한다.

판정 룰 (OR — 하나라도 만족하면 검토 대상):

1. **파일명 stem suffix**: `*_기능설계서.md`, `*_정책서.md` (plan-format 산출 파일명 규약, `plan-format/references/storage-contract.md`).
2. **H1 제목**: 본문 첫 H1이 `기능설계서`, `화면설계서`, `정책서` 단어를 포함.
3. **폴더 입력**: 입력이 폴더면 폴더 내부에서 위 1·2 조건을 만족하는 파일 ≥1개 존재.

명시적 제외 (즉시 `올바른 검토 대상이 아님`):

- 상위설계서, PRD, 회의록, 기획 메모, README, 코드 파일.
- 본문에 plan-format 산출 섹션 구조(`## 1. 개요`, `## 8. 미결 사항`/`## 10. 미결 사항` 등)가 전혀 없는 경우.

판정 모호 시(파일명 미일치 + H1 부분 일치)는 본문 섹션 헤더 패턴이 plan-format 템플릿과 일치하는지 추가 확인한 뒤, 그래도 모호하면 `올바른 검토 대상이 아님`으로 종료한다.

## 검토 입력

- 검토 대상 초안 폴더 또는 기능설계서/정책서 파일 경로.
- 검토 대상 본문.
- 초안에 명시된 관련 문서.
- 구체적 주장과 충돌 가능성이 있어 실제 읽은 Product Docs SSOT 근거.
- 검토 대상에서 키워드로 좁힌 SSOT corpus 후보. 후보가 0건이면 corpus 본문은 읽지 않는다.

대화 맥락에만 있고 검토 대상이나 근거 문서에 없는 사실은 근거 부족으로 본다.

## 실행 모델

1. `outputRoot`, `ssot.include`, `ssot.exclude`를 `../../references/config-contract.md` 기준으로 확정한다.
2. config 파일 없음, JSON 파싱 실패, `version` 미일치, `outputRoot` 검증 거부는 치명 설정 오류로 즉시 종료한다. 다른 검토 단계를 수행하지 않는다.
3. 입력이 기능설계서/정책서인지 확인한다. 다른 문서 타입이면 검토 결과를 만들지 않고 `올바른 검토 대상이 아님`으로 종료한다.
4. 폴더 입력이면 같은 폴더의 기능설계서와 정책서를 함께 읽는다. 단일 파일 입력이면 같은 폴더에서 `[안전기능명]_기능설계서.md` / `[안전기능명]_정책서.md` 같은 stem의 짝문서를 찾는다. 짝문서가 없으면 단일 검토를 진행하고 검증 한계에 `짝문서 없음`을 기록한다.
5. SSOT corpus 후보를 키워드로 좁힌다. 매칭 후보가 1건 이상이면 직접 관련된 Markdown과 필요한 linked local resource만 읽고, 0건이면 A축을 `검증 대상 없음`으로 처리한다.
6. 2축(SSOT 충돌, 용어 일관성)을 점검하고 발견 사항을 만든다. worker는 main이 inline으로 전달한 본문과 근거 패키지만 사용한다.
7. 보수 합성과 dedup 정규화로 최종 결과(통과/조건부 통과/수정 필요)를 결정한다.

검토자는 SSOT corpus 비용을 이유로 직접 관련된 후보를 임의 축소하지 않는다. 다만 config 실패, 입력 타입 실패, SSOT corpus 추출 실패, SSOT 매칭 0건 분기에서 쓰지 않는 corpus 본문은 읽지 않는다. 핵심 근거를 읽지 못하면 `검증 한계`에 남기고 결과를 낮춘다.

## SSOT corpus 선택 규칙

1. 검토 대상은 항상 읽는다. 단, 검토 대상이 `<outputRoot>/` 아래에 있으면 review target으로만 사용하고 SSOT 근거로 승격하지 않는다.
2. 프로젝트 루트에서 `<outputRoot>/`, `.git/`, dependency/vendor/build/cache/generated 경로를 제외한다.
3. 검토 대상에서 기능명, 정책명, 도메인, 역할명, 상태명, 권한명, 화면명, 핵심 조건·예외 키워드를 추출한다.
4. 위 키워드로 프로젝트 내 `*.md`, `*.markdown` 후보를 좁힌다. 제품 정책, PRD/요구사항, 기능/화면 설계, 운영/QA 판단 문서를 우선한다.
4.5. SSOT 후보 파일의 상위 20줄을 Bash 1회 호출로 일괄 읽어 인덱스를 구성한다. 파일명, 제목, 버전 표기(vX.Y), 상태 신호(archive/draft/deprecated/old), 섹션 헤더로 1차 분류한다. 인덱스 단계에서 제외되는 문서:
     - archive/draft/deprecated/old 신호가 파일명·제목·상단 메타데이터에 있는 문서
     - 같은 문서군에서 낮은 버전의 문서 (규칙 8 적용)
     - 키워드가 제목·섹션 헤더에 전혀 매칭되지 않는 문서
     인덱스로 분류 후 핵심 후보만 전문 읽기 대상으로 선정한다.
5. 인덱스에서 선정된 핵심 후보 Markdown이 상대경로로 명시 참조한 로컬 resource만 필요한 범위에서 추가 확인한다.
6. 외부 URL, 코드, 설정 파일은 SSOT 근거로 사용하지 않는다. 핵심 근거가 외부 URL뿐이면 `검증 한계`에 남긴다.
7. 같은 주장과 직접 충돌 가능성이 있는 Markdown 후보를 찾는다. 충돌 후보를 읽지 않으면 `읽지 않은 관련 후보`에 이유를 남긴다.
8. 파일명, 제목, 상단 메타데이터에 `vX.Y` 버전 표기가 있는 같은 문서군은 가장 높은 버전을 current evidence 후보로 사용한다. 낮은 버전은 과거 맥락으로만 쓰고 current evidence로 승격하지 않는다.
9. `archive`, `old`, `deprecated`, `draft` 신호가 있는 문서는 과거/초안 맥락으로만 사용한다.
10. 제품 문서인지 불명확한 Markdown은 context_only 또는 제외 후보로 남기고 current evidence로 승격하지 않는다.
11. 관련 Markdown이 없거나 핵심 linked local resource를 읽지 못하면 `검증 한계`에 남긴다.
12. SSOT corpus가 0건일 때는 추출 성공 여부에 따라 다르게 처리한다.

    (a) 추출 성공 + 매칭 0건 (glob 평가 OK, 후보 폴더 read OK, hit 없음):
        `A. SSOT 충돌` 축은 `검증 대상 없음`으로 자동 통과. 결과를 낮추지 않는다.
        `읽은 근거`/`기준 문서와의 충돌` 출력에 `SSOT corpus 0건 (관련 Markdown 부재)`을 명시한다.
        `검증 한계`에는 남기지 않는다.

    (b) 추출 실패 (glob 평가 실패, 후보 폴더 권한 거부, 핵심 후보 파일 read 실패, IO 오류 등):
        핵심 근거 미확보로 본다. 최종 결과는 `수정 필요`로 취합한다.
        `검증 한계`에 `SSOT corpus 추출 실패: <자연어 사유>` 한 줄 남긴다.
        `먼저 고칠 항목`에 `ssot.include glob 또는 파일 권한 확인 후 plan-review 재실행` 안내를 포함한다.

## 2축 점검 기준

각 축은 main이 확정한 검토 대상 본문과 근거 패키지를 기준으로 점검한다. SSOT corpus 매칭이 0건이면 A축은 `검증 대상 없음`으로 처리하고 B축은 검토 대상 본문만으로 점검한다. 같은 발견 사항이 여러 축에 걸치면 한 번만 기록하고 가장 보수적인 분류를 채택한다.

마커(`[미정]`/`[가정]`/`[확인 필요]`/`[충돌 후보]`) 자체는 본 검토의 분류 대상이 아니다. 마커는 plan-format 책임 영역이며, 검토 대상에 마커가 남아 있다는 사실만으로 결과를 낮추지 않는다. 다만 마커 본문이 SSOT current evidence와 충돌하면 A축 발견으로, 마커 본문 안에서 같은 대상을 가리키는 표기가 어긋나면 B축 발견으로 취급한다.

### A. SSOT 충돌

- 초안의 확정 문장이 SSOT current evidence와 충돌하는가.
- 같은 주장에 대해 SSOT가 침묵하면 근거 부족인지, 의도된 새 정책인지 검토 대상이 명시했는가.
- 버전이 낮거나 archive 상태인 문서를 근거로 채택하지 않았는가.
- 외부 URL, 코드, 설정 파일을 핵심 근거로 사용하지 않았는가.

### B. 용어 일관성

- 같은 대상을 가리키는 역할명, 상태명, 권한명, 화면명, 도메인 stem이 문서 묶음 안에서 통일되어 있는가.
- 정책서와 기능설계서 사이에서 용어가 어긋나지 않는가.
- SSOT의 표준 용어와 다르게 쓴 항목이 있으면 사유가 명시되어 있는가.

## 발견 사항 필드

각 발견은 아래 7 필드를 가진다. 축은 worker 정체성과 main A축이 자체적으로 부여하므로 출력 표에는 두지 않는다 (블록 헤더가 축을 지시한다). 분류는 사람용 출력 라벨과 동일하다.

| 필드 | 값 |
|---|---|
| 제목 | 한 문장 요약 |
| 위치 | 문서 경로 + 섹션 |
| 분류 | 필수 수정 / 발행 전 확인 / 참고 |
| 발견 유형 | 오류 / 누락 |
| 근거 인용 | 짧은 원문 인용 또는 파일 근거 |
| 영향 | 발행, 디자인, 구현, 운영, QA 판단에 미치는 영향 |
| 최소 수정 또는 확인 조건 | 필요한 최소 수정 또는 기획자 확인 조건 |

### 표 출력 형식 (GFM)

모든 발견 사항(main A축, B worker, 상단 통합 list)은 GFM pipe table 형식으로만 출력한다. 같은 규칙을 main과 worker 모두에 적용한다.

1. 헤더 행과 데이터 행 모두 **leading/trailing `|` 필수**: `| 제목 | 위치 | 분류 | 발견 유형 | 근거 인용 | 영향 | 최소 수정 또는 확인 조건 |`.
2. 헤더 바로 아래에 **separator 행** 1개: `|---|---|---|---|---|---|---|` (7 컬럼). 컬럼 수가 다르면 행 그대로 plain text로 렌더되어 표가 깨진다.
3. **cell 안 `|`는 `\|`로 escape한다 — backtick·HTML 안에 있어도 동일 적용**. GFM table 파서는 backtick code span 안 `|`를 column separator로 해석하는 경우가 많아 escape 없이 두면 컬럼 수가 어긋난다. 전각 `｜` 치환은 금지(의미 변형). 근거 인용에 원문 표 헤더(`\| 액션 \| 대상 채널 \|` 등), 역할 구분자(`사용자 \| 액션`), 용어 정의 행(`Active \| 활성화`)이 들어오는 경우가 잦으니 항상 escape 적용.
4. cell 안 줄바꿈은 1칸 공백 또는 `<br>`로 치환한다. 실제 개행을 cell 안에 넣지 않는다.
5. cell 안 backtick·HTML 그 자체는 그대로 둔다 (가독성). 단 backtick 안 `|`는 3번 룰에 따라 반드시 escape한다. cell 양 끝 공백 1칸은 가독성용으로 허용.
6. 빈 cell은 `—`(em dash) 또는 `없음`으로 채운다. 빈 문자열은 사용하지 않는다.
7. 표 외부에 추가 prose가 필요하면 표 위 또는 표 아래 별도 단락에 둔다. 표 직속 행 사이에 prose를 끼우지 않는다.

이 규칙은 worker 출력 계약과 `output-format.md` 하단 agent 블록 형식의 단일 진실 소스다. 워커가 1·2번 어김(separator 행 누락, leading/trailing pipe 누락) 또는 3번 어김(escape 안 한 pipe로 컬럼 어긋남, backtick 안 unescaped `|` 포함)을 했으면 `## 합성 규칙`의 retry/검증 한계 처리를 적용한다.

main 보정 단계 cell escape 알고리즘 (단일 진실 소스):
- 각 cell 내부에서 leading/trailing 외 `|` 문자가 unescaped 상태(`\|` 직전이 `\\` 아님)이면 모두 `\|`로 치환한다.
- backtick code span(` `...` `, `` ``...`` ``), HTML tag 안의 `|`도 동일하게 escape 대상이다. backtick·HTML 자체는 보존한다.
- 헤더 행과 separator 행은 escape 대상에서 제외한다 (구분자 역할).
- escape 후 cell `|` 카운트가 0이 될 때까지 반복 적용. 컬럼 수가 헤더와 일치하면 보정 성공.

### 분류 기준

- **필수 수정**: 문서 수정 없이는 발행 판단이 달라질 수 있는 충돌, 누락, 핵심 가정 미확정. 결과는 `수정 필요`.
- **발행 전 확인**: 사실 충돌이 경미하거나 의도 변경 가능성이 있어 기획자가 명시적으로 확인·수용하면 문서 수정 없이 발행 후보가 될 수 있는 항목. 결과는 `조건부 통과`.
- **참고**: 사실 기반 관찰이지만 발행 판단을 낮추지 않는 항목. 결과를 낮추지 않는다.

## 합성 규칙

합성은 **상단 통합 list**에만 적용한다. 하단 agent별 원본 블록은 dedup·재합성하지 않고 raw 그대로 노출한다 (`output-format.md`의 `## 출력 2층 구조`).

1. 필수 필드(제목, 위치, 분류, 근거 인용, 영향)가 빠진 발견은 최종 판단에 사용하지 않고 `검증 한계`에 기록한다. 축은 블록 헤더가 부여한다. `## 발견 사항 필드 → 표 출력 형식 (GFM)`을 어긴 worker 출력은 1회 retry, 2회 어김이면 main이 cell escape·separator 행 보정만 수행해 노출하고 `검증 한계`에 `<worker> 출력 형식 보정 적용` 한 줄 남긴다. 보정으로도 컬럼 수를 맞출 수 없으면 해당 worker 블록을 fenced ` ```text ``` ` 원본 텍스트로 노출한 뒤 `검증 한계`에 사유를 남긴다.
2. `위치 + 제목 + 근거 인용`을 정규화해 중복 발견을 병합한다 (상단 통합용).
3. `위치`는 repo 상대 경로 + 섹션 경로로 정규화한다.
4. `제목`과 `근거 인용`은 앞뒤 공백 제거, 연속 공백 1칸 축약, NFC 정규화 적용. ASCII는 lower-case로 맞춘다.
5. 같은 위치에서 영향과 최소 수정 또는 확인 조건이 동일하면 하나로 병합한다 (상단 통합용).
6. 병합 시 더 보수적인 분류를 채택한다 (필수 수정 > 발행 전 확인 > 참고).
7. 같은 위치에서 축 사이 판단이 충돌하면 하나로 병합하고 더 보수적인 분류로 남긴다 (상단 통합용).
8. 상단 통합 표에는 축·내부 ID 컬럼을 두지 않는다. 출력 형식은 `output-format.md`의 결과별 템플릿을 따른다.
9. 하단 agent별 원본 블록은 main A축 / B worker 발견을 그대로 노출한다. dedup·정규화·보수 합성을 적용하지 않는다.

## 결과 3종 기준

- **통과**: 필수 수정·발행 전 확인이 모두 0건이고, 핵심 근거를 충분히 읽었을 때만 사용한다.
- **조건부 통과**: 필수 수정이 0건이며 발행 전 확인 항목이 명시적이고 기획자가 발행 전에 확인·수용할 수 있을 때 사용한다.
- **수정 필요**: 필수 수정 1건 이상, 또는 핵심 근거를 확보하지 못해 gate 판정이 불가능할 때 사용한다. 단, SSOT corpus 자체가 0건이면 A축 검증 대상 부재로 보고 그 사유로는 결과를 낮추지 않는다. 단, 추출 자체에 실패해 0건이 된 경우는 핵심 근거 미확보로 보고 `수정 필요`로 취합한다.
- **올바른 검토 대상이 아님**: 입력이 기능설계서/정책서가 아닐 때 사용한다. 검토 결과를 만들지 않고 입력 안내로 종료한다.

짝문서가 없는 단일 입력은 결과 차단 사유가 아니다. 단, 검토 대상이 명시적으로 다른 문서의 정책/기능 판단에 의존하면 짝문서 부재가 `필수 수정` 또는 `발행 전 확인` 사유가 될 수 있다.

## 통과 금지 조건

아래 중 하나라도 해당하면 `통과`를 출력하지 않는다. 지정 종료 분기가 있으면 그 분기로 종료하고, 일반 검토 중 발견되면 `검증 한계`에 남긴 뒤 `보수 합성 우선순위`로 결과를 낮춘다.

- config 치명 오류가 있다.
- 입력이 기능/화면설계서 또는 정책서 초안이 아니다.
- SSOT corpus 추출이 실패했다.
- 키워드 매칭 핵심 후보가 있었지만 전문을 읽지 못했다.
- 필요한 linked local resource를 읽지 못했고 그 resource가 발행 판단에 영향을 준다.
- worker 발견 사항이 7필드 형식을 2회 연속 지키지 못했고 main이 동등 수준으로 보정하지 못했다.
- 필수 수정 또는 발행 전 확인 항목이 1건 이상 남아 있다.
- 결과 판단이 검토 대상 본문 또는 읽은 근거가 아닌 대화 컨텍스트·기억·추정에 의존한다.
- 최종 리포트에 읽은 근거, 읽지 않은 관련 후보, 제외 후보, 검증 한계 중 해당되는 기록이 누락되어 사용자가 판정 근거를 추적할 수 없다.

## 보수 합성 우선순위

`수정 필요 > 조건부 통과 > 통과` 순으로 가장 보수적인 결과를 선택한다.

- 필수 수정 1건이라도 → `수정 필요`.
- 핵심 근거 미확보 + 영향 큼 → `수정 필요`. 단, 미확보 사유가 SSOT corpus 자체 0건이면 A축 검증 대상 부재로 보고 결과를 낮추지 않는다.
- SSOT corpus **추출 실패**(권한 거부, read 실패, IO 오류 등)로 0건이 된 경우 → `수정 필요`. 결과 낮춤.
- 발행 전 확인 항목만 있으면 → `조건부 통과`.
- 모두 0건이면 → `통과`. SSOT corpus 0건으로 A축이 `검증 대상 없음`이어도 다른 축 조건을 충족하면 `통과`로 판단한다.

## 근거 패키지 (사람용)

YAML 스키마는 사용하지 않는다. 사람용 출력 하단에 4 sub-list로 기록한다.

- **읽은 근거**: 한 줄에 한 항목.
  - 형식: `path: <상대경로> / kind: <markdown|linked_local_resource> / source_type: <policy|prd|requirement|feature|screen|operations|qa|unknown> / role: <primary|supporting|conflict_candidate|context_only> / version: <vX.Y|unversioned|unknown> / current_evidence: <true|false> / status: <current|draft|archive|deprecated|unknown> / freshness: <explicit_current|dated|undated|unknown>`
- **읽지 않은 관련 후보**: 후보 경로 + 읽지 않은 이유.
- **제외 후보**: 외부 URL, 코드, 설정, `<outputRoot>/` 하위 등 + 제외 사유.
- **검증 한계**: 관련 Markdown 부재, linked resource 미확인, 상태/최신성 불명확, 짝문서 없음 등.

## 검토 경계

- 초안을 직접 다시 쓰지 않는다.
- 필요한 최소 수정만 짚는다.
- 대화 기억을 근거로 사용하지 않는다.
- `<outputRoot>/` 산출물은 review target 또는 과거 초안 맥락으로만 취급한다. SSOT 근거로 승격하지 않는다.
- 외부 시스템에 직접 게시하지 않는다.
- Product Docs SSOT Markdown, 팀 문서 export snapshot, linked local resource를 자동 수정하지 않는다.
- 로컬 근거가 부족하면 가정으로 채우지 않고 어떤 근거가 부족한지 기록한다.
